# 11. Triton Flash Attention 分块注意力前向 — 小白讲解

> 对应 notebook：[`11_Triton_Flash_Attention.ipynb`](./11_Triton_Flash_Attention.ipynb)

## 一句话总结

这个 notebook 教你用"在线 Softmax"（online softmax）把注意力计算拆成一块一块地流式完成，从头到尾不把巨大的分数矩阵写进显存。

## 为什么需要它：痛点是什么

注意力的公式是 $O=\mathrm{softmax}(QK^\mathsf{T}/\sqrt{D})V$。如果用朴素 PyTorch 的思路"先算完整矩阵再归一化"，就必须先物化一整张 $S_q\times S_k$ 的分数矩阵。序列一长（比如几千 token），这张矩阵的大小按序列长度**平方**增长，显存直接爆；就算显存装得下，把它写进显存再读回来，也是一大笔开销——GPU 的算力很强，但显存带宽（HBM）是瓶颈，大部分时间都耗在搬数上。

生活类比：统计全班同学对 100 家餐厅的评分并算加权平均。笨办法是先把 100×100 的打分表全部抄在黑板（显存）上再算；聪明办法是每个统计员（program）拿一小沓问卷，看完一家记一次"当前最高分、当前总分"，看完所有餐厅直接报结果——黑板上一行字都不用写。

麻烦在于：Softmax 的分母是**所有**位置的指数和，你必须"看完所有 Key"才能归一化。看不完怎么办？这就是本节要回答的。

## 核心问题

1. 一个 Q 块怎样遍历所有 K/V 块，且不同头之间互不干扰？
2. 处理后面的块时出现更大的分数，前面已经算过的部分怎样"追认修正"？（在线 Softmax 状态合并）
3. 序列尾部补零的位置和因果掩码（causal mask，即"查询只能看过去"）怎样保证不污染归一化？

## 解决思路：一步步看懂

**第 1 步：分工。** Q/K/V 形状为 $(B,H,S,D)$（批量、头数、序列长、每头维度）。二维 grid 的第一维选 Q 序列块（块宽 `BLOCK_M=32`），第二维把"批量×头"展平。比如 $B=2,H=3,S_q=70$ 时 grid 为 $(3,6)$，每个 program 负责某批某头的 32 行查询，独占一份输出。

**第 2 步：维护三个"滚动账本"。** 对每行查询保存三个状态：最大分数 $m$（初始 $-\infty$）、以 $m$ 为基准的指数和 $l$（初始 0）、同基准下的加权 V 之和 $a$（初始 0）。读入一个 K/V 块后：

$$m'=\max(m,\max_j s_j),\quad \alpha=e^{m-m'},\quad l'=\alpha l+\sum_j p_j,\quad a'=\alpha a+\sum_j p_j v_j$$

文字解释：换新的最大值基准时，历史 $l$ 和历史 $a$ 必须**乘同一个修正系数 $\alpha$**，因为它俩的比例就是最终输出的比例。notebook 里有个精巧的数值例子：第一块分数 0、值 2，状态 $(0,1,2)$；第二块分数 $\ln 2$、值 4，新基准下旧状态乘 $1/2$，最终输出 $10/3$——如果只修分母不修加权和，会错算成 4。对应核心代码：

```python
m_new = tl.maximum(m_i, m_block)      # 新基准 = 历史最大 vs 本块最大
p = tl.exp(scores - m_new[:, None])   # 本块分数的指数（都不超过 1）
alpha = tl.exp(m_i - m_new)           # 旧账本换算到新基准的汇率
l_new = l_i * alpha + tl.sum(p, axis=1)   # 分母：旧账×汇率 + 本块
acc = acc * alpha[:, None] + tl.dot(p.to(v.dtype), v)  # 加权和同理
```

**第 3 步：掩码要分清两种"补"。** 特征维越界补零只是加载安全——补零不改变真实点积，缩放也用真实 `head_dim`（`1/sqrt(head_dim)`），不是补齐后的宽度。但**键位置**越界必须把分数设成 $-\infty$：只把 K 补零的话，零点积是 0，$e^0=1$ 照样进分母，稀释真实位置的权重。因果模式再加一条 $j\le i$：查询位置 2 只能看键 0、1、2。

**第 4 步：循环结束才归一化。** 所有 K/V 块处理完后 `out = acc / l_i`，此时分母才包含全部有效键；再按真实查询行和特征边界写回输出。分数、$m$、$l$ 用 FP32 累加降低误差（FP16/BF16 输入，`p` 在矩阵乘法前转回 V 的类型）。

## 关键概念速查表

| 术语 | 大白话解释 |
|---|---|
| program | 一个工人线程块，这里负责"一个头的 32 行查询 × 全部 Key" |
| online softmax | 边流式处理边维护最大值/分母/加权和的 Softmax，不需要完整分数矩阵 |
| m_i / l_i / acc | 滚动账本三件套：历史最大分数、指数和、加权 V 累加器 |
| alpha | 换最大值基准时的"汇率"，历史分母和加权和要乘同一个 |
| BLOCK_M / BLOCK_N | Q 块宽（32）和 K/V 块宽（64） |
| mask（掩码） | 标记哪些位置有效的布尔条件，加载补零用一种、分数屏蔽用另一种 |
| causal（因果） | 查询只能看自己及之前的键位置，防止"偷看未来" |
| -inf 屏蔽 | 无效键分数设负无穷，指数变 0，彻底不进分母 |
| HBM 带宽 | 显存读写速度，长序列注意力往往卡在搬数而不是计算 |

## 小白常见疑问

**Q1：为什么不直接 for 循环逐块算 Softmax 再拼起来？**
每块各自 Softmax 再平均是错的：Softmax 的分母必须覆盖全部位置。不同块的分母不可比，先各自归一化再平均会给分数分布不同的块错误权重。必须用 $\alpha$ 把所有历史量换到同一基准。

**Q2：补零和设 $-\infty$ 有什么区别？零不是"没有贡献"吗？**
零分数的指数是 $e^0=1$，不是 0！它会被算进分母，把真实位置的权重全部拉低。所以特征维补零（安全加载）和键位置设 $-\infty$（概率归零）是两套逻辑，不能混用。

**Q3：为什么 $m$、$l$、acc 要用 FP32？**
一是 FP16/BF16 的表示范围和精度有限，长序列的累加误差会放大；二是指数前的减最大值让有效指数不超过 1，FP32 归约更稳。

**Q4：这个 kernel 支持训练反传吗？**
不支持。本 notebook 只实现等头数的稠密前向，启动器会拒绝 `requires_grad` 输入，也不支持 dropout 和 GQA。
