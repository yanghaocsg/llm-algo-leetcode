# 17. Triton 内存模型与调试 — 小白讲解

> 对应 notebook：[`17_Triton_Memory_Model_and_Debug.ipynb`](./17_Triton_Memory_Model_and_Debug.ipynb)

## 一句话总结
拆解 Triton 里两类最常见、又最会"装无辜"的计算错误——地址算错（步长）和填充值填错（掩码），并给出一套逐步缩小错误范围的调试方法。

## 为什么需要它：痛点是什么
在 PyTorch 里写 `x[i, j]`，框架替你处理一切布局细节；在 Triton 里你要自己把逻辑坐标换算成读写地址。于是出现两类典型事故：矩阵形状没变，结果却按行错位（读错了地址）；尾块只有几个真实元素，归约结果却多出一截（掩码位置填错了值）。
类比：步长（stride）就像楼房的门牌编号规则——两栋楼户型图（形状）完全相同，但一栋是每层 8 号起排、另一栋每层 11 号起排，"3 层 2 号房间"在两栋楼里根本不是同一个房间。掩码填充则像会议投票：缺席的人该投什么票？求和就投"零票"，选最大值就得投"负无穷票"——填错了，缺席者反而会赢。

## 核心问题
- 同一个逻辑坐标 `(i, j)`，为什么在不同张量里对应不同读写地址？
- 被掩码排除的位置仍然占着计算块里的一个位置，该给它填什么值？
- 出了错，怎样一步步定位是读错、写错还是填错？

## 解决思路：一步步看懂
1. **地址 = 基址 + 行号×行步长 + 列号×列步长**（步长以元素计）。例如两个形状同为 2×3 的视图，输入步长 (8,2)、输出步长 (11,3)：逻辑坐标 (1,2) 的输入偏移是 1×8+2×2=12，输出偏移却是 1×11+2×3=17。读输入用输入的步长，写输出用输出自己的步长——形状相同不等于布局相同。
```python
# TODO 1/2 的核心：两次换算各用各的步长
x_offsets = row * stride_x_row + columns * stride_x_col   # 读：输入布局
y_offsets = row * stride_y_row + columns * stride_y_col   # 写：输出布局
```
2. **掩码位置的填充值由后续运算决定**。求和补零、最大值补负无穷、最小值补正无穷。反例：有效值全为负数时，最大值归约补零会让无效位置"获胜"。
3. **尾块点积的账**。长度 100、块宽 64：第二块只有 36 个真实元素，剩下 28 个逻辑位置仍参与乘法和求和。两路输入都补零，无效乘积才是零；若两路都补一，结果凭空多出 28。输入全为一时，两块的正确部分和是 64 和 36，而不是 64 和 64。本页输出的是逐块部分和，跨块求和是另一次独立计算。
4. **调试方法论**：先用互不相同的行值、列值复现；再分别只改输入步长或只改输出步长；给输出底层存储的间隙填上哨兵值（测试用 -999），事后检查间隙是否原样——间隙被动过说明"写错了位置"，数值错但间隙完好说明"读错了位置"。尾块问题用非整除长度和可手算的值，逐块比较部分和，避免跨块总和恰好掩盖错误。
5. **偶发不一致**（相同输入不同输出）时查竞态：多个 program 写同一位置就需要原子加法（一次加法更新不可分割）或先写部分和再分阶段归约。注意：原子加法救不了错误地址，多个浮点贡献的到达次序仍可能让舍入结果有微小差别。工具箱：`TRITON_INTERPRET=1`（在 CPU 上逐个 program 解释执行，看索引和中间值）、`tl.device_print`（设备端打印少量中间值）、Compute Sanitizer（查非法访存和竞态）。

## 关键概念速查表
| 术语 | 大白话解释 |
|---|---|
| stride（步长）| 沿某维移动一个位置要跨过的存储元素数 |
| mask（掩码）| 标记哪些逻辑位置真实有效，越界位置不读不写 |
| other / 填充值 | 掩码排除位置在计算块里占位所用的值 |
| 归约（reduction）| 把多个数合成一个结果，如求和、最大值 |
| 尾块（tail block）| 长度不被块宽整除时，最后那个没装满的块 |
| program | 一个工人线程块，各管一块数据 |
| 视图（view）| 共享底层存储的张量窗口，切片/转置会产生间隙 |
| 原子加法 | 不可分割的"读-加-写"，防止并发更新互相覆盖 |
| TRITON_INTERPRET | 让 kernel 在 CPU 上逐 program 解释执行的环境变量 |

## 小白常见疑问
- **Q：行步长直接写列数不行吗？** 只对连续行主序布局成立。列切片（列步长变成 2）或转置（快慢维互换）输入会让这种写法悄悄读错地址——只测连续布局发现不了。
- **Q：为什么测试要比较整个底层存储，而不只比较输出视图？** 视图数值对了，间隙也可能被误写；比较整块 backing 存储才能同时确认"该写的写对了"和"不该写的没动"。
- **Q：为什么逐块比较部分和，而不是直接比总和？** 不同块的错误可能在总和中相互抵消；逐块对照 FP64 参考能把"哪一块错了"直接暴露出来。
