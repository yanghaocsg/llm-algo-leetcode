# 22. Triton 两阶段归约 — 小白讲解

> 对应 notebook：[`22_Triton_Two_Stage_Reduction.ipynb`](./22_Triton_Two_Stage_Reduction.ipynb)

## 一句话总结

这个 notebook 教你把一条长向量的求和拆成两个 kernel：先让每个 Program 各算一段的部分和、写进自己的槽位，再用第二个 kernel 把这些部分和合并成总和。

## 为什么需要它：痛点是什么

归约（reduction，把多个数合并成较少结果）一个向量到**一个**数时，如果开多个 Program 分工，就遇到一个经典难题：谁来写最后那个数？最直觉的"每个 Program 都直接往同一地址写自己的段和"会导致结果只剩其中一段——后写的覆盖先写的。这就像三个小组分别统计各楼层的人数，却把结果写在同一张纸的同一个格子里：最后纸上只剩最后交的那组数字。

用 PyTorch 的 `.sum()` 时你从不用想这些；但手写 Triton 归约时，跨 Program 合并是绕不开的问题。两条常见出路：原子累加（加法可以，但浮点顺序不可控、要管初始化）或本节的两阶段方案——每个 Program 先写**独占**的部分和槽位，再由第二个 kernel 统一合并。

## 核心问题

- 怎样把 $N$ 个元素的分段和合成为总和，且每个结果只被一个 Program 写？
- 两个阶段的尾部（输入尾块、部分和尾块）分别怎么屏蔽？
- 第二个 kernel 怎么知道第一个 kernel 已经写完？

## 解决思路：一步步看懂

1. **拆分计划。** $N$ 个元素、每 Program 最多 $B$ 个，共 $P=\lceil N/B\rceil$ 个 Program。编号 $g$ 的 Program 负责从 $gB$ 开始的一段：

   $$p_g=\sum_{i=gB}^{\min((g+1)B,\,N)-1}x_i,\qquad s=\sum_{g=0}^{P-1}p_g$$

   例：$x=[1,2,\ldots,10]$、$B=4$，三个 Program 分别得 10、26、19，合并得 55。

2. **第一阶段：分段求和，独占写入。** 参考实现核心：

   ```python
   values = tl.load(X + offsets * STRIDE_X, mask=offsets < N, other=0.0)
   # 逻辑位置乘真实步长寻址（输入可能是切片）；尾部补 0，零是加法的单位元
   partial = tl.sum(values, axis=0)      # 本段的部分和
   # 写到 PARTIAL + program：每个 Program 有自己的槽位，互不覆盖
   ```

   注意这里的掩码检查的是"逻辑位置 < N"——输入长度。

3. **第二阶段：合并真实部分和。** 计算宽度补到二次幂，但有效条件是"槽位编号 < P"：

   ```python
   slots = tl.arange(0, MERGE_BLOCK)
   values = tl.load(PARTIAL + slots, mask=slots < PARTS, other=0.0)
   total = tl.sum(values, axis=0)   # P=3 时第 4 个候选位补 0，缓冲本身仍只有 3 个槽
   ```

   两个阶段的尾部是两码事：第一阶段看输入长度，第二阶段看部分和数量。部分和缓冲占 $4P$ 字节，两阶段合计逻辑流量约 $8P$ 字节。

4. **顺序由 CUDA 流保证。** 同一 CUDA 流（组织设备操作的执行队列）里先提交第一阶段、再提交第二阶段，设备会按流内依赖先完成部分和写入再读取，Python 端不用在中间等待整个设备。这就像流水线传纸条：你把两张工单按顺序塞进同一个信箱，后面的人自然先拿到第一张。

5. **数值检查的讲究。** 改变分组会改变浮点加法的结合顺序，所以用 FP64 参考和预定容差核对；整数样例则能精确暴露漏段或重复段。每次调用完整覆盖各个槽位，天然可重复调用。

## 关键概念速查表

| 术语 | 大白话解释 |
|---|---|
| 归约（reduction） | 把多个值按某运算合并成较少结果，本节是求和 |
| 部分和（partial sum） | 每个 Program 对自己那段算出的中间和 |
| 独占槽位 | PARTIAL 缓冲里只属于一个 Program 的写入位置 |
| 单位元 | 补齐值选 0，因为 0 加任何数不变 |
| CUDA 流 | 组织设备操作顺序的队列，流内先提交先执行 |
| `tl.cdiv` | 向上取整除法，用来算 Program 数 |
| `next_power_of_2` | 把块宽补到二次幂（Triton 块宽的要求） |
| 哨兵（sentinel） | 缓冲两端预埋的值，检查写入有没有越界 |

## 小白常见疑问

- **Q：为什么不能所有 Program 直接原子累加到一个数？** 原子加可行但是另一套方案：要管输出初始化，浮点累加顺序不可控。两阶段用独占写入把"各算各的"和"最后合并"分开，逻辑更清楚。
- **Q：第二个 kernel 怎么等第一个写完？** 不需要手动等。两次启动放在同一当前流里，流内依赖保证第一阶段全部完成后才开始第二阶段。
- **Q：第二阶段只合并 3 个数，也要补到 4 吗？** 块内归约宽度必须是二次幂，第四项补 0 参与；但缓冲本身仍只要 3 个 FP32 槽位，别把计算宽度当缓冲长度。
- **Q：拆成两阶段多了一次提交和临时缓冲，值得吗？** 取决于输入规模与配置，本节明确说要"确定输入规模与配置后再测量"，没有一刀切的答案。

## 动手验证：怎么知道自己做对了

测试分层核对：逐项比较每个部分和与 `expected_partials`；在缓冲两端放哨兵，确认写入没有越界；`triton_two_stage_sum` 的总和与 FP64 参考按预定容差对照，整数样例精确核对覆盖。用例覆盖块宽前后边界、三个以上输入段、非连续切片、正负抵消、全零与最大长度 $2^{20}$。最有意思的是 `KernelLaunchRecorder`：它记录两次真实启动的名称、网格、流与缓冲地址，验证第一阶段输出正是第二阶段输入、两次启动都在调用方当前流，防止你绕开目标内核用别的实现"作弊"；还有非默认流用例，在该流上生成输入并连续执行两阶段。
