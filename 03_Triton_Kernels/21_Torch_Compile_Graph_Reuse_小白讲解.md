# 21. torch.compile 图捕获与编译版本复用 — 小白讲解

> 对应 notebook：[`21_Torch_Compile_Graph_Reuse.ipynb`](./21_Torch_Compile_Graph_Reuse.ipynb)

## 一句话总结
用一个自己写的"记录后端"观察 torch.compile 的真实行为：同一个"加偏置再 ReLU"的函数连调八次，看什么时候新增图版本、什么时候复用、什么时候图被切段——全程 CPU 可做，不需要 GPU。

## 为什么需要它：痛点是什么
很多人对 torch.compile 的理解是玄学："第一次慢后面快"、"改了输入会不会重编译"。这些疑问靠背结论回答不了，因为答案取决于输入的形状、步长、类型等条件。这节的做法是把黑盒打开：自定义后端（backend，编译器把捕获的图交给它、它返回一个可执行体）在这里是一个"记录员"——把每次收到的 FX 图存档计数，让"捕获了几张图、每张跑了几次"变成可以直接断言的事实。类比：给快递中转站装一块计数牌，每收到一个新包裹（新图版本）就 +1，包裹重复投递（复用）不计数——八次调用下来，哪种输入算"新包裹"一目了然。

## 核心问题
- 只改数值、改形状、改步长、改 dtype，分别会不会产生新的编译版本？
- "新增了一个图版本"、"执行了已有图"、"图被分段（graph break）"三件事怎么区分？
- fullgraph=True 的"整图要求"和允许分段有什么行为差别？

## 解决思路：一步步看懂
1. **图是怎么来的**。`affine_relu(x, bias) = relu(x + bias)` 用 torch.compile 包装后，TorchDynamo 分析函数，提取成 FX 图（PyTorch 表示计算图的工具，节点记录输入、操作与输出；GraphModule 把图和可执行入口放在一起）。记录后端保存计算节点的 target（本页就是 add 和 relu 两个节点），返回这张图自己的 forward 去执行——后端契约要求执行收到的图，而不是绕回原函数。
2. **八次调用的实验设计**（`make_input_sequence`）：首次 2×3 → 同形状新数值 → 4×3 → 重复 4×3 → 回到 2×3 → 新步长（3×2 转置出的非连续视图）→ 新 dtype（float64）→ 重复该 dtype。每次用"调用前后计数差"算本次新增图数。
3. **结果与解读**：新增图数为 [1, 0, 1, 0, 0, 1, 1, 0]。数值变化复用；形状、步长、类型各新增一个版本；回到旧条件命中旧版本——`dynamic=False` 固定形状参与特化，但不等于每次都重编译。guard（编译版本适用条件检查）查的是"这份实现还适用吗"（形状/步长/dtype），不是张量里的数值。还要同时检查图调用体的执行次数，排除"函数根本没运行"。
4. **图中断**。在加法和 ReLU 之间插入一个 `@torch.compiler.disable` 声明的恒等调用（数值原样返回，但把捕获切开）：允许分段时，加法图、这个 Python 调用、ReLU 图依次执行，得到两张各含 1 个计算节点的图，重复输入复用两段但两段各执行一次；`fullgraph=True` 要求整图捕获，遇到这个主动边界会抛出 Unsupported 异常——它要求的是图完整，不承诺只生成一个设备内核。
5. **工程意义**：回调数是"后端收到几张 FX 图"，不能当作 GPU 内核数或性能指标；想看设备上的融合与耗时，要接着用 18 节的产物与 CUDA 事件手段。测试结束 `torch.compiler.reset()` 清理全局 Dynamo 缓存，不污染后续实验。

## 关键概念速查表
| 术语 | 大白话解释 |
|---|---|
| TorchDynamo | torch.compile 的前端，追踪 Python 函数捕获计算图 |
| FX / GraphModule | PyTorch 的计算图表示；GraphModule = 图 + 可执行入口 |
| backend（后端）| 接收捕获的 FX 图并返回可调用体的组件 |
| guard（适用条件）| 复用某版本前检查输入形状/步长/dtype 是否匹配 |
| dynamic=False | 固定具体形状参与特化的编译策略 |
| stride（步长）| 沿某维移一个元素跨过的存储数；形状相同布局可不同 |
| graph break（图中断）| 函数某处无法继续被同一张图捕获，切成多段 |
| fullgraph=True | 要求本次调用完整捕获成一张图，否则报错 |

## 小白常见疑问
- **Q：dynamic=False 是"每次调用都重编译"吗？** 不是。它让具体形状参与特化；回到先前出现过的输入条件时仍然命中旧版本（实验里"回到 2×3"新增为 0）。
- **Q：形状都没变，为什么换了步长就要新图？** 编译版本的条件包含布局：2×3、步长 [3,1] 和 [1,2] 描述的是不同存储排列，生成的代码访问方式不同。
- **Q：为什么不能直接用累计回调数判断本次行为？** 累计数说明不了"这一次"有没有新增；必须用本次调用前后的计数差，再配合图执行次数才能区分新增、复用和没执行。

## 动手验证：怎么知道自己做对了
`test_graph_capture_and_reuse` 先做后端契约测试：直接塞进一张 `(x - bias).sin()` 的 FX 图，后端必须按这张图计算（抓"无论收到什么都调 affine_relu"的作弊实现）。随后断言八次序列的新增图 [1,0,1,0,0,1,1,0]、累计 [1,1,2,2,2,3,4,4]、每次图调用体恰好执行一次、共四组静态特化且每张图含 add 和 relu 两个节点、输入未被修改；边界实验断言分段报告 `{first_graphs: 2, repeat_new_graphs: 0, repeat_graph_executions: 2, fullgraph_rejection: "Unsupported", whole_backend_callbacks: 0}`；最后清空缓存重放全序列，确认结果不依赖上次测试残留的缓存。
