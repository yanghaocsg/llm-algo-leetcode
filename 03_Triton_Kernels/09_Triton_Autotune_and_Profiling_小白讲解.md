# 09. Triton 自动调优与基准测量 — 小白讲解

> 对应 notebook：[`09_Triton_Autotune_and_Profiling.ipynb`](./09_Triton_Autotune_and_Profiling.ipynb)
> NPU 版：[`09_Triton_Autotune_and_Profiling_NPU.ipynb`](./09_Triton_Autotune_and_Profiling_NPU.ipynb)

## 一句话总结

这个 notebook 用最简单的向量加法教你三件容易混淆的事：挑合法配置、让自动调优替你选配置、以及怎样把准备成本和真实耗时分开测量。

## 为什么需要它：痛点是什么

同一段向量加法 `x + y`，BLOCK_SIZE 取 512 还是 2048，运行时间可能就是不一样。手动挑配置像买鞋靠猜：你得一双双试。更坑的是测量——第一次调用 Triton kernel 包含编译和候选搜索，耗时好几秒；拿这个"第一次"去跟早已预热的 PyTorch 比，就像拿你刚睡醒的百米成绩跟运动员比，输赢都说明不了任何问题。

朴素做法的两个典型错误：一是把编译/搜索时间混进稳态耗时，二是因为自动调优"帮你选了"，就以为选出来的配置一定正确。本节逐一拆解。

## 核心问题

- 候选配置集合怎么给？为什么是有限集合而不是穷举？
- 输入长度怎么影响网格和调优选择？
- 首次调用的编译、搜索成本怎样与稳态耗时分开？

## 解决思路：一步步看懂

1. **候选是有限的。** 自动调优（autotune）只在你给的集合里试跑比较，不替代算法设计。参考实现给三个候选：

   ```python
   configs = [
       triton.Config({'BLOCK_SIZE': 512},  num_warps=2),
       triton.Config({'BLOCK_SIZE': 1024}, num_warps=4),
       triton.Config({'BLOCK_SIZE': 2048}, num_warps=8),
   ]
   ```

   BLOCK_SIZE 是每个 Program 处理的元素数，num_warps 是 warp（32 线程执行组）数量，两者分别计量。

2. **长度改变一切。** 10000 个元素时，三档块宽分别需要 20、10、5 个 Program，尾块有效元素 272、784、1808——逻辑位置都是 10240 个，多出的 240 项靠掩码排除。块宽在编译期已知，不同块宽对应不同的代码版本（特化，specialization）。调优键 `key=['n_elements']` 按长度分别选配置：编译缓存和调优选择缓存是两个东西——新长度可能已有编译好的代码，却还没有对应的调优结果。

3. **动态网格。** 被选中的配置不同，Program 数就不同，所以网格必须从当前配置取：

   ```python
   grid = lambda meta: (triton.cdiv(n_elements, meta['BLOCK_SIZE']),)
   # meta 里的块宽才是当前候选的，不能写死成某一档
   ```

   调优对象通过 `@lru_cache(maxsize=1)` 的工厂函数延迟创建——定义题目时不会触发搜索。

4. **把四段成本分开。** 编译（生成候选代码，可被缓存省去）→ 搜索（多次试跑选配置，不能算进稳态耗时）→ 预热（进入可重复状态）→ 稳态测量（同输入、同类型、同设备重复执行）。自动调优会重复运行 kernel，所以覆盖式写出没问题，而原地累加类 kernel 需要重置状态。

5. **读数要克制。** 接近 1 的速度比要结合重复样本判断；计时只给耗时，不提供缓存命中率或显存流量，不能一慢就归因于"带宽瓶颈"。

## 关键概念速查表

| 术语 | 大白话解释 |
|---|---|
| autotune | 让候选配置各自试跑、自动选最快者的机制 |
| `triton.Config` | 一份候选配置：块宽、warp 数等参数组合 |
| 调优键（key） | 区分"哪种输入条件用哪份配置"的依据，本节是长度 |
| 特化（specialization） | 块宽等编译期常量不同，生成不同版本的代码 |
| 编译缓存 / 调优缓存 | 分别存"可用代码"和"选中的配置"，复用条件不同 |
| `meta['BLOCK_SIZE']` | 启动时当前候选的块宽，动态网格从它取数 |
| `triton.cdiv` | 向上取整除法，算需要几个 Program |
| `do_bench` | Triton 自带的预热+重复执行计时工具 |

## 小白常见疑问

- **Q：为什么不穷举所有块宽和 warp 数？** 候选越多编译和搜索越贵；有限集合覆盖典型档位就够了，配置选择不是算法正确性的保证。
- **Q：第一次调用很慢，是 kernel 慢吗？** 大概率不是。首次调用含编译和候选搜索；比稳态性能要先让准备阶段完成、再重复测量。
- **Q：自动调优选出的配置会不会算错？** 会有这种风险场景，所以本节测试直接逐个候选运行核对数值，而不是只信被选中的那个。
- **Q：网格写死 `(n_elements // 1024,)` 行不行？** 不行。块宽 2048 的候选会漏掉一段元素；必须用 `cdiv` 向上取整并从 `meta` 取当前块宽。

## 动手验证：怎么知道自己做对了

`test_add_candidates` 逐个候选直接启动，在每个块宽的前后边界（1、block−1、block、block+1、10000）与 `x + y` 对照，并检查输入未被修改；`test_autotune_correctness` 对 1 到 10000 的 12 种长度走自动选择路径核对结果，另验证 7 组非法输入（CPU 张量、长度不匹配、FP16、二维视图、步长切片、空张量）被拒绝。性能测量做五轮正逆序交替，报告两条路径耗时中位数与逐轮速度比中位数；计时包含输出分配，不含输入搬运、首次编译和搜索，也不要求必须快于 PyTorch。

## 与 NPU 版的区别

NPU 版的 kernel、候选、TODO 完全相同；差异是设备相关代码：设备检查换成 `x.is_npu`、`torch.npu.is_available()`，张量与测试输入建在 `device="npu"`，启动上下文用 `torch.npu.device`，基准记录里设备名从 `torch.npu.get_device_name` 读取；仍用 `triton.testing.do_bench` 计时。
