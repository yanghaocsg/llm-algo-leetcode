# 14. Triton W8A16 融合反量化矩阵乘法 — 小白讲解

> 对应 notebook：[`14_Triton_Quantization.ipynb`](./14_Triton_Quantization.ipynb)

## 一句话总结

这个 notebook 教你把"INT8 权重恢复成浮点数"这一步揉进矩阵乘法的 kernel 里：每次只反量化当前输出块需要的那一小片权重，用完就扔，不产生完整的中间权重矩阵。

## 为什么需要它：痛点是什么

大模型推理的最大瓶颈之一是显存：模型权重动辄几十 GB，而权重里绝大部分数值其实用不了 FP16 的精度。W8A16（8 比特权重、16 比特激活）就是把这幅"权重地图"压缩存放：每列一个正的缩放因子 $s_n$，存整数 $Q_{k,n}$，用的时候重建 $\widehat W_{k,n}=Q_{k,n}\cdot s_n$（零点固定为 0，所以叫对称量化）。INT8 元素只有 1 字节，FP16 是 2 字节，权重体积直接减半。

但朴素 PyTorch 的用法是"先解压、再使用"：

```python
w = dequantized_weight(weights, scales)   # 先恢复出完整的 FP16 大矩阵
y = x @ w                                  # 再做普通矩阵乘
```

问题就在第一行：它凭空写出一份和原模型一样大的 FP16 中间张量——搬进显存、写出来、再被 GEMM 读进去，带宽开销几乎抵消了压缩省下的读取量。类比：宜家家具运来时是平板压缩包装（INT8），你却坚持先把所有零件在客厅全组装成半成品（FP16 大矩阵）摆一地，再开始搭房子；聪明的做法是搭到哪一堵墙，现场拆哪一箱。

## 核心问题

1. 融合反量化省掉了什么、又没省掉什么？（融合 ≠ 整数矩阵乘）
2. 每列一个尺度 $s_n$，这个尺度该跟随哪个轴？跨 K 轮次变不变？
3. 怎样证明 kernel 算的和"先重建整张 FP16 权重再 GEMM"完全一致？

## 解决思路：一步步看懂

**第 1 步：分清"存得省"和"算得对"。** 输入 $X\in\mathbb R^{M\times K}$ 是 FP16，整数权重 $Q\in\mathbb Z^{K\times N}$，尺度 $s\in\mathbb R^N$（每**输出列**一个）。目标：

$$Y_{m,n}=\sum_{k=0}^{K-1}X_{m,k}\cdot Q_{k,n}s_n$$

注意：融合的只是"反量化 + 矩阵乘"这两步，乘法本身仍是 FP16 输入、FP32 累加——不是把整个 GEMM 改成整数运算（那是 W8A8/INT8 kernel 的事）。

**第 2 步：一个 program 消费一片权重。** 每个 program 负责输出的一块 16 行 × 64 列（`BLOCK_M=16, BLOCK_N=64, BLOCK_K=64`），沿 K 维逐段读取 X 和 Q。关键寻址认识：**尺度只由输出列决定**，同一输出块的 64 列在所有 K 轮次里始终用同一段尺度 $s_{64:128}$ 这类切片，绝不能用归约位置 k 去索引长度为 N 的尺度向量——轴用错了，非均匀尺度的测试立刻露馅。

```python
# TODO 1：列尺度在所有K轮次中保持不变。
w_fp16 = (w_int8.to(tl.float32) * scales[None, :]).to(tl.float16)  # 按列广播，先FP32乘再舍入
# TODO 2：保留前面K子块的贡献。
acc += tl.dot(x, w_fp16)   # 累加，不是覆盖
```

**第 3 步：三条尾巴各管各的。** M 尾部只影响有效输入行；N 尾部影响权重列、尺度加载与输出写回；K 尾部则要求 X 和 Q **两路同时补零**（补零项乘出来是 0，不贡献乘积）。特别要盯住累加器：K=70、块宽 64 时第二轮只有 6 个有效位置，如果每轮把 `acc` 重置了，前 64 列的贡献就全丢了——"累加，别覆盖"。

**第 4 步：验证时把两种误差分开。** 本题固定给定的 Q 和 s，参照路径是"用同样顺序重建 FP16 权重（先 FP32 算 $Qs$ 再转 FP16）再做 GEMM"，两条路径的舍入顺序一致，才能逐位对上。而 $XW$ 与 $X\widehat W$ 的差异是**权重量化本身**的误差，本 notebook 不评估它——它验证的是 kernel 实现的正确性，不是压缩前后模型质量的好坏。

## 关键概念速查表

| 术语 | 大白话解释 |
|---|---|
| W8A16 | 权重存 INT8、激活是 FP16 的量化方案 |
| 对称量化 | 零点固定为 0，只用一个正尺度即可重建权重 |
| 尺度（scale） | 每输出列一个的浮点系数，整数乘它变回浮点 |
| 反量化（dequantize） | 整数 × 尺度恢复浮点权重的过程 |
| 融合（fusion） | 把反量化揉进 GEMM kernel，按块恢复、即恢复即使用 |
| 列尺度广播 | `scales[None, :]` 让一行的每个 k 用同一列尺度 |
| K 维累加 | 输出块沿归约轴分段循环，累加器必须跨轮保留 |
| 尾块（tail） | 矩阵三轴上不足整块的部分，靠掩码补零处理 |
| 步长视图（strided view） | 切片/转置产生的非连续张量，寻址要乘真实步长 |

## 小白常见疑问

**Q1：权重从 FP16 变 INT8，字节数减半，速度一定翻倍吗？**
不一定。除了 INT8 元素，还要额外存尺度、执行反量化乘法；收益取决于矩阵形状、读取量和计算量的权衡。notebook 的基准分三条路径测：预先重建后 GEMM、每次重建整张再 GEMM、融合接口——不预设结论。

**Q2：为什么尺度乘法要先转 FP32 再舍入到 FP16？**
为了让融合路径与"先重建整张 FP16 权重"的参照路径有**相同的舍入顺序**。若舍入顺序不同，即使逻辑正确，逐元素对比也会出数值差，分不清是实现 bug 还是精度差异。

**Q3：累加器为什么用 FP32？**
K 维要做几十上百次加法，FP16 累加误差会滚雪球。FP32 累加只能减小**实现**误差，恢复不了权重压缩时已经丢掉的精度——两种误差要分开谈。

**Q4：每列一个尺度是不是唯一的量化粒度？**
不是。还有沿 K 分组的多尺度（每组一个尺度）等方案，它们各有自己的索引与恢复规则；本节实现的是每列一尺度这一种。
