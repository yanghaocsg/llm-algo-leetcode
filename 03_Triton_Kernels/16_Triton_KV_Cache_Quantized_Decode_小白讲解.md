# 16. Triton KV Cache 量化解码 — 小白讲解

> 对应 notebook：[`16_Triton_KV_Cache_Quantized_Decode.ipynb`](./16_Triton_KV_Cache_Quantized_Decode.ipynb)

## 一句话总结
把解码时的 KV Cache 从 FP32 压成 INT8（每条向量配一个 FP32 尺度），并用一个 Triton kernel 完成"读编码 → 乘尺度恢复 → 算注意力"的全流程，顺便算清楚：缓存到底省了多少、输出到底错了多少。

## 为什么需要它：痛点是什么
长上下文推理时，KV Cache（缓存的历史 Key/Value 向量）显存占用暴涨，FP32 下每个元素要 4 字节。朴素 PyTorch 做法：要么不量化，显存先撑爆；要么先反量化整个缓存再算注意力——这会多一次全量读写，而解码恰恰是被访存卡住的任务。
量化也不是"把 4 字节换 1 字节"那么简单：每条向量还要额外存一个尺度，读回时只能近似恢复。就像搬家时把每箱东西拍照登记（INT8 编码）并记一个"放大倍数"（scale，尺度），箱子确实小了，但取用时必须乘回倍数，而且还原出来的东西和原物有一点点差别（表示误差）——这个差别会顺着注意力公式传到最终输出。

## 核心问题
- 一条向量怎么存成"INT8 编码 + FP32 尺度"？为什么 0.5 必须舍入成 1、-0.5 舍成 -1？
- 解码注意力里，K 的尺度和 V 的尺度分别在哪一步乘回去？搞混会怎样？
- "1 字节 vs 4 字节 = 省 4 倍"这个直觉错在哪？

## 解决思路：一步步看懂
1. **逐向量量化**。对每个请求、每个头、每个位置的一条 K（或 V）向量，沿特征维求绝对值最大值，得到尺度和编码：$s=\max(\max_d|x_d|/127,\ 10^{-8})$，$z=\mathrm{clip}(\mathrm{round}_{away}(x/s),-127,127)$。文字说：尺度 = 这条向量最大绝对值除以 127（下限 1e-8 防零向量除零），编码是"除完再四舍五入"的整数，不用 -128。舍入必须是"半值远离零"（0.5→1、-0.5→-1），和默认 round 的"半值取偶"不一样。K 与 V 各自独立量化，每条向量各存一个尺度。
2. **解码先恢复 K**。INT8 编码先乘各自的 K 尺度恢复成 FP32，再与查询点积形成分数：
```python
k = kq * sk[:, None]                      # 编码乘"每个位置自己"的K尺度
scores = tl.sum(k * q[None, :], axis=1) * SCALE   # 点积后乘 1/sqrt(D)
scores = tl.where(positions < valid_length, scores, -float('inf'))  # 补齐位置不许进分母
```
无效位置的分数必须设负无穷，否则补齐处 0 点积的 exp(0)=1 会混进 softmax 分母。
3. **再恢复 V**。V 用自己的 V 尺度（与 K 尺度无关），乘完再按注意力权重沿位置求和。K 的误差改变的是"权重分布"，V 的误差改变的是"被加权的数据"——两者不可交换：同一位置 K 尺度 0.1、V 尺度 0.01，读 V 时误用 K 尺度会把该位置重建值放大十倍。
4. **算清字节账**。设缓存向量条数 R=B·H·T，原始 FP32 K/V 共占 8RD 字节，量化后编码+尺度占 2R(D+4) 字节。D=16 时比值 0.3125；D=1 时却是 1.25——每条向量那 4 字节尺度的开销，在特征维很短时反而让缓存变大。"省 4 倍"只在 D 足够大时近似成立。
5. **知道本页的边界**。包装函数每次重新量化全部 T 个预留位置（容量 128、有效长度 64 也编码 128 个位置），这是"编码+解码"的演示；持久缓存只转换新位置的追加式更新留给后续扩展。

## 关键概念速查表
| 术语 | 大白话解释 |
|---|---|
| KV Cache | 解码时缓存的历史 Key/Value，避免每步重算全部上下文 |
| 逐向量量化 | 每个 token、每个头的 K 或 V 向量单独配一个尺度 |
| scale（尺度）| FP32 存的"放大倍数"，读回时乘它恢复幅值 |
| round away from zero | 半值远离零舍入：0.5→1、-0.5→-1，本页的硬性规定 |
| softmax 分母 | 全部权重之和；无效位置分数设 -inf 才会被排除 |
| mask（掩码）| `positions < valid_length` 之外的位置不读、不写、不进分母 |
| 有效长度 L | 每个请求实际拥有的 token 数 |
| BLOCK_T / BLOCK_D | 位置维和特征维一次处理的块宽度 |

## 小白常见疑问
- **Q：为什么不直接用 `round()`？** 默认 round 对半值取偶（0.5→0、1.5→2），本页定义的是远离零；测试用 `atol=0, rtol=0` 的逐项对照，规则差一点都会被抓。
- **Q：测试为什么对照"重建缓存"而不是原始 FP32 缓存？** 量化天然有表示误差。实现的正确性 = 和"用同样编码规则重建出来的 K/V"算出的注意力一致；和原始缓存的差距只用来观察量化误差有多大。若连重建缓存都没算对，那是索引、尺度或归约的 bug，不能甩锅给量化。
- **Q：误差到底有多大？** 最近整数舍入使单个分量的重建误差约不超过半个尺度（测试断言 `error <= scale * 0.5001 + |x|*1e-6`），再叠加浮点舍入。
