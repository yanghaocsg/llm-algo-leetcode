# 12. Triton 变长序列 GQA 解码 — 小白讲解

> 对应 notebook：[`12_Triton_Variable_Length_GQA.ipynb`](./12_Triton_Variable_Length_GQA.ipynb)

## 一句话总结

这个 notebook 教你在"一批请求长度各不相同、多个查询头共用一份键值头"的解码场景下，怎样让每个查询头读对 K/V、又让补齐位置不稀释真实上下文的权重。

## 为什么需要它：痛点是什么

先说两个真实推理服务的痛点。

**变长**：同一批请求里，有的只积累了 3 个历史 token，有的已有 7 个。但张量必须形状整齐，所以缓存统一预留最大长度 $T_{max}$，每个请求另配一个真实长度 $L_b$。朴素 PyTorch 做 batch 注意力时要么按最长补齐再算（短请求的补齐位置会以 $e^0=1$ 的权重混进 Softmax 分母，把结果拉偏），要么放弃批量、逐请求 for 循环（GPU 利用率极低）。

**GQA（Grouped-Query Attention，分组查询注意力）**：解码时每个请求只有 1 个新查询，却有几十个头。如果每个查询头都存一份 K/V，缓存太浪费。GQA 让连续 $G$ 个查询头共用一个键值头：比如 $H_q=4,H_{kv}=2$ 时头 0、1 共用 KV 头 0，头 2、3 共用 KV 头 1。MHA（标准多头注意力）是 $G=1$ 的特例，MQA（多查询注意力）是 $H_{kv}=1$ 的极端。共享省的是**存储**的 K/V 头数，**输出**仍每个查询头一份。

生活类比：一排储物柜（$T_{max}$ 个格子）人人同宽，但有人只用了前 3 格；柜子该多大是物业统一规定的，你实际放多少东西由 $L_b$ 决定，收拾时只该动自己真正放了的格子。

## 核心问题

1. 查询头 $h$ 怎样映射到它共享的键值头 $g$？映射错了会发生什么？
2. 同一缓存容量下，不同请求的有效长度怎样限制 Softmax 的归一化范围？
3. 补齐位置为什么必须把分数设为 $-\infty$ 而不是依赖 K 补零？

## 解决思路：一步步看懂

**第 1 步：头映射用整除。** Q 形状 $(B,H_q,D)$，K/V 形状 $(B,H_{kv},T_{max},D)$，要求 $G=H_q/H_{kv}$ 为正整数。零起始的查询头 $h$ 对应键值头 $g=\lfloor h/G\rfloor$：

```python
# TODO 1：同组查询头读取同一键值头。
kv_head = q_head // GROUP_SIZE   # 连续 G 个查询头共用一个 KV 头
```

例：$H_q=4,H_{kv}=2$ 时查询头 0、1 都读 KV 头 0。如果手滑写成取余 `q_head % GROUP_SIZE`，查询头 1 会被错配到 KV 头 1；只有 1 个 KV 头时两种写法结果恰好相同，测试都测不出错——这是隐蔽 bug 的经典藏身处。

**第 2 步：一个 program 包揽一个请求的一个头。** 把 B 个请求的查询头依次展平，program 编号 $p$ 对应 $b=\lfloor p/H_q\rfloor$、$h=p\bmod H_q$（grid 就是 `(batch * q_heads,)`）。它先读出该请求的 `valid_length`，再对 $0\le t<L_b$ 的位置计算

$$w_t=\frac{e^{s_t-m}}{\sum_{u=0}^{L_b-1}e^{s_u-m}},\qquad O_{b,h,d}=\sum_{t=0}^{L_b-1}w_tV_{b,g,t,d}$$

文字解释：分母只累加**这个请求**的前 $L_b$ 个位置；$m$ 是这行有效分数的最大值，先减它再求指数防止溢出。因为解码时上下文一次装得下（本练习 $T_{max}\le128$，`BLOCK_T` 补到 2 的幂），不需要第 11 篇那种跨块在线状态，一次归约即可。

**第 3 步：先屏蔽，再归约。** 顺序很关键：

```python
scores = tl.where(positions < valid_length, scores, -float('inf'))  # 无效位置先踢出局
weights = tl.exp(scores - tl.max(scores, axis=0))                   # 再减最大值求指数
```

若先把补齐 K 填零就算分母：零点积得 0 分，$e^0=1$ 照样加分母。哪怕所有**有效**分数都是大负数，也不能让补齐的"零分数"浑水摸鱼。全负分数测试专门卡这一点。

**第 4 步：只沿位置轴归约 V。** `output = tl.sum(weights[:, None] * v, axis=0)`——位置轴被加掉，特征轴保留，得到 D 维向量，每个查询头独立写回。K/V 的寻址要同时包含"请求编号 × 预留容量"和"KV 头编号"：program 5（请求 1、查询头 1）必须落在请求 1 的缓存区域，不能只按头编号定位。

## 关键概念速查表

| 术语 | 大白话解释 |
|---|---|
| GQA | 多个查询头分组共用一个键值头，介于 MHA 和 MQA 之间的省钱方案 |
| MHA / MQA | 每头一份 KV（G=1）／全部头共用一份 KV（H_kv=1） |
| GROUP_SIZE | 一组里查询头的个数 G = H_q / H_kv |
| 变长序列（variable length） | 同批请求真实上下文长度不同，靠每请求的 L 控制 |
| T_max / valid_length | 缓存预留的最大长度／该请求真实有效的位置数 |
| 解码（decode） | 逐 token 生成阶段，每请求每步只有 1 个新查询 |
| 补齐（padding） | 把短序列填到统一长度；填出的位置必须从 Softmax 里剔除 |
| -inf 屏蔽 | 无效位置分数设负无穷，指数为 0，不进分母 |
| 连续化（contiguous） | 把带步长视图拷成内存连续张量，kernel 才能按线性地址访问 |

## 小白常见疑问

**Q1：共享 KV 头之后，同组查询头的输出会一样吗？**
不会。共享的只是被读取的 K/V，各查询头自己的 Q 向量不同，分数和输出也不同。测试里专门有"共享 KV 不应强制同组 Query 输出相同"的检查。

**Q2：为什么不能按批次最大长度统一归一化？**
那样短请求的补齐位置会贡献 $e^0=1$ 的权重，把真实位置的权重稀释掉。每个请求必须用自己的 `valid_length`。

**Q3：这个 kernel 读了共享 KV，是不是省了显存带宽？**
逻辑上共享同一份缓存，但这个教学内核按查询头分别启动，同组的多次加载并不自动合并成一次。省的是**存储空间**，不一定省**读取次数**——两件事要分开算。

**Q4：为什么要 `.contiguous()`？**
输入可能是切片视图（带步长），kernel 按连续线性地址寻址，不连续就必须先显式拷贝，否则读错位置。
