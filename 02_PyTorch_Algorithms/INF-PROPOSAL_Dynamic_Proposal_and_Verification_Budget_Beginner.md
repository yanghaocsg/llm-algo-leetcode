## 一句话说清

投机解码先让一个模型快速猜出几个词元，再让负责输出的模型一次性检查。这本 notebook 教你按最近猜中的情况调整每轮猜多少个，并把省下的时间和多花的成本算清楚。

## 为什么需要它

大模型通常一个词元一个词元地生成，每出一个词元都要调用一次模型。投机解码换了思路：先让草稿器一口气提出几个候选词元，再让目标模型一次检查，通过的直接留下。

麻烦出在“这一轮提几个”上：

- 提少了：目标模型一次检查推进的位置太少，省不下多少次调用。
- 提多了：没被接受的那部分白提了，草稿和验证的成本照付，拒绝之后还要多付修正的成本。

notebook 的 Step 5 记录了作者在一台机器上的一次实验：固定预算把目标模型前向次数的中位数从 192 降到 61，延迟比却是 1.059。调用少了，端到端并没有更快。

所以要回答两个问题：下一轮提几个候选，这一轮省没省时间。这本 notebook 只做 CPU 上能算清的部分：按近期接受率调预算，把草稿、验证和修正的成本分开记账。

## 先认识几个词

| 词 | 人话解释 |
|:---|:---|
| 投机解码（speculative decoding） | 先让草稿器猜几个词元，再让目标模型一次检查的生成方式 |
| 草稿器 / 目标模型 | 草稿器负责提出候选，目标模型负责验证，最后的输出以它为准 |
| 候选预算 `k` | 一轮里最多提出多少个候选词元。它是上限，不等于最后真正提交的数量 |
| 连续接受前缀 | 从头开始逐个比较草稿和目标词元，相同就算接受；第一个不相同的位置叫拒绝位置，它之后的候选全部丢弃 |
| 近期接受率 | 最近几轮“已接受草稿数 ÷ 已提议数”的平均值，用来决定下一轮预算 |
| 贪心验证（greedy verification） | 直接比较候选和目标模型得分最高的词元是否相同。这本 notebook 实现的是这一种，不涉及随机接受 |
| 净收益（net gain） | 接受的草稿省下的时间，减去草稿、验证和修正多花的时间 |

## 核心思路

notebook 的 Step 1 把一轮投机解码拆成四个阶段：提出候选、目标验证、修正或追加、更新状态。Step 4 的三个函数对应其中三个可以算清楚的环节：

- 调预算：输入最近几轮的接受率和当前预算，输出下一轮的预算。平均接受率不低于 `high` 就加 1，不高于 `low` 就减 1，中间不变，结果夹在 `min_k` 和 `max_k` 之间。
- 验证候选：输入草稿词元和目标词元，从左往右逐个比较，输出连续接受的个数和第一个不相同的位置。
- 记时间账：输入接受数、提议数和各项成本，输出节省的时间、额外的成本和净收益。

验证只认“连续”。下面是 notebook 测试里的一组草稿和目标词元：

```text
位置    0     1     2     3
草稿    1     2     3     4
目标    1     2     9     4
结果    接受  接受  拒绝  丢弃
```

从第 2 个位置开始不同，所以只接受前 2 个。第 3 个位置两边都是 4，但它在拒绝位置之后，不能补回来。

时间账本是 notebook Step 3 的公式：

```text
G_A = A * t_b - [K * t_d + t_v + 1(A < K) * t_c]
```

`A` 是被接受的草稿数，`K` 是总提议数，`t_b` 是普通解码生成一个词元的成本，`t_d` 是草稿器提出一个词元的成本，`t_v` 是本轮验证的耗时，`t_c` 是拒绝后修正的耗时。`1(A < K)` 的意思是：发生了拒绝才记 1，否则记 0。下面把预算和账本算一遍，数字取自 notebook 的 Step 3 和测试：

```python
from statistics import mean

def next_k(recent, k, high=0.8, low=0.4):
    rate = mean(recent)                               # 近期接受率的平均值
    return k + (1 if rate >= high else -1 if rate <= low else 0)

print(next_k([1, 1, 1], 4), next_k([0.6], 4), next_k([0, 0, 1], 4))

def ledger(A, K, t_b, t_d, t_v, t_c=0.0):
    saved = A * t_b                                   # 接受的词元按普通解码算，省下的时间
    extra = K * t_d + t_v + (t_c if A < K else 0.0)   # 草稿、验证、修正
    return saved, extra, saved - extra

print(ledger(4, 4, 2.0, 0.2, 1.0))        # 4 个全部接受
print(ledger(2, 4, 2.0, 0.5, 1.0, 0.25))  # 只接受 2 个
print(ledger(0, 4, 2.0, 0.5, 2.0, 1.0))   # 全部拒绝
```

```text
5 4 3
(8.0, 1.8, 6.2)
(4.0, 3.25, 0.75)
(0.0, 5.0, -5.0)
```

第一行是下一轮预算：三组近期接受率的平均值一个不低于 0.8、一个是 0.6、一个约 0.33，预算分别加 1、不变、减 1。后三行是时间账本，都提出了 4 个候选：全部接受时净收益 6.2 ms，只接受 2 个时只剩 0.75 ms，全部拒绝时还要倒贴 5 ms 的草稿和验证成本。提出得更多，不保证接受得更多。

这项估算没有计入修正或追加词元的产出，净收益为负不能直接推出完整生成更慢。

## 容易踩的坑

- **把预算当成提交数**：候选预算 `k` 只是本轮最多提出多少个，最后提交多少由验证决定。
- **跳过拒绝位置继续匹配**：贪心前缀在首个不同词元处结束，后面重新相同也不能补回。
- **阈值边界写成严格大于或严格小于**：平均接受率大于等于 `high` 才加 1，小于等于 `low` 才减 1。
- **每次都扣修正成本**：只有发生拒绝，也就是 `accepted < proposed` 时，才加入修正成本；全部接受时不扣。
- **净收益为负就下结论**：这项估算没有计入修正或追加词元的产出，为负不能说明完整生成更慢。
