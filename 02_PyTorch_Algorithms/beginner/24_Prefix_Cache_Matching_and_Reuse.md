## 一句话说清

很多请求的开头是一样的，比如同一段系统提示词。前缀缓存把这段开头算过的结果留下来，后面的请求直接复用。这本 notebook 教你判断一个请求的开头能复用多少。

## 为什么需要它

一个请求进来，模型要先把整段输入处理一遍，这一步叫预填充，处理完会得到这份输入的 KV Cache。很多请求的开头是一样的：同样的系统提示词、同样的工具说明、多轮对话里相同的历史。每来一个请求都把这段开头重新算一遍，是重复劳动。

前缀缓存的做法是：把这段相同开头对应的 KV Cache 登记下来。后面的请求如果开头一样，就直接复用，只处理从第一个不同词元开始的部分。

但“开头一样”要判断得准确，否则会出错：

- 只算连续的开头。请求 `[0, 1, 2, 3]` 和登记的 `[1, 2, 3]` 中间有三个词元相同，但不是从开头相同，不能算命中。
- 只有登记过的对象才能复用。只登记了 `[1, 2, 3]`，请求 `[1, 2, 0]` 虽然前两个词元相同，在这本 notebook 的模型里也返回零。
- 命中不等于没有计算。命中的请求仍然要处理后缀，完全命中也可能还有工作要做。

这本 notebook 在 CPU 上用整数序列模拟这套逻辑：登记前缀、找最长命中、把请求拆成两段、算一笔复用账。

## 先认识几个词

| 词 | 人话解释 |
|:---|:---|
| 前缀缓存（prefix cache） | 把请求开头那段相同的词元对应的 KV Cache 留下来，供后面的请求复用 |
| 预填充（prefill） | 处理输入词元并形成 KV Cache 的那一步 |
| KV Cache | 预填充时为每个输入词元保存的 K 和 V，后面的计算要读取 |
| 词元（token） | 模型处理文本的基本单位。这本 notebook 用整数编号表示，比如 `[1, 2, 3]` |
| 共享前缀 / 未命中后缀 | 共享前缀是从请求开头连续相同的词元区间；未命中后缀是从第一个不一致词元开始的剩余内容 |
| 登记对象 | 一条完整登记进缓存的前缀。只有请求的开头和某个登记对象完全一致，才算命中 |
| 命中长度 / 复用比例 | 命中长度是从请求开头连续命中的词元数；复用比例是命中词元数除以输入词元数 |

## 核心思路

notebook 里有一个 `PrefixCacheManager` 类，用一张列表 `cached_prefixes` 登记前缀，每一项是一个整数元组，比如 `(1, 2, 3)`。它不保存真实的 K/V，只演示匹配的逻辑。五个 TODO 对应五步：

- 规范输入：把词元序列转成保持顺序的整数列表，不是整数就报错。
- 登记：把非空的前缀转成元组放进列表，重复的不重复登记。
- 匹配：逐个检查登记对象，看请求的开头是不是和它完全一样，在一样的里面选最长的。
- 拆分：按命中长度把请求切成两段。
- 记账：数一下命中多少、未命中多少，算出复用比例。

notebook Step 2 的公式说的是拆分：

```text
prompt = reusable_prefix + suffix
```

`prompt` 是请求的词元序列，`reusable_prefix` 是命中的前缀，`suffix` 是未命中的后缀。这里的加号是拼接，不是数值相加。

下面的例子取自 notebook 的测试，登记了 `(1, 2, 3)` 和 `(1, 2, 9)` 两个前缀：

```python
cached = [(1, 2, 3), (1, 2, 9)]                 # 已经登记的两个完整前缀

def match(prompt):                              # 请求的开头和哪个登记对象一致
    best = 0
    for prefix in cached:
        n = len(prefix)
        if n <= len(prompt) and prompt[:n] == list(prefix):
            best = max(best, n)
    return best

for prompt in ([1, 2, 3, 9], [1, 2, 9, 8], [1, 2, 0], [0, 1, 2, 3]):
    hit = match(prompt)
    print(prompt, hit, prompt[:hit], prompt[hit:], hit / len(prompt))
```

```text
[1, 2, 3, 9] 3 [1, 2, 3] [9] 0.75
[1, 2, 9, 8] 3 [1, 2, 9] [8] 0.75
[1, 2, 0] 0 [] [1, 2, 0] 0.0
[0, 1, 2, 3] 0 [] [0, 1, 2, 3] 0.0
```

每一行依次是请求、命中长度、可复用的前缀、要继续处理的后缀、复用比例。`[1, 2, 0]` 和 `[0, 1, 2, 3]` 都是零命中：前者和登记对象只有前两个词元相同，没有登记过 `[1, 2]`；后者虽然中间有三个词元和 `(1, 2, 3)` 相同，但不是从开头相同。

notebook 特意说明：这里的账本只是词元计数，不代表实测性能。真实后端的可复用粒度可能不同，实际跳过量要读取后端计数。

## 容易踩的坑

- **把中间相同当成命中**：匹配只看请求的开头。`[0, 1, 2, 3]` 对 `(1, 2, 3)` 的命中长度是 0，整个输入仍需预填充。
- **没登记就当作可复用**：只登记了 `[1, 2, 3]` 时，`[1, 2, 0]` 返回零；另行登记 `[1, 2]` 以后才能命中两个。
- **空前缀没报错、重复前缀没去重**：空对象不能进入索引，相同前缀只登记一次。
- **空输入求比例时除以零**：输入为空时复用比例约定为 `0.0`。命中数加未命中数要等于输入词元数，拆出的两段拼回去也必须还原原输入。
- **把账本当成性能**：复用比例只是词元计数，不代表实测性能。完全命中也不等于没有首词元成本，实际跳过量要读取后端计数。
