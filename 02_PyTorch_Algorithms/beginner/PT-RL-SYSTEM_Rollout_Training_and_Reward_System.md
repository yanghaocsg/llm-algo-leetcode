## 一句话说清

在线训练要经过生成、打分、更新几个环节，一个环节快不代表整体快。这本 notebook 把各环节的处理能力换算成同一种单位，找出瓶颈，再判断一套部署方案能不能用。

## 为什么需要它

在线后训练是一个循环：模型生成回答，打分，更新参数，再把新权重分发回去。每一步由不同的角色负责，角色可以放在同一组 GPU 上，也可以分开放。

只看单个角色，很容易判断错。notebook 举了一个例子：奖励器每秒能处理 80 条轨迹，听起来够快。但每个提示词（prompt）要生成 4 条候选，所以它每秒只相当于处理 20 个提示词组。如果提示词组每秒到达 24 组，奖励这一步的队列还是会越来越长。

部署方式也有取舍：

- 全部放在同一个资源池，叫共置。数据不用来回传，但策略、参考模型、奖励模型和训练状态要抢同一份显存。
- 分开放在不同的资源池，叫分离。每个角色可以单独扩容，但轨迹、对数概率和权重都要跨池传输。

这本 notebook 的做法是先算账再下结论：把各阶段的处理率换算成同一种单位，列出每个资源池的显存和每条跨池链路的传输量，然后分两层判断，哪些是硬失败，哪些只是需要调优。

## 先认识几个词

| 词 | 人话解释 |
|:---|:---|
| 资源池 | 一组放在一起分配的 GPU 等资源，每个角色都要落在某个池里 |
| 轨迹生成器、奖励、学习器 | 在线训练的三个角色：让模型生成回答、给回答打分、用数据更新参数 |
| 共置 / 分离部署 | 共置是让几个角色共用同一个资源池，分离是把它们放到不同的池 |
| 统一工作单位 | 账本里统一使用的计数单位，比如“一个提示组”或“一条轨迹” |
| 队列余量（queue margin） | 阶段的处理能力减去到达率，正数有余量，负数会积压 |
| 互连域（fabric） | 连接资源池的一条共享链路，同一条链路上的传输会抢带宽 |
| 暴露占用（exposed） | 扣掉可以和其他工作重叠的部分以后，传输真正占住链路的时间比例 |

## 核心思路

账本分三张：各阶段的处理率、各资源池的显存、跨池链路的传输。处理率和传输的算法如下：

```text
统一处理率   c_j = q_j / m_j                阶段 j 每秒能处理多少个工作单位
流水线容量   C_pipe = min_j c_j               最慢的阶段决定整体
队列余量     s_j = c_j - lambda               负数表示会积压
传输载荷     b_e = z_e * m_e * lambda_e       跨池的边每秒要传的字节数，同池的边记 0
暴露占用     x_e = (b_e / B_e) * (1 - o_e)    扣掉可以和其他工作重叠的部分
互连域汇总   X_f = 同一互连域内各边 x_e 相加；X_critical = 各域取最大值
```

`q_j` 是阶段 `j` 的原始处理率，`m_j` 是每个工作单位包含的对象数，`lambda` 是工作单位的到达率。`z_e` 是单个对象的字节数，`B_e` 是链路的有效带宽，`o_e` 是可重叠的比例，取 0 到 1。

下面用测试里的数字算一遍容量和传输：

```python
rates = {'rollout': 240, 'reward': 160, 'learner': 80}   # 各阶段每秒处理的对象数
items = {'rollout': 3, 'reward': 2, 'learner': 1}        # 每个提示组包含的对象数
c = {name: rate / items[name] for name, rate in rates.items()}
print(c)
print(min(c.values()), {name: rate - 70 for name, rate in c.items()})   # 到达率是每秒 70 组

print({name: rate - 90 for name, rate in {'rollout': 120, 'reward': 80}.items()})   # 两个阶段每秒 120 和 80 个提示组，到达率 90

edges = [  # (每对象字节数, 每提示组对象数, 提示组/秒, 带宽 字节/秒, 可重叠比例, 互连域, 是否跨池)
    (100, 2, 5, 1000, 0.5, 'pcie-0', False),
    (1000, 1, 1, 2000, 0.0, 'pcie-1', True),
    (500, 1, 1, 2000, 0.0, 'pcie-1', True),
    (1000, 1, 1, 2000, 0.5, 'pcie-2', True),
]
fabric = {}
for z, m, lam, bw, o, f, cross in edges:
    traffic = z * m * lam if cross else 0.0    # 同池的边不用传输
    if cross:
        fabric[f] = fabric.get(f, 0.0) + traffic / bw * (1 - o)
print(fabric, max(fabric.values()))
```

```text
{'rollout': 80.0, 'reward': 80.0, 'learner': 80.0}
80.0 {'rollout': 10.0, 'reward': 10.0, 'learner': 10.0}
{'rollout': 30, 'reward': -10}
{'pcie-1': 0.75, 'pcie-2': 0.25} 0.75
```

前两行是容量。三个阶段的原始处理率不同，但每个提示组在生成阶段要处理 3 个对象，奖励阶段 2 个，学习阶段 1 个，换算以后都是每秒 80 个提示组。容量取最小值，所以三个阶段都是瓶颈。到达率是 70 时，每个阶段都剩 10 的余量。

第三行是另一种情况：生成阶段每秒 120 个提示组，奖励阶段 80 个，到达率是 90。奖励阶段的余量是 −10，会积压，属于不稳定阶段。

第四行是传输。第一条边的两端在同一个资源池，不用传输。第二、三条边共用 `pcie-1`，暴露占用要相加，0.5 加 0.25 等于 0.75。第四条边单独用 `pcie-2`，是 0.25。关键值取最大者 0.75，而不是把所有边加起来。

账本算完以后分两层判断：显存超限、版本未确认、恢复路径缺失属于硬失败，结果是 `reject`；队列积压或传输暴露过高说明需要调优，结果是 `tune`；都没有就是 `accept`。硬失败优先于调优。账本通过只说明这套部署值得进入真实的多工作进程实验，不代表已经获得吞吐收益。余量等于 0 也只是理想情况下流量平衡，不能证明随机队列稳定。

## 容易踩的坑

- **处理率没换算到同一单位**：每个提示词生成 `G` 条候选，逐轨迹处理的阶段就要除以 `G`。阶段集合不一致、速率或倍率不是正数、到达率为负，都要报错。
- **并列的瓶颈只记一个**：容量是最小的等价处理率，所有等于容量的阶段都是瓶颈，要全部保留。余量为负的阶段也要逐项列出。
- **同池的边也算传输，或把不同互连域的占用相加**：同池边的载荷记 0。同一个互连域的边抢带宽，要相加；不同互连域可以并行，关键值取最大值。重叠比例必须在 0 到 1 之间。
- **硬失败被调优原因盖住**：`reject` 优先于 `tune`。显存超限、版本未确认、恢复路径缺失同时出现时要全部记录，不能只返回第一个。
- **账本通过就当成有收益**：`accept` 只表示可以进入真实的多工作进程实验，不代表已经获得吞吐收益。
