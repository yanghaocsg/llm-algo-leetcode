## 一句话说清

GRPO 让模型对同一道能自动判分的题生成一组回答，再按组内谁好谁坏来更新。这本 notebook 教你判断这样的训练结果能不能交付。

## 为什么需要它

有一类题能自动判对错。notebook 的真实实验用的是 GSM8K 数学题：规则验证器提取回答里的最后一个数值，和标准答案比较。

GRPO（组相对策略优化）的做法是：让模型对同一道题生成一组回答，验证器给每条回答打奖励，再按组内谁好谁坏来更新模型。它和 84 节的 DPO 并列，都从 62 节的 SFT 基线出发。

交付结果时，有三个坑：

- 一组回答全对或者全错。组内没有差别，就比不出谁好谁坏，这一组不产生更新。采样成本已经付了，训练信号却是零。
- 拿训练时的奖励当质量证据。这些回答既参与了计算，又参与了更新，分数好看不说明问题。
- 只算生成速度。生成得快，不代表真正进入更新的训练信号多。

这本 notebook 解决的是“哪些算数”：先检查轨迹能不能用，再把采样成本换算成有效更新量，最后给出 `reject`（拒绝）、`tune`（调优）或 `accept`（接受）。

## 先认识几个词

| 词 | 人话解释 |
|:---|:---|
| 验证器（verifier） | 给回答自动判分的规则，比如提取回答里的最后一个数值和标准答案比较 |
| 轨迹（trajectory） | 模型对一道题生成的一条完整回答，连同问题、策略版本、验证器版本等身份信息 |
| 轨迹组 / 组规模 | 同一道题一次生成的一组回答；组规模是一组里有几条，测试里是 4 |
| 奖励（reward） | 验证器给每条回答的分，测试里的取值是 0.0 或 1.0 |
| 有效组 / 零方差组 | 组内奖励不全相同的组是有效组；全对或全错的组叫零方差组，不产生更新 |
| 有效轨迹吞吐 | 每秒有多少条进入了更新的轨迹，分母是采样、验证和更新的总耗时 |
| `accept` / `tune` / `reject` | 决策的三种结果：接受、调优、拒绝 |

## 核心思路

输入分两部分。一部分是轨迹组：每组记录问题编号、来源策略版本、验证器版本和组内各条轨迹的编号。另一部分是证据：每组的奖励、采样和更新耗时、更新次数、更新前后的奖励比较、触顶率和峰值显存。

你补三处判断，中间的候选门槛骨架已经写好：

```text
轨迹契约 → 有效组和有效吞吐 → 候选门槛（骨架已给） → 交付决策
```

Step 2 的几个量，写成纯文本是：

```text
有效组        = 组内奖励不全相同的完整组
有效组比例    = 有效组数 / 全部组数
有效轨迹数    = 有效组数 * 组规模
有效轨迹吞吐  = 有效轨迹数 / (采样耗时 + 验证耗时 + 更新耗时)
```

“完整组”指组内轨迹条数等于组规模。下面用测试里的数字算一遍：

```python
group_size = 4
reward_groups = [[0.0, 1.0, 0.0, 1.0],   # 有对有错：有效
                 [1.0, 1.0, 1.0, 1.0],   # 全对：组内没有差别
                 [0.0, 0.0, 0.0, 0.0],   # 全错：组内没有差别
                 [0.0, 0.0, 1.0, 1.0]]   # 有效
complete = [g for g in reward_groups if len(g) == group_size]
valid = [g for g in complete if max(g) > min(g)]

ratio = len(valid) / len(reward_groups) if reward_groups else 0.0
count = len(valid) * group_size
seconds = 4.0 + 2.0                     # 采样 4 秒，更新 2 秒
throughput = count / seconds if seconds > 0 else 0.0
print(ratio, count, round(throughput, 2))
print(round(len(reward_groups) * group_size / seconds, 2))   # 对照：按全部轨迹算
```

```text
0.5 8 1.33
2.67
```

4 个组里，第 2 组全对、第 3 组全错，都是零方差组，不计入。有效组有 2 个，比例是 0.5；有效轨迹是 2 组各 4 条，共 8 条。采样加更新用了 6 秒，有效轨迹吞吐是每秒 1.33 条，过了门槛 1.0。最后一行是对照：按全部 16 条轨迹算会得到 2.67，这个数虚高。

候选门槛有八项，要同时通过：执行成功；有效组比例、有效轨迹吞吐、更新次数不低于下限；更新前后的平均奖励和组内至少一次通过率（notebook 里写作 `pass@group`）的变化不低于下限；触顶率和峰值显存不超过上限。

最后一步是交付决策，按顺序判断：

```text
轨迹没通过、执行失败或产物缺失 → reject
候选门槛没通过               → tune
全部通过                     → accept
```

更新后，候选要在隔离的评测题上重新生成一批回答，再和更新前配对比较。notebook 强调：训练轨迹只说明更新发生过，不能兼任独立质量证据。

## 容易踩的坑

- **把零方差组算成有效组**：全对或全错的组没有组内差异，必须从有效组比例和有效轨迹吞吐里排除。完成生成但没有相对奖励信号，候选不能通过。
- **用总轨迹数和生成耗时算吞吐**：分子只数有效组里的轨迹，分母是采样、验证和更新的总耗时。上面的例子里，按全部轨迹算是 2.67，有效的吞吐是 1.33。
- **旧策略、旧验证器或重复轨迹混进来**：组内优势只能比较有明确问题身份、同一策略、同一验证器和完整组的真实轨迹。重复轨迹会重复计权，空的轨迹组也不通过。
- **拿训练轨迹当质量证据**：训练轨迹既参与了优势计算，又参与了参数更新。更新后要在隔离的评测题上、固定随机条件下重新生成，再和更新前配对比较。
- **奖励提高就认为更新安全**：notebook 把代理比率、平方惩罚和实际更新次数单独记为“更新约束记录”，提醒奖励提高不能证明更新幅度安全。
