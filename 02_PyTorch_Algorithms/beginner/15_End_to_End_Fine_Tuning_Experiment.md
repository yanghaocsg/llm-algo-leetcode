## 一句话说清

训练时把一批数据拆成几小份依次算梯度，攒够了再更新一次参数，这叫一次有效更新。这本 notebook 教你把评估、参数更新、学习率和训练记录都对齐到同一个计数上。

## 为什么需要它

显存放不下一大批数据时，常见的做法是把它拆成几个小份，每份各算一次梯度并累加，最后一起更新参数。这本 notebook 把“处理完一份大的、更新一次参数”叫作一次有效更新。

拆开以后容易出三种错：

- 每一小份各自算平均损失，再把几个平均值取平均。回答短的那一份里，每个词元的权重就被放大了。
- 评估完忘了把模型切回训练模式，或者评估时改动了已有的梯度。下一次训练就不对劲。
- 学习率和训练记录按小份的次数推进，参数却按有效更新推进。两边差了步数，记录就对不上参数。

看 notebook 的例子：两个微批次的回答长短不同，有效监督词元分别是 4 个和 10 个，两份损失总和都应该除以 14。如果先各除以自己的词元数再取平均，短回答里每个词元的权重就比长回答大。

这本 notebook 就带你把这条训练循环写对：评估怎么隔离状态，损失怎么缩放，哪些东西必须按同一个更新编号推进。

## 先认识几个词

| 词 | 人话解释 |
|:---|:---|
| 微批次（micro-batch） | 逻辑批次里一次前向传播和反向传播处理的那一小份样本 |
| 逻辑批次 | 共同参与一次参数更新的全部样本，通常由几个微批次组成 |
| 有效更新 | 处理完一个逻辑批次后，优化器完成的一次参数写回 |
| 更新时钟 | 按参数写回的次数计数，不是真实时间；学习率和记录都跟着它走 |
| 监督词元 | 标签里真正参与损失计算的词元，也就是回答和结束标记 |
| 训练模式 / 评估模式 | 模型的两种状态：训练模式下随机失活生效，评估模式下关闭 |
| 计算图 | 自动求导记录的运算过程，训练时保留它才能反向传播，评估时不需要 |

## 核心思路

题目区的骨架已经写好了训练循环，一次有效更新从头到尾是这样的（以两个微批次为例）：

```text
optimizer.zero_grad()                   更新开始：梯度归零
微批次 1：损失总和 / N_u，反向传播      参数不变
微批次 2：损失总和 / N_u，反向传播      参数不变
optimizer.step()                        参数写回一次，更新编号加 1
scheduler.step()                        学习率推进一次
evaluate_loss(...)                      评估结果记在这个更新编号下
```

`N_u` 是整个逻辑批次的有效监督词元总数。Step 3 的公式写成纯文本是：

```text
g_u = sum over k of grad(S_{u,k} / N_u)          N_u = N_{u,1} + N_{u,2} + ...
theta_{u+1} = OptimizerStep(theta_u, g_u)
```

`u` 是更新编号，`k` 是微批次的序号；`S_{u,k}` 是第 `k` 个微批次的损失总和，`N_{u,k}` 是它的监督词元数；`g_u` 是攒出来的总梯度；`theta` 是模型参数。

为什么要共用一个分母，用数字看一下。设短的那份每个词元损失 1.0，长的那份每个 0.2：

```python
tokens = [4, 10]                    # 两个微批次各自的有效监督词元数
per_token = [1.0, 0.2]              # 各自每个监督词元的损失
loss_sum = [n * p for n, p in zip(tokens, per_token)]            # 各自的损失总和
total = sum(tokens)
scaled = [round(s / total, 4) for s in loss_sum]                # 每个微批次反向传播时用的损失
print(loss_sum, scaled, round(sum(s / total for s in loss_sum), 4))
print((loss_sum[0] / tokens[0] + loss_sum[1] / tokens[1]) / 2)   # 先各自平均，再各乘 1/2
print(round(tokens[0] / total, 4))                              # 短回答的词元在全部监督词元里的占比
```

```text
[4.0, 2.0] [0.2857, 0.1429] 0.4286
0.6
0.2857
```

两份“损失总和 ÷ 14”加起来，正好是 14 个词元的平均损失 0.4286。先各自平均再取平均得到 0.6：短回答那份在结果里占了一半，可它的词元只占 0.2857。

评估走的是另一条路：复用同一个损失函数，但不记录梯度，也不改参数。做之前记下模型原来是什么模式，切到评估模式，算完再切回去。这一步写在 `finally` 里，就算中途出错也能恢复。

## 容易踩的坑

- **各微批次先取平均再平均**：微批次的损失总和要除以整个逻辑批次的目标总数。只有各微批次目标数相等时，等权平均才等价。
- **评估完没切回训练模式**：评估前记下 `model.training`，在 `finally` 里用 `model.train(was_training)` 恢复，中途出错也能恢复。
- **评估时动了梯度**：评估要在 `torch.no_grad()` 里做，只读取参数，已有的梯度不能被修改。
- **学习率和记录按微批次推进**：`scheduler.step()` 和过程记录只在 `optimizer.step()` 之后各做一次，一个逻辑批次只写回一次参数。
- **整个逻辑批次没有监督词元**：这时平均损失没有定义，要报错。没有有效目标的单个微批次则直接跳过。
