# INF-PARALLEL-DRAFTING. 并行草稿与置信度调度 — 小白讲解

> 对应 notebook：[`INF-PARALLEL-DRAFTING_DFlash_and_DSpark.ipynb`](./INF-PARALLEL-DRAFTING_DFlash_and_DSpark.ipynb)

## 一句话总结
自回归草稿要一个词元等一个词元地串行生成；DFlash 让块扩散草稿模型在一次前向里同时给出多个位置的分数，DSpark 再在并行主干后加一个轻量 Markov 修正，并按置信度决定送多少个连续候选给目标模型验证。本节用 `dflash_parallel_candidates`、`project_markov_bias`、`choose_confident_prefix` 三个函数把"并行选词、低秩前驱修正、连续前缀预算"变成可单测的数值步骤。

## 为什么需要它：痛点是什么
投机解码的基本流程是"草稿模型先猜几个词元，目标模型一次前向并行验证，接受最长的正确前缀"。如果草稿是自回归的，猜 5 个词元就要串行跑 5 次草稿模型，草稿阶段本身成了瓶颈。并行草稿能把这 5 次压成 1 次，但新问题来了：块里后面的位置在打分时还没看到前面最终选了什么，容易出现"前一个位置选了 A，后一个位置却按 B 的语境打分"的不协调；而且如果后部候选经常被拒绝，生成和验证它们的算力就白花了。

生活类比：开卷考试，甲同学一题一题往后写（自回归草稿），乙同学一次性把五道题的答案都写出来（并行草稿）。乙快，但第二题可能和第一题答案不连贯；于是老师（DSpark 的 Markov 模块）在乙交卷前，根据前一题答案给后一题加一点提示分；最后阅卷人（目标模型）从第一题开始连续批改，遇到第一道错题就停止，不浪费时间看后面。

## 核心问题
- 并行草稿的"并行"到底并行在哪？为什么选完词元后还要目标模型验证？
- 前一个候选怎样通过低秩投影修正当前位置的分数？为什么用 $r\ll V$ 的小矩阵？
- 置信度阈值怎样决定验证预算？首位置就低于阈值时怎么办？
- 为什么预算必须取"连续前缀"，不能跳过中间低置信位置只验证后面的？
- 这些函数和真实草稿模型、真实加速比之间还差哪些环节？

## 解决思路：一步步看懂

**Step 1：三种草稿路径的分工。** 自回归草稿每一步都经过草稿模型，后一位置等待前一候选，草稿时延随长度增长；DFlash 用目标模型提供的上下文特征，通过块扩散草稿模型在一次前向中形成多个位置的候选分布，单轮得到"候选块"；DSpark 在并行主干之后加轻量顺序模块，先保留整块基础分数，再沿候选顺序修正，并给出置信度。notebook 特别强调：这里的"并行"指各位置的分数一起产生，选完词元后仍要交给目标模型连续验证，接受与否由目标模型决定。

**Step 2：TODO 1——逐位置独立取 argmax。** `_validate_block_logits` 先检查块非空、每行长度一致，并返回词表大小 $V$。参考答案：

```python
candidates = [max(range(vocab_size), key=lambda token: row[token]) for row in block_logits]
```

每个位置只看自己那一行分数，不读取相邻位置的候选，这正是"并行"的含义。`test_dflash_parallel_candidates` 用 `[[0.1,0.8,0.1],[0.6,0.2,0.2],[0.1,0.2,0.7]]` 得到 `[1,0,2]`；只改第二行为 `[0.1,0.2,0.9]`，结果变成 `[1,2,2]`，第一、三位不受影响。空块 `[]` 和行长不一致的 `[[0.1,0.9],[0.3]]` 都必须抛 `ValueError`。

**Step 3：TODO 2——低秩前驱投影。** DSpark 的 Markov 模块只依赖前一个词元。记前一个词元为 $x_{i-1}$，它的低维表示为 $e(x_{i-1})\in\mathbb{R}^{r}$，投影矩阵为 $P\in\mathbb{R}^{r\times V}$，则当前位置的词表偏置是

$$b_i=e(x_{i-1})P,\qquad b_i[v]=\sum_{j=1}^{r}e(x_{i-1})[j]\cdot P[j][v].$$

因为 $r$ 远小于词表大小 $V$，这一步只需要一个小状态和一个小矩阵，比直接学一个 $V\times V$ 的转移矩阵便宜得多。参考答案：

```python
bias = [
    sum(float(latent[index]) * float(markov_projection[index][token]) for index in range(rank))
    for token in range(vocab_size)
]
```

`latent = markov_embeddings.get(previous_token)`；如果前一个词元不在表里，返回 `[0.0] * vocab_size`，表示"没有先验，不做修正"，而不是报错或随便猜一个。`len(latent) != rank` 要抛 `ValueError`，因为维度和投影矩阵对不上。手算测试：`embeddings={7:[2.0,-1.0]}`、`projection=[[0.5,0.0,1.0],[1.0,-1.0,0.5]]`、$V=3$，则
- 第 0 列：$2\times0.5+(-1)\times1.0=0$；
- 第 1 列：$2\times0.0+(-1)\times(-1.0)=1$；
- 第 2 列：$2\times1.0+(-1)\times0.5=1.5$。

所以偏置是 `[0.0, 1.0, 1.5]`；未知前驱 9 返回 `[0.0,0.0,0.0]`。

**Step 4：顺序循环怎样把修正传下去。** `dspark_markov_candidates` 从 `anchor_token` 开始，对每一行先算偏置、把 `row` 加上 `bias` 得到 `corrected`，再取 `argmax` 作为当前位置候选，并把它设为下一位置的 `previous`。手算测试：`logits=[[0.4,0.6],[0.7,0.3],[0.6,0.4]]`、`embeddings={9:[1.0],0:[-1.0],1:[1.0]}`、`projection=[[0.5,-0.5]]`、anchor 9。
- 位置 0：前驱 9 → latent `[1.0]` → bias `[0.5,-0.5]`；修正后 `[0.9,0.1]` → 选 0。
- 位置 1：前驱 0 → latent `[-1.0]` → bias `[-0.5,0.5]`；修正后 `[0.2,0.8]` → 选 1。
- 位置 2：前驱 1 → latent `[1.0]` → bias `[0.5,-0.5]`；修正后 `[1.1,-0.1]` → 选 0。

结果 `[0,1,0]`。这说明前一个候选确实改变了后一位置的修正方向，而不是各位置各算各的。

**Step 5：TODO 3——连续置信前缀。** 置信度估计"在此前候选都被接受的前提下，该位置能通过目标验证"的可能性。参考答案：

```python
should_stop = confidence < threshold
if should_stop:
    break
prefix_length += 1
```

从第一个位置开始累计，遇到第一个低于阈值的位置立即停止；返回长度同时受 `confidences[:max_tokens]` 和输入长度约束。为什么不能跳过中间低置信位置只验证后面的？因为目标模型是从头连续验证的：前面一旦被拒绝，后面的候选就失去了上下文前提，单独验证没有意义。`test_choose_confident_prefix` 覆盖五种情况：`[0.9,0.8,0.3,0.95]`、阈值 0.5、上限 4 → 2；`[0.1,0.9]` → 0（首位置失败，预算为零）；`[]` → 0；`[0.9]*10`、上限 4 → 4（被预算截断）；置信度 1.1、阈值 −0.1、上限 0 三种非法输入都抛 `ValueError`。

**Step 6：统一记录与零预算回退。** `build_draft_record` 把候选块和预算整理成 `mode`、`block_tokens`、`verify_tokens`、`proposed`、`verify_budget`、`fallback_to_decode` 六个字段。`verify_tokens` 是 `candidates[:budget]`；`budget == 0` 时列表为空，`fallback_to_decode=True`，表示这一轮不提交候选，直接让目标模型生成。`test_unified_draft_record` 用 `dspark`、候选 `[4,5]`、置信度 `[0.2,0.9]`、阈值 0.5，得到空验证列表、预算 0、回退为真；未知 `mode` 抛 `ValueError`。

## 关键概念速查表
| 术语 | 大白话解释 |
|---|---|
| 投机解码 | 草稿模型先猜，目标模型并行验证并接受最长正确前缀 |
| 自回归草稿 | 一个词元等一个词元地串行生成，草稿时延随长度增长 |
| 并行草稿（DFlash） | 一次前向同时给出块内多个位置的分数 |
| 块扩散 | 用扩散式草稿模型一次形成整块候选分布 |
| Markov 修正（DSpark） | 用前一个候选的低维状态给当前位置加词表偏置 |
| 低秩投影 | $r\times V$ 的小矩阵，$r\ll V$，把前驱状态映射成词表偏置 |
| 置信度 | 该位置在此前候选都被接受时通过验证的估计概率 |
| 连续前缀 | 从第一个位置起连续达到阈值的候选，不能跳过中间失败项 |
| 验证预算 $k$ | 这一轮实际送给目标模型验证的候选个数 |
| 零预算回退 | $k=0$，不提交候选，由目标模型直接生成 |
| 前缀存活概率 | 从起点到某位置全部被接受的概率 |
| 接受长度 | 目标模型验证后真正接受的连续词元数，由目标模型决定 |

## 小白常见疑问

**Q1：既然各位置独立取 argmax，为什么还需要 DSpark 的顺序修正？**
因为并行主干打分时，后面的位置还没看到前面最终选出的词元，容易出现跨位置不协调。`dspark_markov_candidates` 在保留整块基础分数之后，按候选顺序把前一个词元的低维状态投影成偏置，逐位置修正，再选 argmax；`test_dspark_markov_candidates` 的 `[0,1,0]` 就是修正会改变选择结果的例子。

**Q2：前一个词元不在 `markov_embeddings` 里，为什么返回全零而不是报错？**
零偏置表示"没有先验信息，退回并行主干分数"，这是一种安全的默认行为，不会让整个块失败。维度不匹配才是真正的配置错误，所以 `len(latent) != rank` 会抛 `ValueError`；`test_project_markov_bias` 对未知前驱 9 断言全零，对 `{7:[1.0]}` 断言抛错。

**Q3：置信度低于阈值就一定被拒绝吗？**
不一定。置信度只是"估计"，用来决定送多少候选去验证；真正接受与否由目标模型验证决定。notebook 说"筛选决定送去验证的长度，目标模型决定实际接受结果"。所以置信度校准得越准，预算越接近真实接受长度，浪费越少。

**Q4：为什么预算取连续前缀，而不是把所有高于阈值的位置都送去验证？**
目标模型是顺序验证的：第 2 个候选被拒绝后，第 3 个候选就失去了"前两个都被接受"的前提，单独验证它没有意义。`choose_confident_prefix` 遇到第一个低置信位置就 `break`，返回的是连续长度，不是高于阈值的个数。

**Q5：跑通这些测试，就能说明 DFlash/DSpark 真的能加速吗？**
不能。本节是 CPU 机制练习：给定分数、投影矩阵和置信度，检查候选选择、低秩修正和预算截取。真实草稿模型的加载、目标验证和性能采集需要配对权重与执行后端，notebook 明确把它们放到后续机制选型项目里；这里不产生也不引用任何加速比。
