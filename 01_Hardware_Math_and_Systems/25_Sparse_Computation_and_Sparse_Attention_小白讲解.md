# 25. 稀疏计算与稀疏注意力 — 小白讲解

> 对应 notebook：[`25_Sparse_Computation_and_Sparse_Attention.ipynb`](./25_Sparse_Computation_and_Sparse_Attention.ipynb)

## 一句话总结
本节用五个 CPU 上就能跑的小计算器，把"稀疏"拆成三件不同的事：数保留了多少（密度）、检查保留位置是否符合 2:4 的局部规则、估算 COO 存储与理想乘加量。再用一组给定的准备耗时说明"稀疏主体更快，整次调用未必更快"，最后用双向局部窗口注意力核对连接数（8 个位置从 64 条降到 22 条）和输出变化。结论是：密度相同不等于执行相同，索引、准备和连接语义都必须单独记账。

## 为什么需要它：痛点是什么
初学者最常见的误解是"剪掉一半权重，就应该快一倍、省一半显存"。实际至少有三道坎。第一，把权重置零但继续用稠密张量和稠密矩阵乘，存储大小和遍历的元素一个都没少；第二，就算真的换成稀疏格式，坐标（COO）要为每个非零值额外存行、列两个索引，非零值少了，总字节反而可能更多；第三，稀疏路径往往要先准备掩码、索引或压缩格式，调用一次时分摊下来的准备成本可能比省下的乘法还贵。

生活类比：图书馆清掉一半书。如果只是把书从架上拿走、目录和书架布局不动，找书的工作量没变；如果改成"只登记留下的书"，那本目录本身也要占地方，书越少、每本书的索引相对越贵；如果再把书按主题分散到不同楼层，找一本书可能要在几个楼层之间跑——书的总数一样，取书路径完全不同。

## 核心问题
- 密度和稀疏率怎么定义？权重密度与注意力连接密度是一回事吗？
- 全局 50% 非零，为什么可能过不了"每四项最多两个非零"的局部检查？
- 非零元素变少了，COO 存储为什么反而更大？理想稀疏 FLOPs 又该怎么算？
- 稀疏主体更快，为什么一次完整调用还可能更慢？准备成本怎么摊销？
- 局部窗口注意力减少了哪些连接？输出为什么和稠密结果不同，什么时候才该相等？

## 解决思路：一步步看懂

**第 0 步：先分清三个"稀疏对象"。** notebook 的表格把可稀疏的对象分成三类，每类省掉的工作和要核对的代价都不同：权重稀疏省掉的是"被移除权重参与的乘加"，代价是索引、格式转换和实际稀疏矩阵乘；注意力连接稀疏省掉的是"选定查询—键连接的得分及值加权"，代价是掩码生成、连接选择和输出质量；前馈网络的通道或激活稀疏省掉的是"未选通道或零激活参与的计算"，代价是选择、聚集和各工作块的负载差异。三者不能共用一个"密度 × 耗时"公式，下面的每个计算器只回答其中一小块。举个具体对照：把某层权重剪掉 50%，如果只是把数值置零，张量形状和矩阵乘都不变；只剪注意力的远距离连接，权重一个都没少，省的是得分计算和加权求和；如果是前馈层里未被选中的通道，省的是这些通道的乘加。三个"50%"指的根本不是同一批工作，所以 notebook 坚持让每个问题生成自己的标记，而不是拿一个密度标签直接推性能。

**第 1 步：Q1——密度只数"保留了几个"，不描述"保留在哪"。** `retained_position_report(keep)` 接收一串布尔保留标记：

```python
if not keep or any(type(value) is not bool for value in keep):
    raise ValueError("保留标记须为非空布尔序列")
retained = sum(keep)
return {"total_positions": len(keep), "retained_positions": retained,
        "density": retained / len(keep), "removed_ratio": 1 - retained / len(keep)}
```

`sum(keep)` 能直接对布尔序列求和，是因为 Python 里 `True` 当 1、`False` 当 0；但函数先用 `type(value) is bool` 卡住类型，拒绝把 `0/1` 整数混进来——否则你分不清"这是一个保留标记"还是"这是一个数值"。密度 `density` 是保留数除以总数，移除比例 `removed_ratio` 是它的补数，两者相加为 1。

两个探针序列很关键：

```python
balanced  = [True, False, True, False, True, False, True, False]
clustered = [True, True, True, False, False, False, False, True]
```

`balanced` 是隔一个留一个，`clustered` 是前三个加最后一个。两者的 `retained_positions` 都是 4，`density` 都是 0.5，但保留位置完全不同。这正是 Q2 要接着问的：只看总数，看不出局部模式。全 `True` 时 `removed_ratio` 为 0，全 `False` 时 `density` 为 0，这两个边界也在单元里断言了。注意全 `False` 在 Q1 只是"可统计"，放到注意力里就不可用了：`masked_attention_cpu` 会检查每一行至少允许一个键，整行屏蔽会直接抛 `ValueError`，因为 Softmax 失去了归一化对象。同一个"密度 0"，在统计函数里合法，在注意力语义里非法。

注意力里的"连接密度"要单独理解：掩码里的 `True` 表示"允许这个查询看这个键"。八个位置允许四个参与，连接密度就是 0.5；**即使这四个位置的得分恰好都是零，它们仍然参与 Softmax 归一化**——得分为零只说明权重均分，不说明它们被排除。所以不能拿"权重里有多少零"去推断"注意力会跳过多少连接"，两者数的根本不是同一批标记。

**第 2 步：Q2——全局一半非零，局部可能违规。** notebook 先区分几种稀疏结构：非结构化稀疏允许每个位置独立保留；行列稀疏直接移除整行或整列；块稀疏以小矩阵为单位保留；半结构化稀疏再加局部约束，典型就是 2:4——按指定维度的每四个连续位置保留两个存储槽，其余置零。注意"保留槽本身也可能装的是零值"，格式合规和数值上真的非零是两件事。

`group_sparsity_report(values, group_size=4, max_nonzero=2)` 只做一件事：把一行数按 `group_size` 切成完整组，数每组里 `value != 0` 的个数，超过 `max_nonzero` 的组记为违规：

```python
counts = [sum(value != 0 for value in values[start:start + group_size])
          for start in range(0, len(values), group_size)]
violating = [index for index, count in enumerate(counts) if count > max_nonzero]
return {"nonzero_counts": counts, "violating_groups": violating,
        "pattern_matches": not violating}
```

两行八元素的权重，全局都正好 4 个非零：`balanced_weights = [1, 0, 2, 0, 3, 0, 4, 0]` 的每组计数是 `[2, 2]`，通过；`clustered_weights = [1, 2, 3, 0, 0, 0, 0, 4]` 的计数是 `[3, 1]`，第 0 组有三个非零，违规。函数还检查 `group_size` 是正整数、`0 <= max_nonzero <= group_size`、输入非空且长度能被组大小整除；全零的 `[0, 0, 0, 0]` 计数为 `[0]`，`pattern_matches` 为 `True`。换句话说，同样四个非零值，换个摆放位置就可能从合规变成违规，这就是"局部模式"比"全局密度"多出来的约束。

为什么叫"半结构化"？纯非结构化稀疏的位置完全随机，内核要先读索引再逐个取数，很难做规则的向量化；2:4 把随机性限制在每组四个位置里，格式为每组提供两个存储槽，读取模式比任意稀疏更规则。代价是约束更硬：不能任意剪，必须按组来；而且"槽"是格式概念，槽里装的值可以是零，检查只要求非零数不超过上限。

必须强调：这个函数**不是设备能力查询**。真实要用稀疏矩阵乘加指令，还要满足接口规定的维度、格式、布局和设备支持；任意块稀疏或行列稀疏，不能仅因为"看起来规则"就被认定为能用稀疏 MMA（矩阵乘加指令）。

**第 3 步：Q3——非零少了，索引可能让总字节变大。** `sparse_matmul_ledger(m, n, k, retained_weights, value_bytes=2, index_bytes=4)` 按二维 COO 估算：每个保留的权重存一个数值、一个行索引、一个列索引。

```python
"dense_weight_bytes": k * n * value_bytes,
"coo_value_bytes": retained_weights * value_bytes,
"coo_index_bytes": retained_weights * 2 * index_bytes,
"coo_total_bytes": retained_weights * (value_bytes + 2 * index_bytes),
"dense_flops": 2 * m * k * n,
"ideal_sparse_flops": 2 * m * retained_weights,
```

拿 4×4 权重、FP16（2 字节）、默认 4 字节索引手算：稠密载荷是 $4 \times 4 \times 2 = 32$ B；只保留 4 个值时，数值占 $4 \times 2 = 8$ B，索引占 $4 \times 2 \times 4 = 32$ B，合计 40 B——比稠密还大 8 B。按这组字节数还能看出盈亏平衡点：每保留一个非零值要花 $2 + 2 \times 4 = 10$ B，而稠密每个元素只花 2 B，所以只有当保留比例低于 $2/10 = 20\%$ 时，COO 载荷才会比稠密小。这是从给定常量推出来的算术，不是实测结论；块格式和 2:4 压缩有自己的元数据账目，不能套这个 40 B。COO 的特点是索引按"每个非零值"付费：非零越少，索引总量确实线性下降，但每个值固定背着 8 B 索引，稀疏度不够时就不划算。块格式和 2:4 则使用各自的元数据，不按每个值配两份索引。它们省索引的方式不同，账目自然不同。

运算量这边，稠密矩阵乘按"一次乘加 = 两次浮点运算"计，工作量是 $2MKN$；如果真能逐个跳过零权重，理想工作量是 $2M n_{\mathrm{nz}}$，其中 $M$ 是输出行数、$n_{\mathrm{nz}}$ 是保留权重数。代入 $M=2, N=4, K=4$：稠密 $2 \times 2 \times 4 \times 4 = 64$ FLOPs；保留 4 个时理想值 $2 \times 2 \times 4 = 16$，保留 2 个时 8，保留 0 个时 0。notebook 明说这个"理想值"**没有计**索引遍历、Softmax、负载不均衡；它回答的是"乘法本身少做了多少"，不是"实际快了多少"。

**第 4 步：Q4——把准备成本摊销到每次调用。** `sparse_call_cost(dense_ms, sparse_ms, setup_ms, reuse_calls)` 的模型很朴素：准备一次，然后复用 `reuse_calls` 次，平均每次耗时是

$$\text{average} = \text{sparse\_ms} + \frac{\text{setup\_ms}}{\text{reuse\_calls}}$$

给定稠密 1 ms、稀疏主体 0.6 ms、准备 2 ms：只调用一次时平均 $0.6 + 2 = 2.6$ ms，比稠密还慢 1.6 ms；复用十次时平均 $0.6 + 0.2 = 0.8$ ms，比稠密快 0.2 ms。把复用次数逐个代进去，可以看出一条很直观的曲线：1 次 2.6 ms、2 次 1.6 ms、4 次 1.1 ms、5 次 1.0 ms、10 次 0.8 ms。第 5 次正好追平稠密，之后才开始赚——这就是"摊销"两个字的含义。边界用例把参数凑成 `dense_ms=1, sparse_ms=0.5, setup_ms=2, reuse_calls=4`，平均正好 $0.5 + 0.5 = 1.0$ ms，`saved_ms_per_call` 为 0——不多不少，白忙一场。

复用能不能成立，取决于**权重和稀疏模式是否保持不变**：固定权重的推理可以一次准备、多次复用；动态激活或每次请求都变的注意力连接，可能每次都要重新准备。函数里的耗时全是传入的给定值，它不从密度预测速度，也不判断某个格式是否真的被内核支持。真正比较时还要把每次发生的索引、聚集开销算进主体，并检查相同输入的数值误差或任务质量。

**第 5 步：Q5——局部窗口改变了连接图。** `build_local_attention_mask(seq_len, window)` 生成 `[1,1,L,L]` 的布尔掩码：

```python
positions = torch.arange(seq_len, device="cpu")
return (positions[:, None] - positions[None, :]).abs().le(window)[None, None]
```

`positions[:, None] - positions[None, :]` 是 $i-j$ 的矩阵，取绝对值后 `<= window` 表示"距离不超过窗口半径"。这是**双向、包含自身**的窗口，不是自回归因果窗口；如果用于生成式解码，还要额外排除未来位置。掩码形状是 `[1, 1, L, L]`，前两维是 1，会广播到 batch 和 head 维；所以 22 条是"每个头、每个 batch 元素"的连接数，代码里 `local_mask.sum()` 统计的也是这一份。长度 8、半径 1 时，对角线 8 条，加上左右各 7 条偏移，共 $8 + 2 \times 7 = 22$ 条；全连接是 $8 \times 8 = 64$ 条。换个算法验证：中间的 $L-2$ 个位置各有左、中、右 3 条，两端的两个位置只有 2 条，总数是 $3(L-2)+4 = 3L-2$，代入 $L=8$ 得 22。注意它**不是**每行固定 3 条——首尾两行各少一条，所以不能直接用 $3L$。

`masked_attention_cpu(q, k, v, mask)` 是 CPU 参考实现，先算完整得分再施加掩码：

```python
scores = q @ k.transpose(-2, -1) / math.sqrt(q.shape[-1])
weights = torch.softmax(scores.masked_fill(~mask, -math.inf), dim=-1)
return weights @ v
```

`masked_fill(~mask, -math.inf)` 把不允许的位置设成负无穷，Softmax 之后这些位置的权重就是 0；如果改成设 0，$e^0=1$ 仍会分到非零概率，这是常见的写错方式。函数还做了几项校验：Q/K/V 必须是相同的非空 `[B,H,L,D]` 形状、同一 dtype 的 CPU 浮点张量；掩码必须是 `[1,1,L,L]` 的 CPU 布尔张量；并且每一行至少要允许一个键，否则归一化没有对象，直接报错"每个查询须至少允许一个键参与归一化"。

为了能心算，探针把 Q、K 全设为零，V 设成位置编号：所有得分都是 0，稠密 Softmax 在 8 个位置上均分 $1/8$，输出是 $0$ 到 $7$ 的平均值 $3.5$。半径 1 的局部窗口下，第 0 行只能看 $\{0,1\}$，输出 $(0+1)/2 = 0.5$；第 1 行看 $\{0,1,2\}$，输出 1；中间第 $i$ 行看 $\{i-1,i,i+1\}$，输出正好是 $i$；最后一行看 $\{6,7\}$，输出 $6.5$。所以断言的是 `[0.5, 1, 2, 3, 4, 5, 6, 6.5]`。窗口为 0 时只剩自身，输出等于 `v`；窗口扩大到 `seq_len` 时覆盖全序列，才要求与稠密结果一致。

工作量的账目也在单元里：按"每条连接做 QK 与加权 V 共约 $4D$ 次运算"计，稠密是 $4 \times B \times H \times L^2 \times D = 4 \times 1 \times 2 \times 64 \times 2 = 1024$ FLOPs，理想局部是 $4 \times 1 \times 2 \times 22 \times 2 = 352$。但注释同时说明：**这个 CPU 参考仍然遍历了全部连接**，`352` 只是"如果真跳过会少做多少"的理想值，不是这段代码实际执行的运算量。这也是为什么输出差异要单独解释：改变连接就是改变模型函数，局部注意力的结果本来就不该等于稠密结果，只有窗口覆盖整个序列时才应相等。

把 Q5 的两个 FLOPs 相除，还能验证账目是线性的：$352/1024 = 34.375\%$，连接数 $22/64 = 34.375\%$，两者完全一致，因为"每条连接约 $4D$ 次运算"里的 $D$ 是常数。也就是说，理想工作量严格随连接数缩放；但这段 CPU 参考仍然执行了 1024，所以它测的是语义而不是加速。真实稀疏注意力内核还要处理不规则索引、块对齐和负载均衡，22 条连接不一定能整齐地映射到硬件块上，实际收益可能低于"少做 65.6%"这个理想值。

另一处对照是 Q2 的全零输入：`group_sparsity_report([0, 0, 0, 0])` 的 `pattern_matches` 为真，说明"格式合规"和"有内容"是两回事。一个全零的 2:4 权重在格式上完全合法，但计算上没有任何有效乘加；反过来，一个密度很低的权重也可能因为索引和准备成本而不划算。格式检查只回答"结构对不对"，不回答"值不值"。

**把五问连起来读。** Q1 回答"数的是哪个对象"，Q2 回答"局部模式是否合规"，Q3 回答"存储和理想乘加怎么记"，Q4 回答"准备成本摊销后是否还划算"，Q5 回答"连接改变后语义和实际执行分别变了什么"。五问没有任何一问能单独证明"稀疏会更快"：密度相同可能执行完全不同，2:4 通过检查不代表内核可用，COO 可能更大，摊销可能不划算，局部注意力还可能改变模型质量。遇到一个"稀疏加速"的说法，按这个顺序逐项追问，比记住一个倍数可靠。

## 关键概念速查表
| 术语 | 大白话解释 |
| --- | --- |
| 密度 / 稀疏率 | 非零（或保留）元素占比 / 它的补数，只描述数量不描述位置 |
| 非结构化稀疏 | 每个位置独立决定保留还是置零，位置没有规律 |
| 行列稀疏（结构化） | 整行或整列一起移除，形状仍然规整 |
| 块稀疏 | 以小矩阵块为单位保留或移除 |
| 2:4 半结构化稀疏 | 每四个连续位置只保留两个存储槽，其余置零 |
| COO（坐标格式） | 每个非零值配一份行索引和列索引 |
| 索引开销 | 稀疏格式为了"说明值在哪里"额外占用的字节 |
| 理想稀疏 FLOPs | 假设真能跳过零时的乘加量，不含索引、聚集与负载不均 |
| 准备成本（setup） | 执行稀疏乘法前生成掩码、索引或压缩格式的时间 |
| 摊销（amortization） | 把一次准备成本摊到多次复用上，平均每次 = 主体 + 准备 / 复用次数 |
| 注意力连接密度 | 掩码允许的查询—键对数占全矩阵的比例 |
| 局部窗口注意力 | 每个查询只看左右一定距离内的键，双向且通常含自身 |

## 小白常见疑问

**Q1：密度 0.5，是不是就能期待快一倍？复用十次就说明稀疏一定值得吗？**
都不能。正文第 1 步的 `balanced` 和 `clustered` 告诉我们"密度只数个数"；如果仍然用稠密张量和稠密矩阵乘，存储和遍历范围都没变。就算换成稀疏格式，正文第 3 步的 4×4 例子显示 50% 稀疏时 COO 反而要 40 B（稠密 32 B）。正文第 4 步的摊销则说明：只有"权重和稀疏模式不变、准备可复用"时，复用十次的 0.8 ms 才成立；动态激活或每次变化的注意力连接可能要重新准备。而且 0.8 ms 只是本模型的算术结果，没有算索引遍历和聚集的实际开销，也没有验证数值质量。

**Q2：2:4 检查通过，就能用稀疏 Tensor Core 了吗？**
不能。`group_sparsity_report` 的文档字符串明确写着"不判断硬件或内核可用性"。它只检查"每四个位置的非零数是否超标"；真实使用还要满足接口规定的维度、格式、布局和设备支持，块稀疏或行列稀疏也不能因为规则就被认定可用。

**Q3：COO 为什么每个值要配两个索引？索引为什么按 4 字节算？**
因为是二维权重，需要行号和列号才能定位，所以是 `2 * index_bytes`。默认 `index_bytes=4` 对应常见的 32 位整数索引；notebook 把 `value_bytes` 和 `index_bytes` 都做成参数，就是为了让你换字节数重算，而不是把 40 B 当唯一答案。

**Q4：局部注意力的输出和稠密不一样，是不是写错了？**
不是。掩码改变了允许的连接，也就改变了模型计算的函数；notebook 明确说"输出差异应解释与评估，不能一律要求与稠密结果相等"。单元里只在窗口扩大到 `seq_len` 时才断言两者一致，另外用窗口 0 断言输出等于 `v`，这两个边界才是正确性检查。

**Q5：为什么 `masked_fill` 用 `-math.inf`，用 0 不行吗？**
Softmax 是 $e^{s_i}/\sum_j e^{s_j}$。被屏蔽位置若设 0，$e^0=1$，仍会分到不可忽略的概率；设 $-\infty$ 后 $e^{-\infty}=0$，才真正排除。notebook 原话是"仅把被屏蔽得分改成零，仍会留下非零概率"。

## 动手验证：怎么知道自己做对了
本节同样没有 `test_*` 函数，断言都写在五个代码单元里；notebook 的 dump 里没有保存任何输出，所以运行结果要以你自己的打印和断言为准。所有计算都在 CPU 上完成，不依赖 GPU；Q4 用 `math.isclose` 比较浮点，是为了避免 2.6 这类十进制小数在二进制里出现尾差。可以预期的关键检查是：

- Q1：`retained_position_report(balanced)["retained_positions"] == 4`，`balanced` 与 `clustered` 的 `density` 都等于 0.5，全 `True` 的 `removed_ratio` 为 0，全 `False` 的 `density` 为 0；非布尔或空序列抛 `ValueError`（由函数校验）。
- Q2：`regular["nonzero_counts"] == [2, 2]` 且 `pattern_matches` 为真；`irregular["nonzero_counts"] == [3, 1]` 且 `violating_groups == [0]`；全零序列也通过。
- Q3：4×4、保留 4 个时 `dense_weight_bytes == 32`、`coo_value_bytes == 8`、`coo_index_bytes == 32`、`coo_total_bytes == 40 > 32`；`dense_flops == 64`、`ideal_sparse_flops == 16`；保留 2 个时总字节 20、理想 8；保留 0 个时理想 0。
- Q4：复用 1 次平均 2.6 ms 且 `saved_ms_per_call < 0`；复用 10 次平均 0.8 ms 且节省为正；`dense_ms=1, sparse_ms=0.5, setup_ms=2, reuse_calls=4` 时节省恰好为 0。
- Q5：`dense_mask.sum() == 64`、`local_mask.sum() == 22`；稠密输出全为 3.5；第 0 个 batch、第 0 个 head 的 8 行输出（取第 0 个特征维）为 `[0.5, 1, 2, 3, 4, 5, 6, 6.5]`；窗口 0 的输出等于 `v`；窗口等于 `seq_len` 时等于稠密输出；局部输出全部有限；稠密 FLOPs 1024、理想局部 352。

运行后每个单元会打印保留数、密度、COO 载荷、平均耗时和连接数，例如 Q1 会打印"分散保留: 保留 4/8，密度 0.5"和"集中保留: 保留 4/8，密度 0.5"，Q3 会打印三行"保留 N 项：COO 载荷 … B，理想乘加 … FLOPs"；Q4 会打印"复用一次：平均 2.6 ms"和"复用十次：平均 0.8 ms"；Q5 会打印"每头连接：64→22；理想 QK/PV 工作量 1024→352 FLOPs"以及局部首位置输出 0.5、稠密输出 3.5。数值对不上时，先检查是不是把 (M,N,K) 的顺序、`value_bytes`/`index_bytes` 的默认值或窗口半径改掉了。另外别忘了函数的入参校验：`retained_weights` 必须落在 $[0, K \times N]$ 内，`m/n/k` 和字节数必须是正整数，越界同样会抛 `ValueError`。
