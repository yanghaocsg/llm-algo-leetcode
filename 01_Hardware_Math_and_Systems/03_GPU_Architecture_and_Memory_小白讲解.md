# 03. GPU 物理架构与内存层级 — 小白讲解

> 对应 notebook：[`03_GPU_Architecture_and_Memory.ipynb`](./03_GPU_Architecture_and_Memory.ipynb)

## 一句话总结
这节讲"GPU 算得快不等于模型跑得快"：峰值算力只是上限，数据要一级一级搬到计算单元，搬得慢、装不下都会让计算单元干等。几个纯算术的小计算器带你量三本账——计算量（FLOPs）、搬运量（Bytes）、工作集大小——再用"算术强度"和"屋顶线模型"判断一个算子更可能卡在计算、带宽还是容量上。

## 为什么需要它：痛点是什么
很多人以为换更强的 GPU 就一定更快，做优化时也不知道往哪儿使劲：是少算一点、少搬一点，还是少占一点显存？这三个方向的办法完全不同，用错了就是白忙。
类比：餐厅后厨。厨师（计算单元）手艺再快，食材（数据）都要从很远的冷库（全局显存）一份一份现取，他就只能站着等；把常用食材放到手边的操作台（寄存器、共享内存）才快得起来。但操作台很小，占用太多又会限制同时做几道菜。

## 核心问题
- 为什么 GPU 峰值算力提高后，Transformer 不一定同比例变快？架构名称、产品型号、计算能力（CC）能不能互换？
- 同一个矩阵乘，计算量和读写字节各怎么算？换了精度，什么变、什么不变？
- 算术强度和屋顶线模型怎么判断一个算子是"搬运受限"还是"计算受限"？
- 寄存器、共享内存、L2 缓存、全局显存各自管什么，会出什么问题？
- Attention 的工作集为什么随序列长度平方增长？显存分摊到多卡后，通信代价从哪里来？

## 解决思路：一步步看懂
1. **先分清是哪一种"慢"（Q1）。** 峰值算力只描述计算单元最快能完成多少运算，不表示数据已经及时送到。Transformer 由多个重复的计算模块组成，Attention 和 MLP 都会产生输入、权重、激活与中间结果；它们的读取、写回和复用跟不上，计算单元就等待。所以判断一个算子受什么限制，先问两件事：它要完成多少计算，要从内存搬运多少数据。notebook 的表把现象和候选约束对上：数据装不下 → 查显存容量（当前工作集、临时缓冲与可用容量）；数据搬得慢 → 查显存带宽或访存路径（实际搬运量、缓存命中与有效带宽）；计算做得慢 → 查计算吞吐（实际计算路径、吞吐与资源用量）。工作集（Working Set）就是当前阶段访问或暂时保留的数据集合。
   - 计算器 `estimate_transfer_times(bandwidths_gb_s, payload_bytes=1024**2)` 固定 1 MiB（$1024^2 = 1{,}048{,}576$ 字节），只改假设带宽：1000 GB/s 时要搬 $1{,}048{,}576 \div 10^{12}$ 秒，约 0.001 毫秒（约 1.05 微秒）；带宽翻到 2000 GB/s，时间减半。这是纯传输时间，不是单次内存访问的延迟；两个带宽只是给定场景，不绑定任何内存层级或 GPU 型号。`bytes_to_gb` 换算的是十进制 GB（除以 $10^9$）。
2. **架构名称、型号、计算能力是三回事。** 架构名称（如 Ampere、Hopper、Blackwell）描述一类硬件设计，产品型号指向具体设备，计算能力（Compute Capability，CC）标识 CUDA 硬件功能与指令特性。NVIDIA 的设备计算能力表把 A100 列为 CC 8.0、H100 为 9.0、B200 为 10.0、GeForce RTX 5070 Ti 为 12.0——CC 是能力分类，不是快慢分数。驱动支持的 CUDA 版本、PyTorch 构建用的 CUDA 版本、本机 Toolkit 版本是软件条件，也不是设备 CC。核对顺序：某条矩阵或搬运指令能否用，看 CC、指令要求和编译器支持，并保留回退实现；一个分块能否容纳，看线程、寄存器、共享内存限制；数据装不装得下、搬得够不够快，看产品的显存、带宽和访问方式；多卡怎么交换数据，看实际链路、主机拓扑与互连配置，不能从架构名称推断带宽。
3. **矩阵乘的账：计算量和读写字节分开记（Q2）。** CUDA Core 负责通用的线程级计算；Tensor Core 是专门提高矩阵乘加吞吐的计算单元，支持的数据类型、累加方式和块形状随设备与实现变化。FP32 输入也可能按 TF32 模式计算——TF32 是计算精度模式，输入仍以 FP32 存储，所以输入 dtype、内部计算精度和实际指令要分别核对。Tensor Core 只覆盖矩阵乘加这一段，数据准备、布局转换、Softmax 和结果写回还要别的单元配合。
   - 例：2×4 的左矩阵乘 4×3 的右矩阵。输出 2×3 共 6 个元素，每个元素是 4 次乘加、每次 2 次运算，共 $6 \times 4 \times 2 = 48$ FLOPs；输入 $8 + 12 = 20$ 个元素，加上输出共 26 个，输入各读一次、输出写一次：BF16（2 字节）是 52 B，FP32（4 字节）是 104 B。计算量没变，搬运字节变了一倍。
   - `estimate_matmul_workload(m, n, k, dtype)` 就是这三行算术：`flops = 2 * m * n * k`，输入元素 `m * k + k * n`，`minimum_io_bytes` =（输入 + 输出元素）× 每元素字节数（fp8 为 1，fp16/bf16 为 2，fp32 为 4）。扩大到 1024×1024×4096，按公式是 8,589,934,592 FLOPs，最低读写 bf16 为 18,874,368 B、fp32 为 37,748,736 B。
   - 执行分组：SM（流式多处理器）调度线程块并组织片上计算资源，Warp（线程束）以一组线程为单位执行指令。SM 占用率（Occupancy）是驻留线程束数相对设备上限的比例，受寄存器与共享内存需求影响，不等于吞吐。
4. **内存层级与屋顶线（Q3）。** 寄存器保存线程正在用的临时值；共享内存供线程块内复用数据；L2 缓存缓冲多个 SM 对全局数据的访问；全局显存容纳权重、激活和大部分状态。各自的典型风险：寄存器溢出（临时值转入本地内存，资源过多还会限制驻留）、共享内存的存储体冲突（访问要分批服务）、L2 命中不足时反复访问显存、显存数据供给过慢或工作集装不下。HBM 和 GDDR 是显存技术，SRAM 是片上缓存和共享存储的技术，它们不是与寄存器、缓存并列的层级。同一个 Warp 的相邻线程读连续地址更容易合并访问，跨度过大可能增加内存事务。
   - 算术强度 $\text{AI} = \text{FLOPs} / \text{Bytes}$，即每搬一个字节完成多少浮点运算。强度低时数据供给更可能限制吞吐，强度高时才轮到计算上限说话。`roofline_estimate(flops, bytes_moved, peak_compute_tflops, memory_bandwidth_gb_s)` 先算带宽屋顶 $\text{AI} \times \text{带宽} / 1000$（单位 TFLOP/s），上界取它与计算峰值中较小的一个，并把瓶颈标成 `memory`、`compute` 或 `balance`。
   - 手算：固定 300 TFLOP/s 与 1500 GB/s，交点是 $300 \times 1000 \div 1500 = 200$ FLOP/B。`low_intensity`（2×10⁶ FLOPs、10⁶ 字节）强度为 2，带宽屋顶 $2 \times 1500 \div 1000 = 3$ TFLOP/s，卡在搬运；`at_balance`（2×10¹⁰ FLOPs、10⁸ 字节）强度正好 200，两道屋顶相交；`high_intensity`（2×10¹² FLOPs、10⁸ 字节）强度 20000，带宽屋顶远高于峰值，上界是 300 TFLOP/s，卡在计算。
5. **Attention 的工作集（Q4）。** 标准多头注意力（MHA）里，Q、K、V 分别是查询、键、值，单头的 score 矩阵保存每对查询与键的分数。序列长度为 $N$ 时每头要 $N \times N$ 个分数：长度翻倍，分数矩阵变四倍，而头数、头维固定时 Q/K/V 和输出只翻倍。`calculate_attention_vram(seq_len, num_heads, head_dim, dtype_bytes=2, batch_size=1)` 的账：QKV 是 $3 \times N \times H \times D \times$ 字节数，分数矩阵是 $H \times N^2 \times$ 字节数，输出是 $N \times H \times D \times$ 字节数，两次矩阵乘（QK 和 PV）共 $4 \times H \times N^2 \times D$ FLOPs，$H$ 是头数、$D$ 是头维。小例子 $N=4$、2 头、头维 3、每元素 2 字节：QKV 144 B，分数矩阵 64 B，输出 48 B，合计 256 B，FLOPs 384。
   - 分块对照：`tile_bytes(block_size=128)` 得 128² × 2 = 32,768 字节，即 32 KiB 的分数块；`compare_attention_working_set` 的网格按行、列分别向上取整，$N=100$、块 32 时是 (4, 4) 共 16 块。按公式，$N=2048$ 时单头 score 是 8 MiB、网格 (16, 16)，$N=4096$ 时是 32 MiB、网格 (32, 32)。MiB/KiB 按 1024 进位，GB 按十进制。注意分数块只是分块注意力临时状态的一部分，分数矩阵的存储大小也不作为 Roofline 的搬运分母。
6. **跨卡分摊的通信代价（扩展 Q5）。** 显存分摊不消除成本，而是把一部分成本转移到通信带宽、通信延迟和同步等待。PCIe 连接 GPU 与 CPU、GPU 与 GPU，带宽和延迟受主机拓扑影响；NVLink 是节点内 GPU 间的高速互连；NVSwitch 让多 GPU 系统的互连更均匀；All-Reduce / All-Gather 用来聚合或交换参数、梯度或激活。`pcie_vs_nvlink(payload_mb, pcie_gb_s, nvlink_gb_s, communication_rounds=1, sync_overhead_ms=0.0)`：单轮时间 = 传输量（MB）÷ 带宽（GB/s），单位恰好是毫秒；多轮 =（单轮 + 每轮同步开销）× 轮数。给定 64 MB、PCIe 16 GB/s、NVLink 64 GB/s：单轮 4 ms 对 1 ms；4 轮、每轮同步 0.05 ms 时是 $(4 + 0.05) \times 4 = 16.2$ ms 对 $(1 + 0.05) \times 4 = 4.2$ ms。这些带宽只是给定场景，不对应固定型号或单链路规格。

## 关键概念速查表
| 术语 | 大白话解释 |
|---|---|
| 峰值算力 | 计算单元最快能做多少运算，不代表数据能及时送到 |
| 工作集（Working Set） | 当前阶段访问或暂时保留的数据集合 |
| 架构名称 / 型号 / CC | 一类硬件设计 / 具体设备 / CUDA 硬件功能等级（不是快慢分数） |
| SM / Warp | 流式多处理器，调度线程块 / 线程束，一组线程一起执行指令 |
| CUDA Core / Tensor Core | 通用线程级计算单元 / 专门做矩阵乘加的单元 |
| TF32 | FP32 输入走较低精度计算的模式，存储仍是 FP32 |
| 占用率（Occupancy） | 驻留线程束数占设备上限的比例，不等于吞吐 |
| 算术强度 | FLOPs ÷ Bytes，每搬一个字节做多少计算 |
| 屋顶线（Roofline） | min(计算峰值, 算术强度 × 带宽) 给出的吞吐上界 |
| 寄存器 / 共享内存 / L2 / 全局显存 | 线程临时值 / 线程块内复用 / 多 SM 共用的缓冲 / 放权重和激活的大显存 |
| 寄存器溢出 / 存储体冲突 | 临时值被迫转到本地内存 / 共享内存访问被迫分批 |
| PCIe / NVLink / NVSwitch | 通用总线 / 节点内 GPU 高速互连 / 多卡间更均匀的互连 |

## 小白常见疑问
**Q1：CC 12.0 比 CC 10.0 大，是不是说消费级显卡比 B200 更快？**
不是。CC 是能力分类，标识的是硬件功能与指令特性，不是快慢分数；同一 CC 也不意味着显存容量、SM 数量、带宽与互连配置相同。

**Q2：矩阵乘能走 Tensor Core，整个 Transformer 模块就会同样比例加速吗？**
不会。Tensor Core 只覆盖矩阵乘加这一段，数据准备、布局转换、Softmax 和结果写回仍要其他执行单元和内存层级配合。

**Q3：换成 BF16，矩阵乘的计算量会变小吗？**
不会。2×4 乘 4×3 的例子里 BF16 和 FP32 都是 48 FLOPs，变的是最低读写字节：52 B 对 104 B。

**Q4：分数矩阵占 32 MiB，能直接拿它当 Roofline 里的 Bytes 吗？**
不能。notebook 明确说分数矩阵的存储大小不作为 Roofline 的搬运分母，完整模型峰值和实际搬运量要单独记录。"占多大地方"和"要搬多少次"是两本账。

**Q5：把显存分摊到多张卡上，成本就消失了吗？**
没有消失，只是换了个地方。成本转到了通信带宽、通信延迟和同步等待上；分摊后若需要频繁 All-Reduce、All-Gather 或状态同步，通信就可能成为新瓶颈。
