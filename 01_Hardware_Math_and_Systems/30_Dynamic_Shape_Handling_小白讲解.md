# 30. 动态 Shape 处理 — 小白讲解

> 对应 notebook：[`30_Dynamic_Shape_Handling.ipynb`](./30_Dynamic_Shape_Handling.ipynb)

## 一句话总结
本节用三个纯 Python 计算器拆开"输入形状一变就变慢"这件事：`shape_reuse_report` 按完整形状元组统计精确缓存命中率；`padding_overhead` 比较"直接补到本批最大长度"和"按桶边界补齐"各浪费多少 Token 位置；`path_stability` 按 256、1024 两个阈值把输入分到短/中/长三条运行分支，并数相邻切换次数。三问分别对应形状复用、填充浪费和运行路径，notebook 还专门区分了"版本适用条件不满足、重新编译、图中断"三种常被混为一谈的现象。

## 为什么需要它：痛点是什么
同一个模型、同一段代码，batch 从 8 改成 9、序列长度从 512 改成 513，耗时可能突然跳一下；日志里出现"recompile"或"graph break"，却不知道是哪一种。初学者常见的误解有三个：以为"形状不同就一定要重新编译"；以为"把输入统一补到 2048 最省事"；以为"运行分支切换得多，就说明重编译多"。这三个判断都缺少中间账目：到底有多少种形状键、每个请求命中不命中、补出来的位置有多少是白算的、分支到底换了几次。举个具体场景：服务同时收到 batch 8、序列 512 和 batch 8、序列 513 的请求，精确形状缓存会把它们当成两种键；如果统一补到 2048，形状键是少了，但 513 那条要多算 1535 个位置，512 那条要多算 1536 个。省下的版本数和多算的 Token 数是两笔账，得分开记。

生活类比：服装厂做版。每个顾客的尺寸都单独打一版，版房会被版本淹没；改成 S/M/L 三个码，版少了，但 M 码的人可能穿得偏大，布料浪费；码分得太粗（全都做成 XL），浪费更多。分桶就是"定几个码"，填充就是"把衣服放宽到码数"，而"换了码"不等于"重新打版"——三个码的版可能早就有了。

## 核心问题
- 精确形状缓存的命中率怎么算？为什么形状种类决定命中？
- 分桶什么时候减少填充、什么时候反而比不补更浪费？
- 输入长度怎样改变运行分支？分支切换和重新编译是一回事吗？
- 版本适用条件（guard）不满足、重新编译、图中断，三者该如何区分？
- 这些数字能说明什么、不能说明什么？

## 解决思路：一步步看懂

**第 1 步：Q1——精确形状键的命中率。** 最简单的缓存模型是：键就是完整形状元组，比如 `(8, 512)`；每种形状第一次出现时不命中，之后出现时命中；缓存不淘汰。`shape_reuse_report(shapes)` 的算法只有三行核心：

```python
normalized = [tuple(shape) for shape in shapes]
keys = len(set(normalized))
hits = len(normalized) - keys
```

不同形状的个数是 `keys`，总请求数是 `len(normalized)`，所以命中次数等于"总数减去不同键数"（每种键的第一次不算命中），命中率再除以总数。函数先把列表形式的形状统一转成元组，因为列表不可哈希、不能放进集合；然后校验每个形状非空、每一维都是正整数。

三组探针的结果值得逐一算：

- `fixed = [(8, 512)] * 4`：4 次请求只有 1 种键，命中 3 次，命中率 $3/4 = 0.75$；单元断言整个字典等于 `{"requests": 4, "distinct_shape_keys": 1, "assumed_exact_shape_hits": 3, "exact_shape_hit_ratio": 0.75}`。
- `mixed = [(8, 128), (8, 512), (8, 128), (8, 2048)]`：3 种键，只有第二个 `(8, 128)` 命中，命中 1 次，命中率 0.25。
- `unique`：四种形状全不同，命中 0 次，命中率 0。

单个请求的命中率是 0，因为第一次出现永远不命中；把 `[8, 128]` 和 `(8, 128)` 混在一起时仍然算同一种键，提示形状的"写法"不影响哈希，值才影响。

但这个模型有明确的边界：它**假设缓存永不淘汰**。真实缓存未必永不淘汰，形状种类太多时可能挤掉旧版本，命中率也可能比这个模型更低。notebook 用"assumed_exact_shape_hits"这样的字段名，就是在提醒这是假设值，不是实测的编译节省。

比"精确形状键"更宽松的机制是**版本适用条件**（guard）：复用某个已编译版本前，系统核对形状、步长、类型以及相关程序状态。notebook 举了一个构造例子：某个版本允许"连续 FP32 输入、序列长度 128 到 256"，那么 128 和 192 都满足；但如果布局改成非连续，即使长度仍是 128，也可能不再适用。这里的范围是**假设**，不是本机编译器采集到的真实 guard。

这也解释了为什么真实系统不必为每个长度都生成一个版本：形状可以用符号加约束来表达，比如"序列长度 $s_0$ 在 128 到 256 之间、且步长为 1"，一个版本覆盖一段区间。代价是区间越宽，编译器能做的静态优化越少（它不知道具体长度，只能按上界预留或加运行时判断）；区间越窄，版本越多、缓存越容易满。精确形状键是"每个长度一版"的极端，符号约束是"一段长度一版"的折中，两者不是谁替代谁，而是不同的缓存粒度。

**第 2 步：Q2——填充与分桶的账。** `padding_overhead(lengths, bucket_boundaries=None)` 有两条规则：不给桶边界时，每条输入补到本批最大长度；给了边界时，先对边界去重排序，再让每条输入补到"能容纳它的最小边界"。函数还要求最大边界不小于最长输入，否则报错"最大桶边界须覆盖全部输入长度"——因为规则是"补到能容纳它的最小边界"，如果没有任何边界能容纳最长输入，这条输入就没有补齐目标，账目也就无从计算。返回值里 `useful_tokens` 是原始长度之和，`total_tokens` 是补齐后的位置数，`wasted_tokens` 是两者之差，`padding_ratio` 是浪费数除以**补齐后的总位置数**——分母不是有效 Token 数，因为问题问的是"实际执行的位置里有多大比例是白算的"。

先看主图那组 `[65, 66]`：

- 直接补齐：两条都补到 66，总位置 $66 \times 2 = 132$，有效 131，浪费 1，比例 $1/132 \approx 0.76\%$；
- 补到桶 128：两条都到 128，总位置 256，浪费 $256 - 131 = 125$，比例 $125/256 \approx 48.8\%$。

只差一个 Token 的两条输入，被一个过宽的桶硬生生补出 125 个空位。这就是"分桶不一定省"的最直观例子：桶边界离输入太远时，分桶比"按本批最大长度补齐"浪费得多。

再看多长度那组 `[64, 128, 256, 520, 800]`，有效总数 $64+128+256+520+800 = 1768$：

- 不分桶：全部补到 800，总位置 $800 \times 5 = 4000$，浪费 $4000 - 1768 = 2232$，比例 $2232/4000 = 55.8\%$；
- 桶边界 `[128, 256, 512, 1024]`：64→128、128→128、256→256、520→1024、800→1024，总位置 $128+128+256+1024+1024 = 2560$，浪费 $2560 - 1768 = 792$，比例 $792/2560 = 30.94\%$。

这一组里分桶明显更好，因为它把 520 和 800 归到 1024，而不是让所有输入都陪 800 或 1024 走。两个例子合起来说明：分桶的收益取决于**边界是否贴近真实长度分布**，不是一个"分了就赚"的操作。

桶边界越细，填充越少，但形状种类越多。用同一组输入再加一个 64 边界 `[64, 128, 256, 512, 1024]` 手算：64→64，其余不变，总位置从 2560 降到 $64+128+256+1024+1024 = 2496$，浪费从 792 降到 728。少的 64 个位置，是拿"多一个桶"换来的；如果桶多到接近输入种类数，分桶就退化回了"每种长度一个形状"，缓存收益也随之消失。notebook 只给了 `[128, 256, 512, 1024]` 这一组，是为了让账目简单，不是推荐这组边界。

还要注意 notebook 固定的规则是"提供边界时补到所属桶上限"，但现实系统也可以"归入同一桶后，再按当前批次的最大长度补齐"——那样桶只负责分组，不负责补齐。分桶能帮助组批，但等待同桶的其他请求也会增加排队时间，这部分本节没有计算；而且"较少的规则形状有机会复用已有实现"只是机会，不是保证。

**第 3 步：Q3——运行分支与切换次数。** `path_stability(lengths, boundaries=(256, 1024))` 的路由规则是：

```python
if length < boundaries[0]:   return "short"
if length < boundaries[1]:   return "medium"
return "long"
```

小于 256 进短分支，256 到 1023 进中分支，1024 及以上进长分支。然后数相邻两个输入的分支是否变化：

```python
transitions = sum(left != right for left, right in zip(paths, paths[1:]))
```

三组结果：`[128, 128, 128]` 全是 `short`，切换 0 次；`[128, 512, 128, 2048]` 是 `short, medium, short, long`，3 种分支、切换 3 次；边界探针 `[255, 256, 1023, 1024]` 是 `short, medium, medium, long`，切换 2 次——255 和 256 之间跨了第一道阈值，1023 和 1024 之间跨了第二道，中间的 256 和 1023 同属中分支。单元还断言单个 `[256]` 的切换次数为 0。

这里的 256 和 1024 是本节自己定的阈值，不是硬件常数；真实系统怎么选阈值不在本节的范围内。它们的作用只是把连续长度切成三段，好让"切换"这件事可以被计数。

关键在"怎么读这个数"：**分支切换 ≠ 重新编译**。如果短、中、长三个分支的实现都已经编译好，请求在它们之间来回跳，只是换了一份现成的执行路径；反过来，一直待在同一个分支，也可能因为 dtype、步长或程序状态变化触发新的 guard 检查。notebook 的原话是"运行时选分支与编译时生成版本是两项动作"。

同理，**图中断**（graph break）也不能从分支次数推断。它发生在捕获过程中，表示当前配置无法把某段程序继续纳入同一个捕获区域；允许分段时，可捕获的部分可能分别编译，其余部分继续普通执行。`fullgraph=True` 要求本次捕获不发生图中断，遇到不支持的捕获会报错，但成功捕获的图**仍可包含多个设备内核和库调用**——它不是"一个 GPU kernel"的保证。

**第 4 步：三种现象的区分表。** notebook 用一张表把最容易混淆的三件事拆开：

| 观察 | 发生了什么 | 还不能据此判断什么 |
| --- | --- | --- |
| 版本适用条件不满足 | 一个已有版本的 guard 不满足 | 不代表所有缓存版本都不可用，也不一定重新生成代码 |
| 重新编译 | 为变化后的程序或输入条件准备另一版本 | 不等于所有底层产物都冷编译，也不保证更快 |
| 图中断 | 捕获无法继续跨越某段程序 | 不等于形状缓存未命中；允许分段与要求整图的模式处理不同 |

三者共同的读法是：先看观察点属于哪一层，再去找对应的诊断记录，而不是用一个计数器解释所有现象。具体说，左列是你能观察到的事件，右列是它**不足以**推出的结论。比如看到 guard 不满足，正确的下一步是查还有没有别的缓存版本，而不是直接宣布"要重编译了"；看到一次重新编译，也不代表整个后端从零开始，底层编译仍可能复用已有缓存。

把三种情况的处理路径写出来会更清楚。guard 不满足时，系统可以先找其他已缓存版本；都找不到，才可能重新捕获或编译；超过限制或不支持时还可能回退到普通执行或直接报错，取决于配置。重新编译时，底层编译仍可能命中自己的缓存，所以"重新编译"不等于"所有产物都冷启动"，更不保证变快。图中断发生在捕获阶段，允许分段时图会被切成几段分别编译、其余部分普通执行；`fullgraph=True` 时则直接报错。三件事的观察点、处理方式、后果都不同，不能用同一个计数器代替。

**第 5 步：把三问当成三组对照实验。** Q1 的自变量是"请求的形状序列"（`fixed`、`mixed`、`unique` 三组），因变量是形状键数和命中率，控制变量是"缓存不淘汰、键只含形状"；Q2 的自变量是"是否给桶边界、边界有多粗"，因变量是浪费位置数和填充比例，控制变量是同一组长度、同一套"补到最小覆盖边界"的规则；Q3 的自变量是"输入长度序列"，因变量是分支序列和相邻切换次数，控制变量是两个阈值。三组实验的因变量里都没有时间，所以它们都不能回答"快了多少"——能回答的是"形状重复多少、白算多少、路径切换多少"。这也是读任何 benchmark 时该先确认的事：自变量、因变量、控制变量分别是什么。

`unique_paths` 和 `path_transitions` 是两个不同的量：前者数"出现过几种分支"，后者数"相邻换了多少次"。`[128, 512, 128, 2048]` 有 3 种分支、切换 3 次；`[128, 512, 2048, 128]` 也有 3 种、切换 3 次；而 `[128, 512, 512, 128]` 只有 2 种分支，却切换 2 次。判断"路径是否稳定"要看切换次数，判断"覆盖了几条路径"要看种类数，两者不能互相替代。

`path_stability` 对 `boundaries` 的校验也值得看一眼：必须是两个严格递增的正整数，`(256, 1024)` 可以，`(1024, 256)` 或 `(256, 256)` 会报错。这保证 `route` 里的两个 `<` 判断不会出现空区间或重叠区间，每个长度都恰好落进一个分支。

**第 6 步：这些数字的适用范围。** 三个计算器分别只回答一个问题：形状键的重复比例、填充位置的多少、分支切换的次数。它们都没有调用编译器，也没有测时间。notebook 结尾说"解释真实波动时，需要把同一次调用的输入元信息、版本适用条件／重编译诊断、实际执行与时间样本对应起来；首次准备和预热也应与稳态耗时分开"，意思是：这些是**做实验前的账目**，用来提出假设和设计对照，不是性能结论。另外，首次准备（编译、捕获、分配工作区）和稳态耗时要分开统计；把第一次请求的冷启动混进平均值，会把一次性的准备成本误当成每次成本，notebook 说的"首次准备和预热也应与稳态耗时分开"就是这个意思。真正的证据要来自 `torch.compile` 之类的诊断输出和固定 workload 的重复计时。

## 关键概念速查表
| 术语 | 大白话解释 |
| --- | --- |
| 动态形状 | 运行时 batch 大小、序列长度等维度不固定 |
| 精确形状缓存 | 以完整形状元组为键缓存编译结果，形状完全一样才命中 |
| 形状键（shape key） | 用来查缓存的完整形状，如 `(8, 512)` |
| 版本适用条件（guard） | 复用已编译版本前要满足的形状、步长、类型等条件 |
| 重新编译 | 为新的程序或输入条件准备另一个版本 |
| 图中断（graph break） | 捕获过程无法继续跨越某段程序，图被切开 |
| 分桶（bucketing） | 按预设长度边界给输入归类，减少形状种类 |
| 填充（padding） | 补占位位置把序列凑到目标长度 |
| 填充比例 | 浪费位置数 ÷ 补齐后的总位置数 |
| 组批（batching） | 决定哪些请求一起执行 |
| 运行分支 | 按长度阈值选择 short/medium/long 三条执行路径之一 |
| `fullgraph=True` | 要求整段程序一次捕获、不允许图中断的模式 |

## 小白常见疑问

**Q1：`fixed` 那组命中率 0.75，是不是说明 75% 的请求不用编译？**
不是。它是"精确形状键、缓存不淘汰"这个假设模型下的命中比例，只能说明 4 次请求里有 3 次能查到同一种键。真实的编译缓存有容量和淘汰策略，底层编译也可能复用；这个数不等于编译时间节省，更不能换算成加速比。

**Q2：分桶不是应该更省吗？为什么 `[65, 66]` 补到 128 反而浪费 125 个位置？`padding_ratio` 的分母又是什么？**
因为桶边界 128 离输入太远。不分桶时只补到本批最大长度 66，浪费 1；补到 128 等于给两条都加了 62 个空位。分桶省的是"形状种类"，不是"填充位置"；边界过宽时两者会打架。分桶只是分组手段，不是省填充的保证。`padding_ratio` 的分母是**补齐后的总位置数**，因为问题问的是"实际要执行的位置里，有多大比例是白算的"；用有效 Token 作分母会得到"浪费/有效"的另一个指标，口径不同。另外，桶边界可以乱序或重复，函数内部做了 `sorted(set(bucket_boundaries))`，所以 `[256, 128, 128]` 和 `[128, 256]` 等价，单元里就断言了 `padding_overhead(lengths=[65, 66], bucket_boundaries=[256, 128, 128]) == coarse`。

**Q3：`path_transitions` 大，是不是说明重编译多、性能差？形状键里为什么没有 dtype 和 stride？**
第一个不能这么推：分支切换只说明输入长度在阈值两侧跳；如果三条分支都已编译好，切换只是选路。反过来，切换为 0 也可能因为 dtype 或步长变化触发 guard。要判断有没有重编译，得去看编译器的诊断记录，而不是只盯着这个计数器。第二个是本节的有意简化：`shape_reuse_report` 只用形状做键，真实 guard 还会核对步长、类型和程序状态，所以两个形状完全相同、但一个连续一个非连续的输入，可能一个命中、一个不命中。notebook 用"改成非连续布局，即使长度仍是 128，也可能不再适用"提醒过这一点。

**Q4：`fullgraph=True` 成功了，是不是就只有一个 kernel？**
不是。notebook 明确说：成功捕获的图仍可包含多个设备内核与库调用。`fullgraph` 约束的是"捕获过程中不许图中断"，不是"融合成一个 kernel"。

## 动手验证：怎么知道自己做对了
本节没有 `test_*` 函数，三个代码单元各自 assert 后 print；dump 里没有保存输出，以运行时是否抛 `AssertionError` 为准。关键断点是：

- Q1：`fixed` 的完整字典必须等于 `{"requests": 4, "distinct_shape_keys": 1, "assumed_exact_shape_hits": 3, "exact_shape_hit_ratio": 0.75}`；`mixed` 的 `distinct_shape_keys == 3`、命中 1；`unique` 命中 0；单请求命中率为 0；`[[8, 128], (8, 128)]` 命中 1（列表和元组归一化后同键）。
- Q2：`direct` 必须等于 `{"useful_tokens": 131, "wasted_tokens": 1, "total_tokens": 132, "padding_ratio": 1/132}`；`[65, 66]` 配桶 128 时浪费 125、总数 256；多长度不分桶浪费 2232，分桶浪费 792，两者有效数都是 1768；`[128]` 配桶 128 浪费 0；乱序重复边界 `[256, 128, 128]` 与 `[128]` 的结果一致。
- Q3：`[128, 128, 128]` 的 `same_runtime_branch` 为真、切换 0；混合序列路径为 `["short", "medium", "short", "long"]`、3 种、切换 3；边界序列 `["short", "medium", "medium", "long"]`、切换 2；单元素切换 0。

运行后会打印每种输入的请求数、形状键数、命中数，以及每种补齐方式的有效/填充/总位置和百分比。打印用的是 `:.2%` 格式，所以看到的是 `0.76%`、`48.83%`、`30.94%` 这样的百分数，不是小数。另外，命中率的分母是请求数而不是形状种类数；切换次数是相邻两个输入比较，不是每个输入都和第一个比较。如果数字对不上，先检查是不是把 `(batch, seq)` 的顺序写反、桶边界没覆盖最长输入，或者把 `< 256` 误写成了 `<= 256`——255/256 那组断言就是专门抓这个边界错误的。
