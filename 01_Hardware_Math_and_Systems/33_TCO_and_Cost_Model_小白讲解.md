# 33. 算力评估与 TCO 模型 — 小白讲解

> 对应 notebook：[`33_TCO_and_Cost_Model.ipynb`](./33_TCO_and_Cost_Model.ipynb)

## 一句话总结
本节用两个构造候选 A、B 走完一条完整的成本链：`tco_ledger` 先把采购、电费、运维按 24 个月、每月 30 天、全程通电算成基础账（A 41930.42，B 39440.90）；`migration_cost` 再加入工程工时与回滚风险的期望损失（A 16500，B 21000），排序立刻反转（A 58430.42，B 60440.90）；`cost_per_million_successful_requests` 除以各自繁忙小时内的成功请求数（A 约 844.96 百万，B 约 714.84 百万），得到每百万成功请求 69.15 与 84.55。最后 `effective_cost_per_used_hour` 演示全额采购与 36 个月直线分摊为什么给出不同的每繁忙小时成本。

## 为什么需要它：痛点是什么
初学者比较两台设备，最容易只盯采购价：22000 比 30000 便宜，就选 B。可真正决定单位请求成本的不止这一项：B 的功率更高、运维更贵、可用率更低，迁移时回滚概率也更大；这些因素会让"便宜 8000"在持有期内被慢慢吃掉。另一个常见错误是把"设备通电时间"和"真正干活的时间"混为一谈，或者把可用时间内的繁忙比例当成 GPU 硬件利用率。

生活类比：买打印机。机器便宜的那台，墨盒贵、故障率高、维修要停机；如果只按购机价选，打印到一定页数后总花费反而更高。TCO（Total Cost of Ownership，总拥有成本）就是把购机、耗材、维修、停机和迁移都摊到"成功打印的页数"上，再比较每页成本。

本节所有价格、功率、比例都是构造输入，货币单位统一但不指定具体币种。notebook 反复强调：只有候选完成相同的计算和质量要求、在同一持有期内比较，单位成本才有意义。

## 核心问题
- 采购、电费、运维、迁移四类成本怎样组成一份可核对的 TCO 账本？
- 可用率（availability）和利用率（utilization）有什么区别？为什么 720 小时会拆成 180 繁忙 + 540 空闲？
- 迁移工时和回滚风险怎样折算成一次性成本？为什么它能让 A、B 的排序反转？
- 每百万成功请求的分母由哪些因子相乘？请求率、可用率、利用率怎样避免重复计算？
- 全额采购与折旧分摊为什么会给出不同的每小时成本？利用率减半时为什么成本恰好翻倍？

## 解决思路：一步步看懂

### 第 1 步：Q1 `tco_ledger`——先算时间，再算能量，最后汇总金额
函数签名把成本拆得很清楚：

```python
def tco_ledger(purchase_cost, power_kw, electricity_per_kwh,
               ops_cost_per_month, migration_cost, months,
               utilization, idle_power_kw=0.0, availability=1.0):
```

输入先做一轮校验：所有金额、功率、月份、比例必须是有限非负实数；`months > 0`；`utilization` 和 `availability` 不超过 1；`idle_power_kw <= power_kw`（空闲功率不能比繁忙功率还高）。然后按下面的顺序展开时间：

```python
powered_hours = months * 30 * 24          # 每月固定 30 天，全期通电
available_hours = powered_hours * availability
busy_hours = available_hours * utilization
idle_hours = powered_hours - busy_hours    # 不可服务 + 可服务但空闲
```

这里有两个关键定义。第一，`availability` 是"能提供服务的时间占日历时间的比例"，`utilization` 是"可用时间内的繁忙比例"，两者相乘才是真正干活的 `busy_hours`。第二，`idle_hours` 用总通电小时减去繁忙小时，所以它同时包含"设备坏了不能服务"和"能服务但没任务"两段；这两段都按 `idle_power_kw` 计费。

能量与成本：

$$\text{energy(kWh)}=\text{power\_kw}\times\text{busy\_hours}+\text{idle\_power\_kw}\times\text{idle\_hours}$$

```python
energy_kwh = power_kw * busy_hours + idle_power_kw * idle_hours
components = {
    "purchase_cost": purchase_cost,
    "energy_cost": energy_kwh * electricity_per_kwh,
    "operations_cost": ops_cost_per_month * months,
    "migration_cost": migration_cost,
}
```

用 notebook 的一月小例子核对：`power_kw=1`、`electricity_per_kwh=1`、`months=1`、`utilization=0.5`、`idle_power_kw=0.1`、`availability=0.5`。通电 $30\times24=720$ 小时，可用 $720\times0.5=360$ 小时，繁忙 $360\times0.5=180$ 小时，空闲 $720-180=540$ 小时；耗电 $1\times180+0.1\times540=180+54=234$ kWh。断言正是 `busy_hours == 180`、`idle_hours == 540`、`energy_kwh == 234`。

把每个输入单独拎出来看，会更容易记住它们的作用方向：

- `purchase_cost` 只进 `components["purchase_cost"]`，与时间无关，是一次性支出。
- `power_kw` 只乘 `busy_hours`。利用率越高、可用率越高，这段越长，电费越高。
- `idle_power_kw` 乘 `idle_hours`，而 `idle_hours` 同时包含"不可服务"和"可服务但没任务"两部分。可用率下降会把时间从繁忙推向空闲，所以它既减少繁忙电费，又增加空闲电费，净效果取决于两种功率的差。
- `ops_cost_per_month` 直接乘 `months`，不管设备忙不忙都要付。
- `availability` 和 `utilization` 都不直接进金额，而是先改变小时数。前者影响"可用/不可用"的切分，后者影响"可用时间内忙/闲"的切分。

这也是为什么 A、B 的对比不能只看采购价：B 的可用率 0.96 比 A 的 0.99 低，意味着 691.2 小时不可服务，而这段时间仍按空闲功率计费；B 的空闲功率又更高，两个因素叠加，电费自然高。

再看 A、B 的 24 个月基础账目（此时 `migration_cost=0`）：

| 项目 | A | B |
|:---|---:|---:|
| 采购 | 30000 | 22000 |
| 功率 / 空闲功率 | 0.7 / 0.1 kW | 0.9 / 0.15 kW |
| 电价 | 0.8 /kWh | 0.8 /kWh |
| 每月运维 | 200 | 350 |
| 可用率 / 利用率 | 0.99 / 0.7 | 0.96 / 0.7 |
| 通电小时 | 17280 | 17280 |
| 可用小时 | 17107.2 | 16588.8 |
| 繁忙小时 | 11975.04 | 11612.16 |
| 空闲小时 | 5304.96 | 5667.84 |
| 耗电 | 8913.024 kWh | 11301.12 kWh |
| 电费 | 7130.4192 | 9040.896 |
| 运维合计 | 4800 | 8400 |
| **基础总成本** | **41930.4192** | **39440.896** |

逐项验算 A：$0.7\times11975.04+0.1\times5304.96=8382.528+530.496=8913.024$ kWh；电费 $8913.024\times0.8=7130.4192$；运维 $200\times24=4800$；总计 $30000+7130.4192+4800=41930.4192$。B 同理：$0.9\times11612.16+0.15\times5667.84=10450.944+850.176=11301.12$ kWh，电费 9040.896，运维 8400，总计 39440.896。此时 B 比 A 便宜约 2490。

B 明明采购价低 8000，为什么基础账只领先约 2490？因为另外三项在往回吃：B 的功率更高（0.9 对 0.7 kW）、空闲功率更高（0.15 对 0.1 kW），而且可用率更低（0.96 对 0.99），导致不可服务的 691.2 小时也按空闲功率计费。A 的不可服务时间是 $17280\times(1-0.99)=172.8$ 小时，B 是 $17280\times(1-0.96)=691.2$ 小时，多了 518.4 小时。B 的耗电比 A 多 $11301.12-8913.024=2388.096$ kWh，电费多 1910.4768；运维又多 $350\times24-200\times24=3600$。所以采购省下的 8000 被电费和运维吃掉约 5510，只剩约 2490 的优势。

这张表还可以用来检查"繁忙小时"是否算对：A 的繁忙占比是 $0.99\times0.7=0.693$，B 是 $0.96\times0.7=0.672$；乘 17280 小时后分别是 11975.04 和 11612.16。可用率和利用率是串联的，不能把 0.99 和 0.7 相加，也不能只乘其中一个。

### 第 2 步：Q2 `migration_cost`——把工时和风险折算成一次性成本
迁移不是免费的：要改编译器、内核或部署流程，要做数值与性能回归。函数只算两块：

```python
labor_cost = (engineering_hours + validation_hours) * hourly_rate
expected_rollback_cost = downtime_hours * downtime_cost_per_hour * rollback_probability
return {"labor_cost": ..., "expected_rollback_cost": ..., "total_cost": ...}
```

notebook 的构造输入是工程 120 小时、验证 40 小时、每小时 100，所以工时费 $(120+40)\times100=16000$；回滚停机 2 小时、每小时损失 5000。A 的回滚概率 0.05，期望损失 $2\times5000\times0.05=500$，总迁移成本 16500；B 的概率 0.5，期望损失 $2\times5000\times0.5=5000$，总迁移成本 21000。

把迁移成本接回 Q1 的账本：

- A：$41930.4192+16500=58430.4192$
- B：$39440.896+21000=60440.896$

排序反转了：基础账 B 更便宜，加入迁移风险后 A 反而便宜约 2010。注意 `expected_rollback_cost` 是"一次迁移事件的条件期望"，不是每月重复发生的费用；迁移完成后运行期的可用率由 Q1 的 `availability` 描述，不要把这 2 小时停机再算一遍。

为什么用"概率 × 损失"而不是直接加 10000？因为回滚不一定发生。设一次回滚的额外损失是 $2\times5000=10000$。A 有 0.05 的概率回滚，期望损失 $0.05\times10000=500$；等价地，$0.95\times16000+0.05\times26000=15200+1300=16500$。B 有 0.5 的概率回滚，$0.5\times16000+0.5\times26000=8000+13000=21000$。这就是 `expected_rollback_cost` 的含义：把"不发生"和"发生"两种情形按概率加权。

这个模型假设决策者是风险中性的，只看期望值。现实中如果停机造成的声誉损失、合同违约或团队压力很大，你可能愿意为低回滚概率多付钱；TCO 的期望值不衡量这种方差。notebook 也提醒，计划内停机或其他迁移损失应另计，不能都塞进这一个概率里。

两个候选的工时费都是 16000，因为 notebook 假设工程 120 小时、验证 40 小时、每小时 100 的投入一样；差异全部来自回滚概率 0.05 对 0.5。如果 B 的软件栈更陌生，工程/验证工时也应该更高，那会进一步拉大差距。反过来说，如果某个候选的迁移风险很低但工时很高，也不能只看 16500/21000 这两个总数，要回到 `labor_cost` 和 `expected_rollback_cost` 两个分项看是谁在驱动。

### 第 3 步：Q3 `cost_per_million_successful_requests`——分母必须和分子同一时间口径
单位成本的分母是持有期内真正成功的请求数：

```python
successful_requests = (requests_per_second * availability * utilization
                       * success_rate * months * 30 * 24 * 3600)
```

也就是"每秒请求率 × 可用率 × 利用率 × 成功率 × 月数 × 30 天 × 24 小时 × 3600 秒"。`requests_per_second` 的定义是"设备可服务且有任务时，每秒处理多少次请求"，所以它只该乘繁忙秒数；如果请求率已经按整个日历时间平均过，就直接乘日历秒数，不能再乘一遍可用率和利用率，否则分母会重复缩小、单位成本虚高。

函数还要求各比例不超过 1、月份为正；成功请求数为 0 时抛 `ValueError`，因为"每百万成功请求成本"没有定义。

`success_rate` 的定义是"在共同功能和质量要求下成功的比例"，不是"HTTP 200 的比例"。如果候选的输出质量不达标、重试后才成功、或者被限流丢弃，都不该算进成功请求。notebook 强调"请求集合、输入规模和成功标准保持相同"，否则 A 的 0.98 和 B 的 0.95 可能不是同一把尺子，单位成本就不可比。

先用一个小例子校验公式：`total_cost=324`、`requests_per_second=1`、`availability=0.5`、`months=1`、`utilization=0.5`、`success_rate=0.5`。成功请求 $=1\times0.5\times0.5\times0.5\times30\times24\times3600=324000$，单位成本 $=324/324000\times10^6=1000$。

代入 A、B：

- A 的成功请求 $=11975.04\times3600\times20\times0.98=844{,}958{,}822.4$，约 844.96 百万；单位成本 $=58430.4192/844.9588224\approx69.15$。
- B 的成功请求 $=11612.16\times3600\times18\times0.95=714{,}844{,}569.6$，约 714.84 百万；单位成本 $=60440.896/714.8445696\approx84.55$。

A 每百万成功请求便宜约 15.4。这里能看出分母的威力：A 的基础成本更高，但它的请求率 20 > 18、成功率 0.98 > 0.95、可用率 0.99 > 0.96，成功请求多了约 18%，把单位成本拉低了。

把分母的因子单独拆开，可以看清每个比例的影响。A 的"日历平均请求率"是 $20\times0.99\times0.7\times0.98=13.5814$ 请求/秒，B 是 $18\times0.96\times0.7\times0.95=11.4912$ 请求/秒，比值约 1.182，正好对应成功请求数 844.96 百万对 714.84 百万的比值。若把 B 的可用率从 0.96 提到 0.99，其他不变，它的成功请求会变成 $11612.16\times(0.99/0.96)\times3600\times18\times0.95$，约 737.2 百万，单位成本降到约 81.99；但仍高于 A，因为请求率和成功率还低。这说明分母的每个因子都要按真实工作负载填，不能只改一个"看起来最差"的数。

重复计算是这一问最常见的错误。假设你拿到的 `requests_per_second` 已经是"按整个日历时间平均"的 13.5814，却仍然传 `availability=0.99, utilization=0.7`，分母会被再乘一次 0.693，成功请求数缩到约 585.6 百万，单位成本从 69.15 虚高到约 99.8。函数本身无法判断你的请求率是"繁忙时"还是"日历平均"，所以参数语义必须由调用者保证：繁忙时请求率配可用率/利用率；日历平均请求率就直接乘日历秒数，两个比例传默认的 1.0。

### 第 4 步：Q4 `effective_cost_per_used_hour`——换一种采购分摊方式
前面把全额采购一次性计入总成本。Q4 只改分摊方式：采购金额按 `depreciation_months` 直线分摊、残值为零，观察期 `horizon_months` 内只分摊其中一段：

```python
allocated_purchase = purchase_cost * min(horizon_months / depreciation_months, 1.0)
used_hours = horizon_months * 30 * 24 * availability * utilization
cost_per_used_hour = (allocated_purchase + operations_cost + migration_cost) / used_hours
```

`min(..., 1.0)` 表示观察期超过分摊期时，这台设备累计也只分摊一次采购金额，不会重复计费。

A 的观察期是 24 个月，非采购费用为电费 7130.4192 + 运维 4800 = 11930.4192，迁移 16500。全额采购（`depreciation_months=24`）分摊 30000：

$$(30000+11930.4192+16500)\div11975.04=58430.4192\div11975.04\approx4.879$$

按 36 个月分摊（`depreciation_months=36`）只计 $30000\times24/36=20000$：

$$(20000+11930.4192+16500)\div11975.04=48430.4192\div11975.04\approx4.044$$

两者相差 $10000/11975.04\approx0.835$，正好是少分摊的那 10000 摊到每个繁忙小时。notebook 还做了一个敏感性对照：只把利用率从 0.7 降到 0.35，费用不变，繁忙小时减半，单位成本恰好翻倍到约 8.089。这提醒我们：分母变小会让单位成本迅速上升，低利用率设备的"便宜"很脆弱。

这一问不模拟分期扩容或二次采购；若要讨论需求增长与替换计划，需要另给逐期需求和采购表。

要分清"现金支出"和"成本分摊"。全额采购口径下，30000 在持有期开始时一次支出；36 个月直线分摊口径下，账面上每月承担 $30000/36=833.33$，24 个月累计 20000，剩下的 10000 是这台设备在观察期末的账面余额（假设零残值，若真有残值还要另算）。分摊不改变你实际付了 30000 这个事实，只改变"这段观察期该承担多少"。所以两个口径的每小时成本不同，不是谁算错了，而是问题不同：一个问"这台设备整个持有期每小时摊多少"，另一个问"这段观察期每小时摊多少"。

`min(horizon_months / depreciation_months, 1.0)` 还有一层保护：如果观察期 48 个月、分摊期 36 个月，比例是 $48/36>1$，但函数只取 1.0，仍然只分摊 30000，不会变成 40000。因为这台设备只买了一次；要继续用 48 个月，不需要在账上再买一台。若真的中途扩容或替换，那是另一套逐期采购计划，不在这个函数的模型里。

利用率敏感性也值得再算一遍：`used_hours = horizon_months * 30 * 24 * availability * utilization`。利用率从 0.7 降到 0.35，分母正好减半，而 `allocated_purchase + operations_cost + migration_cost` 没变（这一问特意不重算用电），所以每小时成本精确翻倍：4.044 变 8.089。现实中利用率下降往往还会降低电费，但本节把用电固定住，只观察分母效应，避免两个变量一起动。

## 关键概念速查表
| 术语 | 大白话解释 |
|:---|:---|
| TCO（总拥有成本） | 持有和使用设备期间计入的全部成本，范围要事先说清 |
| 可用率（availability） | 能提供服务的时间占日历时间的比例 |
| 利用率（utilization） | 可用时间内真正有任务的比例，不是 GPU 硬件利用率 |
| 繁忙小时 / 空闲小时 | 真正干活的时间 / 其余通电时间（含不可服务与无任务） |
| 空闲功率 | 设备通电但不干活时仍消耗的功率 |
| 回滚（rollback） | 迁移失败时恢复原方案；其停机损失按概率取期望 |
| 成功请求数 | 请求率 × 可用率 × 利用率 × 成功率 × 持有期秒数 |
| 单位请求成本 | 总成本 ÷ 成功请求数，再换算成每百万请求 |
| 折旧分摊 | 把采购金额按月份摊到观察期，不是设备必须更换的时间 |
| 直线分摊 / 零残值 | 每月摊同样的金额，期末剩余价值按 0 计 |

## 小白常见疑问

**Q1：可用率 0.5、利用率 0.5，为什么繁忙是 180 小时而不是 360 或 720？**
720 小时先乘可用率 0.5，得到 360 小时"能服务"的时间；再乘利用率 0.5，得到 180 小时"能服务且真的有任务"的时间。两个比例是串联关系，不是二选一。剩下 540 小时里既有设备不可服务的时段，也有可服务但空闲的时段，都按空闲功率计费。

另外，notebook 固定"每月 30 天、全期通电"，所以一个月就是 $30\times24=720$ 小时，24 个月就是 17280 小时。这样做的目的是消除大小月差异，让不同候选在同一时间基准上比较；如果把 30 天换成 365/12 天，数会略有不同，但比较逻辑不变。真实电费账单按自然月和实际抄表计费，做预算时可以把这里的 720 当作月度近似，再按实际天数修正。

**Q2：为什么空闲功率只作用在 540 小时，而繁忙功率作用在 180 小时？**
能量按"这段时间用多大功率"累计：繁忙的 180 小时用 `power_kw`，其余 540 小时用 `idle_power_kw`。不是全程都按繁忙功率算，也不是全程都按空闲功率算。A 的 8913.024 kWh 就是这样得到的。

**Q3：基础账 B 更便宜，为什么最后反而 A 更划算？**
因为 B 的回滚概率 0.5，期望停机损失 5000；A 只有 0.05，期望损失 500。两者工时费都是 16000，所以迁移总成本 A 16500、B 21000。基础账 B 领先约 2490，迁移账 A 领先 4500，净效果是 A 反超约 2010。TCO 比较的是全生命周期，不是采购单。

**Q4：A 的总成本更高，为什么每百万请求反而更便宜？**
单位成本看的是"总成本 ÷ 成功请求数"。A 成功请求约 844.96 百万，B 只有 714.84 百万；A 的总成本 58430.42 只比 B 的 60440.90 低 3.3%，但请求数多了 18.2%，所以单位成本低到 69.15 对 84.55。换句话说，总成本只低 3.3%，成功请求却多 18.2%，单位成本才会低约 18.2%。如果两个候选的成功率、可用率、请求率完全一样，单位成本比才等于总成本比；这里每一项都不同，所以不能直接拿总成本排序代替单位成本排序。

**Q5：36 个月折旧分摊是不是说设备 36 个月后必须换？**
不是。`depreciation_months` 只描述采购金额怎样分配到每个月，不决定替换时间。观察期 24 个月、分摊期 36 个月时，本观察期只计 $30000\times24/36=20000$；设备是否继续用、何时扩容，需要另给需求与采购计划。
