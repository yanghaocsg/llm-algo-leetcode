# 28. 容错与检查点 — 小白讲解

> 对应 notebook：[`28_Fault_Tolerance_and_Checkpointing.ipynb`](./28_Fault_Tolerance_and_Checkpointing.ipynb)

## 一句话总结
本节用四个计算器回答"训练挂了怎么接着跑"。`inspect_checkpoint_manifest` 核对检查点是否包含模型、优化器、调度器、随机数状态和训练进度五类角色；`mean_rollback_minutes` 与 `expected_failure_overhead` 按均匀故障假设算出平均回滚时间和加载开销。`checkpoint_interval_cost` 比较 15、30、60、120 分钟四种保存间隔的总开销，给定参数下 120 分钟最省；`validate_sharded_checkpoint` 检查分片数量、rank 唯一性与覆盖、检查点标识，并标记恢复进程数变化时是否需要重分片。

## 为什么需要它：痛点是什么
"训练到第 70 小时挂了，从第 68 小时的 checkpoint 恢复，loss 却跳了一下"——这是初学者最常遇到的困惑。原因往往不是模型坏了，而是**存的东西不够**：只存了 `model.state_dict()`，优化器的动量和方差没了、学习率调度器回到了起点、随机数生成器重新从种子开始、数据加载器也不知道上次读到哪。恢复后的更新轨迹和原轨迹不是同一条，loss 自然会跳。

第一层是"存什么"，再往下还有两层。第二层：既然要存，是不是存得越勤越好？存一次要暂停训练、把一大组状态写到存储，存得太密会让训练大部分时间都在写盘；存得太稀，一旦故障又要重跑很久。第三层是分布式场景：四个 rank 各写一个分片，怎么确认四片都到齐、没有重复、没有混进别的 step？本节四个问题正好对应这三层：Q1 管"存什么"，Q2、Q3 管"多久存一次"，Q4 管"分片是否成套"。

生活类比：游戏存档。只存"角色等级"不够，还要存地图坐标、背包、任务进度和随机事件的状态；少存一项，读档后可能出现在错误的地点、重复已经做过的任务。检查点里的"角色"就是这些必须一起保存的状态项，清单（manifest）则是存档索引，提交标记（committed）表示这一组文件已经完整发布、不是写了一半的残档。

## 核心问题
- 一次可恢复的训练检查点必须包含哪些状态角色？各自丢了会怎样？
- 保存间隔与平均回滚时间是什么关系？任务末尾不足一个间隔时怎么算？
- 更频繁地保存一定更好吗？写入成本和故障损失如何权衡？
- 分片检查点要检查哪些项？为什么"数量"和"rank 唯一性"必须分开查？
- 清单核对通过，是否等于恢复成功？

## 解决思路：一步步看懂

**第 1 步：Q1——先列角色，再谈文件。** `inspect_checkpoint_manifest(entries, committed, required_roles=None)` 的默认必需角色是：

```python
required_roles = {'model', 'optimizer', 'scheduler', 'rng', 'progress'}
```

五个角色分别对应：模型权重；优化器状态（Adam 的一阶矩和二阶矩）；学习率调度器（恢复当前 step 对应的学习率）；随机数生成器状态；训练进度（当前 step 和数据集位置）。少任何一项都不是"精度差一点"，而是换了一条更新轨迹：没有优化器状态，一阶、二阶矩从零开始，参数更新方向和步长立刻变化；没有调度器，学习率回到初始值，可能重新经历 warmup；没有 RNG，dropout 掩码和数据打乱顺序都变了；没有进度，数据加载器会从头开始，重复已经学过的样本。模型权重缺失则连参数都没有，属于最直接的失败。notebook 特别点明 RNG 的细节：**只保存初始种子不够**，种子只说明序列从哪里开始，恢复时需要的是生成器"已经推进到的位置"，否则 dropout、数据打乱等随机行为会和原轨迹分叉。训练进度里也要有数据位置，避免重复或跳过已经处理过的批次。

清单本身只是一个列表，每项包含角色、路径和大小（MiB）。函数检查四件事：缺了哪些必需角色（`missing_roles`，排序后返回）、有没有重复路径（`duplicate_paths`）、有没有非法文件（路径为空，或大小不是有限正数，`invalid_files`）、以及 `committed` 是否为 `True`。最后：

```python
'manifest_checks_passed': committed and not missing and not invalid_files and not duplicates,
```

四个条件是与关系，缺一不可。`total_mib` 则把所有条目的大小求和后保留两位小数。

`committed` 单独检查，是因为前几项只说明"该有的角色都登记了、路径和大小看起来合理"，并不说明这组文件已经发布完成。想象一次写到一半的保存：清单可能已经写全，但某个大文件还没落盘；如果只看角色齐全就宣布成功，恢复时会读到残档。提交标记就是"这组记录已经完整发布"的承诺；没有它，恢复时可能读到写了一半的残档。

几个实现细节值得单独看。重复路径的写法是 `{path for path in paths if paths.count(path) > 1}`，对每个路径数一遍全表，条目少时这样写很直观，条目多了会退化成平方复杂度。大小检查用 `math.isfinite(entry['size_mib'])`，能同时挡住 `inf`、`-inf` 和 `nan`，再配合 `<= 0` 排除零和负数；也就是说"文件登记了，但大小写成了 NaN 或 0"同样算非法。这些检查全部在内存里的字典上完成，不触碰磁盘。

拿单元里的 `complete_entries` 手算：模型 2400 MiB、优化器 4800 MiB、调度器 0.01 MiB、RNG 0.01 MiB、进度 0.01 MiB，总计 $2400 + 4800 + 0.03 = 7200.03$ MiB。只保留第一项（`complete_entries[:1]`）时，`weights_only` 的 `missing_roles` 是 `['optimizer', 'progress', 'rng', 'scheduler']`——排序后按字母序，不是按重要性。这里要建立一个习惯：**清单检查只核对元数据，不读取磁盘文件**；文件是否真的存在、内容是否损坏，是下一步的事。

**第 2 步：Q2——平均回滚时间怎么推。** `mean_rollback_minutes(run_minutes, interval_minutes)` 基于三个假设：任务开始时已经有一个可用检查点；故障在计划计算时间内均匀发生；一次故障后从最近的检查点重跑。一个完整间隔长 $I$，故障落在间隔内均匀分布，距离上一个检查点的平均时间就是 $I/2$；把整个间隔的"损失"累起来是 $I^2/2$。末尾不足一个间隔的部分长 $T$，同理贡献 $T^2/2$。除以总运行时间 $R$，得到：

$$\text{mean\_rollback} = \frac{n_{\text{full}} \cdot I^2 + T^2}{2R}, \qquad n_{\text{full}} = \left\lfloor \frac{R}{I} \right\rfloor,\quad T = R - n_{\text{full}} \cdot I$$

代码就是这一行的直译：

```python
full_intervals = math.floor(run_minutes / interval_minutes)
tail = run_minutes - full_intervals * interval_minutes
return (full_intervals * interval_minutes**2 + tail**2) / (2 * run_minutes)
```

`run_minutes == 0` 时直接返回 0.0，避免除零。`expected_failure_overhead` 再把它乘上期望故障次数：故障率按"每小时 0.02 次"给，72 小时的期望故障数是 $72 \times 0.02 = 1.44$ 次；每次故障除了回滚，还要重新加载检查点，加载时间按 8 分钟计。

把主例代进去：72 小时 $= 4320$ 分钟，间隔 60 分钟，$4320/60 = 72$ 个完整间隔、尾巴为 0，平均回滚 $72 \times 60^2 / (2 \times 4320) = 259200 / 8640 = 30$ 分钟。于是回滚总时间 $1.44 \times 30 = 43.2$ 分钟，加载总时间 $1.44 \times 8 = 11.52$ 分钟，合计 54.72 分钟——这就是单元里断言的数字。间隔改成 30 分钟，完整间隔 144 个，平均回滚 15 分钟，回滚总时间 21.6 分钟。如果任务本身只有 30 分钟、间隔仍是 60 分钟，则 $n_{\text{full}}=0$、$T=30$，平均回滚 $30^2/(2 \times 30) = 15$ 分钟，也就是"短任务最多只损失任务时长的一半"。

再看一个有尾巴的例子：任务 100 分钟、间隔 60 分钟，$n_{\text{full}}=1$、$T=40$，平均回滚 $(1 \times 3600 + 1600)/(2 \times 100) = 5200/200 = 26$ 分钟。这个数比 30 分钟小，因为尾巴只有 40 分钟，故障落在尾巴里时能回滚的上限比完整间隔短。公式把"完整间隔"和"末尾短段"分开累加，就是为了处理这种不均匀。

这个模型是**一阶估计**：故障按计划计算时长统计，先忽略写入期间发生的故障、也忽略重跑期间再次故障；它适合比较方案，不适合当作精确预算。为什么强调"均匀"和"任务开始时已有检查点"？真实故障未必均匀，写入期间也可能发生故障，重跑期间还可能再挂一次。均匀假设把这些复杂性抹平，换成一个可比较的模型——它的用途是排序方案，不是承诺"你一定会损失 54.72 分钟"。

**第 3 步：Q3——保存频率的两难。** 间隔越短，每次故障回滚得越少，但保存次数越多、同步暂停的写入时间越长。`checkpoint_interval_cost` 把两部分相加：

```python
save_count = max(math.ceil(run_minutes / interval_minutes) - 1, 0)
failure = expected_failure_overhead(run_minutes / 60, fault_rate_per_hour, interval_minutes, reload_minutes)
save_overhead = save_count * save_minutes
```

`- 1` 的原因在 notebook 里写得很清楚：只统计计划结束前的"恢复检查点"，**结束时的最终模型交付另计**。以 1440 分钟、每 120 分钟保存为例，保存点是 120、240、…、1320，共 11 次，不是 12 次。

固定参数是：计划 1440 分钟、每次保存 2 分钟、故障率每小时 0.02、加载 8 分钟。四个候选的结果如下：

| 间隔（分钟） | 保存次数 | 保存开销（分钟） | 故障开销（分钟） | 总开销（分钟） |
| ---: | ---: | ---: | ---: | ---: |
| 15 | 95 | 190 | 7.44 | 197.44 |
| 30 | 47 | 94 | 11.04 | 105.04 |
| 60 | 23 | 46 | 18.24 | 64.24 |
| 120 | 11 | 22 | 32.64 | **54.64** |

故障开销可以逐行手算：1440 分钟等于 24 小时，期望故障数 $24 \times 0.02 = 0.48$ 次；加载时间固定是 $0.48 \times 8 = 3.84$ 分钟，剩下的部分就是 $0.48 \times$ 平均回滚。以 120 分钟为例，平均回滚 60 分钟，于是 $0.48 \times 60 + 3.84 = 28.8 + 3.84 = 32.64$ 分钟；保存 11 次、每次 2 分钟是 22 分钟，两者相加 54.64 分钟，正好对上。

读表的方法：保存开销随间隔变短而线性上升（次数约等于 $1440/I$），故障开销随间隔变长而线性上升（平均回滚约等于 $I/2$），两者相加会有一个最低点。在这四个候选里，120 分钟最省，总开销 54.64 分钟；单元断言 `best["interval_minutes"] == 120`、`best["save_count"] == 11`、`best["total_overhead_minutes"] == 54.64`。

再往两边手算一下，能确认这不是"越粗越好"：90 分钟间隔时保存 15 次、写入 30 分钟，平均回滚 45 分钟，故障开销 $0.48 \times 45 + 3.84 = 25.44$ 分钟，合计 55.44 分钟；240 分钟间隔时保存 5 次、写入 10 分钟，平均回滚 120 分钟，故障开销 $57.6 + 3.84 = 61.44$ 分钟，合计 71.44 分钟。所以曲线在 120 附近触底，两边都会回升。这些都是同一公式的算术，不是实测。notebook 也提醒：这是**同步写入**模型，异步写入还要看写入与计算、I/O 争用的时间线。保存开销也不只是暂停时间：写 7200 MiB 会占用存储带宽，分布式里还可能让其他 rank 等待；同步保存把这些都算进暂停，异步保存则把争用藏进时间线。本例只比较同步暂停，是因为它最容易复现，不是因为它更真实。

**第 4 步：Q4——分片检查点的元数据核对。** 这里采用简化布局：每个保存 rank 登记一个分片包。`validate_sharded_checkpoint(manifest, shards, *, target_world_size=None)` 先复用 Q1 检查角色，再按顺序收集问题：

1. 角色检查没过 → `state manifest checks failed`；
2. 分片数不等于保存时的 `world_size` → `shard count differs from saved world size`；
3. rank 不是整数 → `rank IDs must be integers`；
4. rank 有重复 → `rank IDs are duplicated`；
5. `set(ranks)` 不等于 `set(range(world_size))` → `rank coverage differs from saved world size`；
6. 任一分片的 `checkpoint_id` 与清单不一致 → `checkpoint IDs are inconsistent`；
7. 任一分片大小非有限正数 → `one or more shard sizes are invalid`。

返回值有三个字段：`metadata_checks_passed`（没问题才为真）、`requires_reshard`（恢复进程数与保存进程数不同）、`issues`（问题列表）。

为什么"数量"和"唯一性"要分开查？只查"每个 rank 都出现过"不够：假设保存时 4 个 rank，恢复清单里却有 5 个分片 `[0, 0, 1, 2, 3]`，所有 rank 都出现了，但数量不对；只查数量也不够：4 个分片 `[0, 0, 2, 3]` 数量正好，却重复了 rank 0、缺了 rank 1。所以两个检查都要有，集合去重不能替代计数。

主例的清单是 `checkpoint_id='step-1200'`、`world_size=4`，四个分片各有 900 MiB、rank 为 0 到 3，全部检查通过。删掉最后一个分片（`complete_shards[:-1]`）后，数量变成 3、覆盖也不全，`metadata_checks_passed` 为假；把第二个分片换成 rank 0 的副本（`[0, 0, 2, 3]`）后，`issues` 里会出现 `rank IDs are duplicated`，同时覆盖检查也会报缺 rank 1；恢复进程数传 2 时，`requires_reshard` 为 `True`，但元数据检查仍可通过——**需要重分片不等于清单有问题**，只是加载方式要变。

还有一个**没有检查**的量：四个分片各 900 MiB，合计 3600 MiB，而清单里五项合计 7200.03 MiB，两者并不相等。`validate_sharded_checkpoint` 不比较这两个数，因为本例把"清单条目的大小"和"分片包的大小"当成两组独立给定的元数据；真实系统通常会有自己的校验规则（比如分片总大小应覆盖清单中的张量总量），那要按框架的格式另外实现。提这一点不是让你去改断言，而是提醒：**看到"检查通过"时，要清楚它检查了哪些项、没检查哪些项**。

提交标记和 `checkpoint_id` 解决的是"混档"问题：如果目录里同时躺着 step-1200 和 step-1260 的分片，只按文件名收集就可能拼出一个跨 step 的检查点；`checkpoint_id` 一致性检查就是防这个。`committed` 则防另一类问题：文件还没写完，就被当成可用的检查点。

`issues` 是列表而不是单个布尔值，也有实际考虑：一个清单可能同时缺片、覆盖不全、大小非法，函数会把问题都收集起来，让你一次看到全部，而不是遇到第一个就返回、修一个再跑一次。

还要理解"期望故障数 1.44"的含义：它不是"一定会坏 1.44 次"，而是长期平均。同样 72 小时、同样故障率跑很多次，有的跑 1 次、有的跑 2 次，平均 1.44 次。把它乘平均回滚得到的 43.2 分钟也是期望值，不是某一次的实际损失；把 54.72 分钟当成 SLA 承诺，就误用了模型。

Q3 的保存次数也有一个边界细节：`ceil(R/I)-1`。如果 $R$ 恰好是 $I$ 的整数倍，最后一次保存正好落在结束点，被减 1 排除；如果不是整数倍，`ceil` 会把最后一段也算进去，再减 1 排除结束点。两种情况下，"最终交付"都不会被混进恢复检查点。这也解释了为什么 1440/120 得到 11 而不是 12。

**第 5 步：清单之后还差什么。** notebook 反复强调"通过结果表示给定清单条件满足，尚未读取磁盘文件"。真正的恢复链至少还有：读取每个文件、校验内容（大小只是元数据，损坏要另外发现）、把权重和优化器状态加载回模型、恢复调度器和 RNG、定位数据位置，最后对照"恢复后的下一次更新"是否与不间断训练一致。若恢复进程数变了，还需要目标框架支持并正确执行重分片，否则分片布局对不上。把"清单一致"当成"加载成功"，是这一节最想避免的误判。

**把四问连起来看：** Q1 决定"恢复是否可能"，Q2 把"一次故障平均丢多少"变成可算的数，Q3 把"多久存一次"变成可比较的总开销，Q4 把"分片是否成套"变成可核对的清单。四问都通过，也只走到"可以开始加载"，还没有真正恢复——它们检查的是元数据和模型，不是训练能否无缝接上。

## 关键概念速查表
| 术语 | 大白话解释 |
| --- | --- |
| 检查点（checkpoint） | 训练中途保存的一组状态，用来在故障后接着跑 |
| 清单（manifest） | 列出每个状态项的角色、路径和大小的索引 |
| 提交标记（committed） | 表示这组记录已经完整发布，不是写了一半的残档 |
| 状态角色 | 模型、优化器、调度器、RNG、进度等必须一起保存的对象 |
| RNG 状态 | 随机数生成器"推进到哪"的记录，只有种子不够 |
| 平均回滚时间 | 故障后平均要重跑多久，均匀假设下约为间隔的一半 |
| 故障率 | 每小时期望发生的故障次数，本例是 0.02 |
| 保存间隔 | 两次检查点之间的计划时长，本例比较 15/30/60/120 分钟 |
| 分片检查点 | 每个 rank 各存一个分片包的布局 |
| 重分片（reshard） | 恢复时进程数与保存时不同，需要重新划分分片 |
| 摊销 | 把一次性的准备成本分摊到多次复用上 |

## 小白常见疑问

**Q1：只存 `model.state_dict()` 为什么不够？清单检查通过就能直接继续训练吗？**
因为恢复的是"训练状态"，不只是"推理权重"。`weights_only` 的检查显示它缺 `['optimizer', 'progress', 'rng', 'scheduler']` 四项：没有优化器动量，更新方向会变；没有调度器，学习率回到初始值；没有 RNG 位置，dropout 和数据顺序会分叉；没有进度，不知道该从哪个 batch 继续。反过来，即使清单五项齐全并通过检查，也只说明元数据合理：清单不读文件、不校验内容、不加载状态，"清单一致"离"加载成功"还有读取、校验、加载、对照下一次更新这几步。

**Q2：RNG 为什么不能只存一个种子？**
种子决定序列的起点，但训练到中途时，生成器已经消耗了很多随机数。只恢复种子等于把序列倒回开头，后续的随机掩码、采样顺序都会和原轨迹不同。保存的是生成器的**当前位置**（notebook 原话："它记录生成器已经推进到的位置"）。

**Q3：平均回滚为什么是间隔的一半，而不是整个间隔？**
前提是故障在间隔内均匀分布，且任务开始时已有一个检查点。落在间隔正中间的概率最高，平均下来就是一半；最坏情况才是整个间隔。`mean_rollback_minutes(30, 60) == 15` 就是"任务比间隔还短"的边界：尾巴 30 分钟，平均损失 15 分钟。

**Q4：保存得越频繁，总开销不是越小吗？**
不是。15 分钟间隔要保存 95 次，每次 2 分钟，光写入就 190 分钟，比 120 分钟间隔的 22 分钟多得多；而它省下的故障回滚只有约 25 分钟。总开销是"写入成本 + 故障损失"，两者一个随频率上升、一个随频率下降，所以存在最低点。

**Q5：`requires_reshard=True` 是不是表示检查点坏了？**
不是。它只说明恢复时的进程数和保存时不同，需要框架做重分片。`metadata_checks_passed` 仍可能是 `True`，因为分片本身的元数据没问题；真正加载时能不能正确重分片，要由目标框架决定。本例的 `checkpoint_id` 是 `'step-1200'`，四个分片的 id 必须都与它相同，混进别的 step 就会被检查出来。检查的先后顺序不影响结论，只影响 `issues` 列表里问题的排列。
