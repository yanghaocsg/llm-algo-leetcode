# 07. CPU 与 GPU 异构调度 — 小白讲解

> 对应 notebook：[`07_CPU_GPU_Heterogeneous_Scheduling.ipynb`](./07_CPU_GPU_Heterogeneous_Scheduling.ipynb)

## 一句话总结
本节用四个小计算器回答"这个阶段到底该放 CPU 还是 GPU"：`stage_placement` 把输入搬入、GPU 计算、输出回传串成完整路径，发现 64 MB 进 + 64 MB 出在 16 GB/s 下光搬运就要 8.1 ms，GPU 算 0.4 ms 也救不回来；`overlap_timeline` 说明只有数据分块、计算只依赖前缀时，8 ms 搬运里才可能藏住 3 ms；`offload_ledger` 把 4 GB 状态的每步往返算成 8 GB、250 ms，75% 可隐藏后仍暴露 62.5 ms；`parallelism_evidence` 用串行/实际时间、活跃区间并集和暴露同步等待，区分"时间真的省了"和"只是看起来忙"。

## 为什么需要它：痛点是什么
初学者常把"GPU 算得快"直接当成"放 GPU 更快"。例如某个阶段 CPU 要 2 ms，GPU 只要 0.4 ms，直觉上应该搬过去；但数据在主机内存里，先要传进去、算完还要传回来。如果往返搬运要 8 ms，GPU 路径总共 8.5 ms，比留在 CPU 慢四倍多。反过来，如果 CPU 要 100 ms、GPU 计算要 8 ms，同样的搬运就完全值得。所以判断依据不是单看计算时间，而是"从数据就绪到结果可用的完整路径"。

生活类比：把一份文件发给远处的专家修改。专家手很快（GPU 计算快），但文件传过去、传回来都要时间；如果本地同事两分钟就能改完，就不该为了"专家更专业"而付出来回快递的成本。只有文件能拆成几块、专家改第一块时你还在传后面的块，快递时间才可能被藏掉一部分。

本节所有带宽都按十进制 GB/s（每秒十亿字节），时间用毫秒；`input_bytes`、`output_bytes` 必须是整数。notebook 的比较是估算，不是实测，真实路径还要看依赖、流和事件。

## 核心问题
- 一个阶段放在 GPU 上，端到端时间由哪几段组成？为什么 GPU 计算更快不代表整条路径更短？
- CPU 路径和 GPU 路径在什么条件下打平？输入输出都为空时搬运时间为什么是 0？
- 搬运和计算重叠需要什么前提？8 ms 搬运、20 ms 计算，为什么最多只能藏 3 ms？
- 状态卸载省下的容量，要付多少搬运时间？"卸载 4 GB"为什么不等于"峰值降 4 GB"？
- 串行 30 ms、优化后 20 ms，加速比、节省时间、活跃时间占比和暴露同步占比各说明什么？

## 解决思路：一步步看懂

### 第 1 步：Q1 `stage_placement`——先算往返搬运，再比两条完整路径
函数的输入是 CPU 计算时间、GPU 计算时间、输入字节数、输出字节数、有效带宽和固定开销。核心只有三行：

```python
transfer_ms = (input_bytes + output_bytes) / (bandwidth_gb_per_s * 1e9) * 1e3 \
              + fixed_transfer_ms
gpu_path_ms = gpu_ms + transfer_ms
```

`(input_bytes + output_bytes)` 是往返总字节；除以 `bandwidth_gb_per_s * 1e9` 得到秒，再乘 1000 换成毫秒。这里假设输入搬入和输出回传串行发生、双向有效带宽相同，`fixed_transfer_ms` 是这次往返的固定开销合计。

然后用示例输入手算：`input_bytes=64_000_000`、`output_bytes=64_000_000`、带宽 16 GB/s、固定开销 0.1 ms。

$$\text{transfer}=\frac{64{,}000{,}000+64{,}000{,}000}{16\times10^{9}}\times1000+0.1
=\frac{128\times10^{6}}{16\times10^{9}}\times1000+0.1=8+0.1=8.1\ \text{ms}$$

第一条路径：CPU 2 ms。第二条：GPU 计算 0.4 ms + 搬运 8.1 ms = 8.5 ms。函数返回 `shorter_estimated_path="cpu"`。第二条构造：CPU 100 ms，GPU 计算 8 ms，GPU 路径 $8+8.1=16.1$ ms，返回 `"gpu"`。

边界也检查了：`cpu_ms=8.5` 时两条路径相等，返回 `"equal"`；`input_bytes=0, output_bytes=0` 时，哪怕带宽 16 GB/s，`transfer_ms` 也是 0（公式里分子为 0，固定开销默认 0）。这说明搬运成本来自数据量，不是"只要跨设备就固定收 8 ms"。

输入校验也值得注意：字节数必须是 `int`（浮点会报错），计算时间和固定开销必须有限非负，带宽必须有限且大于 0。这些检查防止把负数或 `NaN` 带进比较，得出"哪条都更短"的荒谬结果。

按同一公式，可以看清数据量和带宽怎样改变结论（以下都是对给定公式的手算，不是 notebook 的断言）：

| 输入+输出 | 16 GB/s 搬运 | 加 0.1 固定 | GPU 计算 0.4 的路径 | 对 CPU 2 ms |
|---:|---:|---:|---:|:---|
| 32 MB + 32 MB | 4 ms | 4.1 ms | 4.5 ms | CPU 更短 |
| 64 MB + 64 MB | 8 ms | 8.1 ms | 8.5 ms | CPU 更短 |
| 128 MB + 128 MB | 16 ms | 16.1 ms | 16.5 ms | CPU 更短 |
| 1 MB + 1 MB | 0.125 ms | 0.225 ms | 0.625 ms | GPU 更短 |

这张表的读法是：数据量越大，搬运越贵；但固定开销 0.1 ms 在小消息里占比很高——1 MB 往返的纯传输只有 0.125 ms，固定开销却占了 0.1 ms，接近一半。真实系统里，"启动一次传输"的成本往往比"多传几 MB"更影响小算子。若带宽从 16 GB/s 提到 32 GB/s，128 MB 往返的纯传输从 16 ms 降到 8 ms，GPU 路径变成 8.5 ms；同样的计算量，链路带宽直接决定该不该搬。

反过来，固定 GPU 计算 0.4 ms、CPU 2 ms、带宽 16 GB/s，可以算出"正好打平"的数据量。设往返总字节为 $X$，需要

$$\frac{X}{16\times10^{9}}\times1000+0.1+0.4=2.0\ \text{ms}$$

解得 $X=1.5\times10^{-3}\times16\times10^{9}=24{,}000{,}000$ B，即输入输出各 12 MB。低于这个量，GPU 路径更短；高于这个量，CPU 更短。这个边界把"计算节省 1.6 ms"换算成了"最多能搬 24 MB"，比单看 0.4 ms 对 2 ms 有用得多。真实阶段还可能有多个算子、不同带宽和并行流，边界要按整条路径重算。

### 第 2 步：Q2 `overlap_timeline`——重叠不是免费的，取决于依赖前缀
真实系统里搬运和计算可以同时进行，但前提是：计算只需要已经搬完的那部分数据，且运行时/硬件允许并发。函数用 `dependency_ms` 表示"计算开始前必须等到的搬运前缀"：

```python
serial_ms = copy_ms + compute_ms
overlappable_copy_ms = copy_ms - dependency_ms
elapsed_ms = dependency_ms + max(overlappable_copy_ms, compute_ms)
hidden_ms = serial_ms - elapsed_ms
```

读法是：先等 `dependency_ms`，之后剩下的搬运 `copy_ms - dependency_ms` 与 `compute_ms` 并行，所以完成时间取两者较大值。校验要求 `dependency_ms <= copy_ms`，否则"等待的前缀"比总搬运还长，没有意义。

用 `copy_ms=8`、`compute_ms=20` 三组前缀对照：

| `dependency_ms` | 串行时间 | 剩余可重叠搬运 | 实际完成 | 隐藏 |
|---:|---:|---:|---:|---:|
| 0 | 28 | 8 | $0+\max(8,20)=20$ | 8 |
| 5 | 28 | 3 | $5+\max(3,20)=25$ | 3 |
| 8 | 28 | 0 | $8+\max(0,20)=28$ | 0 |

前缀 5 ms 时，计算 20 ms 比剩余搬运 3 ms 长，所以搬运全部被藏住，但总时间仍是 $5+20=25$ ms，不是 20 ms——前 5 ms 是硬等。前缀 0 时，8 ms 搬运完全被 20 ms 计算覆盖，完成于 20 ms，隐藏 8 ms。前缀 8 ms 时，计算必须等整份输入，一行也没藏住。

还有两个边界：`copy_ms=8, compute_ms=3, dependency_ms=0` 时，完成于 $\max(8,3)=8$ ms，隐藏 3 ms——这次是搬运比计算长，能藏的是计算；`copy_ms=0, compute_ms=0` 时完成时间为 0。结论是：重叠最多把时间压到"较长的那一段"，不会让搬运成本消失，也不会让总时间小于依赖前缀。

把公式整理一下，可以得到一个更好记的闭式：

$$\text{elapsed}=\text{dep}+\max(\text{copy}-\text{dep},\ \text{compute})=\max(\text{copy},\ \text{dep}+\text{compute})$$

也就是说，完成时间只可能是两者之一：要么搬运总时长更长（`copy`），要么"硬等的前缀 + 计算"更长（`dep + compute`）。当前缀为 0 时，隐藏量是 $\min(\text{copy},\text{compute})$：示例里是 $\min(8,20)=8$ ms。当前缀大于 0 时，可重叠的搬运只剩 `copy - dep`，隐藏量随之下降；前缀等于 `copy` 时，可重叠部分为 0，隐藏量也为 0。这个闭式还能解释为什么"重叠"不能凭空创造时间：它只是把两段本来串行的工作塞进同一窗口，窗口长度由较长者决定。

`dependency_ms` 怎么填，直接决定估算是否乐观。它表示"计算真正开始前必须等到的搬运前缀"，不是"搬运总共花了多久"。示例里计算只依赖前 5 ms 搬完的块，所以填 5；如果计算要等整份输入，就填 8（等于 `copy_ms`），此时隐藏为 0；如果计算完全不需要输入（现实中很少见），才可以填 0。把 5 错填成 8，会低估隐藏量；把 8 错填成 0，会高估成"搬运全藏住"。notebook 的校验只保证 `dependency_ms <= copy_ms`，语义是否正确仍要调用者负责。

notebook 特别说明，这里只比较"指定搬运与计算的组合窗口"；首批填充和末批排空的完整多批窗口要到第 29 节，Stream/Event 怎样表达"某块就绪"要到第 17 节。如果输入被拆成很多批，第一批开始前仍要等它的依赖，最后一批算完后也没有更多计算可以覆盖它的搬运；所以真实多批流水线的总时间通常比"单窗口理想重叠"更长。

### 第 3 步：Q3 `offload_ledger`——卸载容量和搬运时间要分开记账
状态卸载（offload）把参数、优化器状态或激活从设备移到主机，需要时再搬回。函数按"一次往返算两倍状态大小"计算：

```python
transfer_gb = state_gb * 2 * round_trips_per_step
transfer_ms = transfer_gb / bandwidth_gb_per_s * 1e3
estimated_exposed_ms = transfer_ms * (1 - overlap_ratio)
```

示例是 4 GB 状态、32 GB/s、每步往返一次：搬运量 $4\times2=8$ GB，时间 $8/32\times1000=250$ ms。若假设其中 75% 能被独立计算隐藏，暴露时间 $250\times(1-0.75)=62.5$ ms。边界断言也覆盖了：`round_trips_per_step=0` 时搬运为 0；改成 2 时每步 16 GB；`overlap_ratio=0` 暴露 250 ms，`overlap_ratio=1` 暴露 0。

这一问最重要的提醒是：`offloaded_state_gb` 只是"移走了多少状态"，不等于"峰值下降多少"。原峰值出现时这部分状态是否已经卸载、回载是否又制造新的峰值、是否新增传输缓冲区，都要结合时间线核对。notebook 把容量和时间分成两个观察量，不让你用一个 4 GB 的数字直接宣称"显存省了 4 GB"。

把公式再展开一点：每步搬运量 $=\text{state\_gb}\times2\times\text{round\_trips\_per\_step}$，时间 $=\text{搬运量}/\text{带宽}\times1000$。4 GB、32 GB/s、一次往返就是 8 GB 和 250 ms；如果状态减半到 2 GB，时间减半到 125 ms；如果带宽翻倍到 64 GB/s，时间也减半到 125 ms。两个方向都线性，但现实中带宽通常由链路决定，能改的主要是"搬多少"和"搬几次"。

250 ms 这个数还要放回训练/推理的步时间里看。如果一步原本只要 100 ms，卸载往返就比计算还长，除非它能被其他工作完全盖住；如果一步有 1 s 的计算，250 ms 里藏掉 75% 后暴露 62.5 ms，才可能划算。`round_trips_per_step` 也提醒你：有些状态一步要搬两次（卸载再回载），有些只在阶段边界搬一次，不能一律乘 2。

容量侧还要检查三件事：原峰值出现时，这部分状态是不是已经卸载；回载时会不会和当前活跃张量叠在一起，制造新的峰值；卸载是否需要额外的传输缓冲区，反而增加设备侧占用。只拿"4 GB 状态"和"峰值 20 GB"相减，得到的 16 GB 只是账面值，不是时间线上的真实峰值。

还别忘了主机侧：卸载把 4 GB 状态搬到主机内存，主机至少要能放下这 4 GB，加上传输缓冲和框架自身的开销。如果主机内存也很紧，卸载只是把 OOM 从 GPU 推到 CPU。主机到设备的链路带宽通常还和同一台机器上的其他进程共享，250 ms 是"独占 32 GB/s"的理想值，真实可能更慢。

### 第 4 步：Q4 `parallelism_evidence`——时间收益和暴露等待要分开记录
最后一个函数输入串行时间、候选完成时间、GPU 活跃区间并集、暴露同步等待：

```python
speedup = serial_ms / elapsed_ms
elapsed_saved_ms = serial_ms - elapsed_ms
active_time_fraction = active_gpu_union_ms / elapsed_ms
exposed_sync_fraction = exposed_sync_ms / elapsed_ms
```

示例 `serial_ms=30`、`elapsed_ms=20`、`active_gpu_union_ms=18`、`exposed_sync_ms=1`：加速比 $30/20=1.5$，节省 10 ms，活跃时间占比 $18/20=90\%$，暴露同步占比 $1/20=5\%$。第三个构造是"变慢"：`elapsed_ms=32`、`exposed_sync_ms=8`，节省 $-2$ ms，加速比 $30/32=0.9375$，同步占比 $8/32=25\%$。

函数有一条区间约束：`active_gpu_union_ms + exposed_sync_ms <= elapsed_ms`，因为这两段被定义为互不重叠。把同步改成 2 ms 时占比 10%；改成 3 ms 时 $18+3>20$，抛 `ValueError`。另外，`serial_ms` 或 `elapsed_ms` 为 0 也会报错，避免除零。

这里有两个容易误读的指标。`active_time_fraction` 是"GPU 活跃区间的并集占观察窗口的比例"，只是时间覆盖，不代表计算单元、带宽或指令吞吐的利用率；多个重叠内核的时长之和也不能拿来当活跃时间，否则会超过 100%。`speedup` 和 `elapsed_saved_ms` 则回答"同样的工作，端到端到底快了多少"，必须和正确性、额外同步一起看。

读这两个例子时，注意"比例"和"绝对值"要配对：

- 30→20 ms 的加速比 1.5，意思是墙钟时间变成原来的 $1/1.5\approx66.7\%$，节省 $10/30\approx33.3\%$；换成功率/吞吐口径，才是"提升 50%"（$1.5-1$）。"时间减少三分之一"和"吞吐提升一半"描述的是同一件事，报告里最好直接写"从 30 ms 降到 20 ms，加速比 1.5"，避免歧义。
- 30→32 ms 的 `elapsed_saved_ms` 是 −2，加速比 $30/32=0.9375$，即比串行多花 2 ms、约慢 6.7%（$2/30$）。函数没有把负值偷偷截成 0，是为了让你看到真实的回归。
- 区间约束 `active_gpu_union_ms + exposed_sync_ms <= elapsed_ms` 不是形式主义。如果活跃并集 18 ms、暴露同步 3 ms、窗口 20 ms，两者相加 21 ms，说明要么同步其实落在活跃区间里（不是"暴露"），要么活跃并集算重了。函数直接拒绝，避免你把一段等待同时算进"忙"和"等"。

真实记录时，活跃区间应该来自流/事件的时间戳并集，不是把多个内核的时长相加；暴露同步要从关键路径上量，而不是所有同步调用的总和。notebook 也不对单次结果设"采用阈值"，因为 1.5 倍是否值得，要看工作量、正确性和额外复杂度，不能只凭一个比值。

`serial_ms` 的基线也必须同工作量、同正确性、同测量窗口。如果串行版本多做了一次数据校验，或者优化版本偷偷减小了 batch，比较就不成立。warmup、缓存状态、是否包含首次编译、是否同步等待，都会影响这个数。notebook 说"保持工作量与结果一致"，不是客套话：加速比的分母和分子必须是同一道题。

四个计算器的使用顺序可以这样记：先用 Q1 判断"这个阶段整体该放哪边"，它给出端到端的第一版估算；如果 GPU 路径只慢在搬运，再用 Q2 看数据能否分块、依赖前缀有多长，估算能藏掉多少；如果涉及显存容量，用 Q3 把状态大小换算成每步往返时间和暴露时间；最后用 Q4 把串行基线、实际完成时间、活跃并集和暴露同步放在一起，形成一份能复核的证据。跳过 Q1 直接做 Q4，容易拿一个"局部变快"的内核去和不对等的基线比较；跳过 Q2/Q3 直接看 Q4，则解释不了时间到底藏在哪里。

这四步都还是估算。真实系统还要看 Stream 的队列语义、事件依赖、缓冲区生命周期和首批/末批窗口，分别在第 17、29 节展开。

## 关键概念速查表
| 术语 | 大白话解释 |
|:---|:---|
| 主机（Host）/ 设备（Device） | CPU 侧 / GPU 侧，数据默认在主机内存 |
| 端到端路径 | 从输入就绪、搬入、计算、搬出到结果可用的完整时间 |
| 有效带宽 | 估算搬运时实际可用的单向带宽，单位十进制 GB/s |
| 固定传输开销 | 每次往返都要付的启动/握手成本，与数据量无关 |
| 数据依赖前缀 | 计算开始前必须等到的搬运部分，`dependency_ms` |
| 重叠（overlap） | 搬运与计算同时进行，前提是无未满足依赖且资源可并发 |
| 隐藏时间 | 串行时间减去实际完成时间，即被重叠吃掉的部分 |
| 状态卸载（offload） | 把设备上的状态移到主机以省容量，需要时再搬回 |
| 往返搬运量 | 一次卸载+回载按两倍状态大小计 |
| 加速比 / 节省时间 | 串行时间 ÷ 候选时间 / 串行时间 − 候选时间 |
| 活跃区间并集 | 多个 GPU 活跃时段合并后的总覆盖，不是时长求和 |
| 暴露同步占比 | 同步等待占观察窗口的比例，仍在关键路径上的部分 |

## 小白常见疑问

**Q1：GPU 计算 0.4 ms，CPU 要 2 ms，为什么结论是留在 CPU？**
因为比较的是完整路径，而不是单看计算时间。输入输出各 64 MB，16 GB/s 往返要 8 ms，再加 0.1 ms 固定开销，GPU 路径是 $0.4+8.1=8.5$ ms，比 CPU 的 2 ms 长。只有 CPU 慢到 100 ms 时，GPU 的 $8+8.1=16.1$ ms 才划算。

**Q2：为什么输入和输出都要算搬运？只算输入不行吗？**
GPU 算完的结果默认在设备显存里，调用方通常要拿回主机使用，所以输出回传也在路径上。`stage_placement` 的公式是 `(input_bytes + output_bytes)`，两者都计入；如果结果确实留在设备上给下一个 GPU 阶段用，那是另一种路径，需要单独建模。判断标准是"调用方要不要在主机上看到结果"：要，就得回传；不要，就可以把相邻阶段合并，只算一次搬入。这也是为什么算子融合能同时省计算启动和搬出搬入。

**Q3：8 ms 搬运、20 ms 计算，为什么前缀 5 ms 时完成于 25 ms，而不是 20 ms？**
前 5 ms 计算还不能开始，是硬等待；之后剩 3 ms 搬运，20 ms 计算足以把它盖住，所以总时间 $5+20=25$ ms。隐藏的是那 3 ms，不是整个 8 ms。只有 `dependency_ms=0` 时，8 ms 才全部被藏住，完成于 20 ms。

**Q4：75% 的搬运被隐藏了，是不是卸载就没有成本？**
不是。`estimated_exposed_ms` 仍是 62.5 ms，只是从 250 ms 降下来。而且 75% 是给定的假设，真实能藏多少要看依赖和资源；首批填充、末批排空、回载是否撞上原峰值，都要看时间线。

**Q5：活跃时间占比 90%，能说 GPU 利用率是 90% 吗？**
不能。`active_time_fraction` 只是活跃区间并集除以观察窗口，说明"有多少时间 GPU 上有活"，不说明计算单元、带宽或指令吞吐被用了多少。notebook 明确提醒，重叠内核的时长不能相加当活跃时间。报告时最好把"时间覆盖"和"资源利用"分成两栏：前者回答有没有空窗，后者回答空窗内资源是否吃满，两者可以一个 90%、另一个只有 30%。
