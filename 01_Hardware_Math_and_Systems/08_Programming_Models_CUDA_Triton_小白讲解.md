# 08. 编程模型演进 — 小白讲解

> 对应 notebook：[`08_Programming_Models_CUDA_Triton.ipynb`](./08_Programming_Models_CUDA_Triton.ipynb)

## 一句话总结
同一个 $y=(x+b)\times s$，可以用 PyTorch 分开调算子（本节分别算两个和三个的串行链）、让编译器融合、或用 CUDA/Triton 自己写内核。本节用四个计算器把差异拆开：`memory_traffic` 算出两个分离算子要读写 32 MB、三个分离要 48 MB，完全融合只要 16 MB；`block_launch_stats` 说明 48 个线程要占 2 个 32 线程的 Warp、浪费 16 个槽；`shared_tradeoff` 比较共享内存省下的 4 us 读取与每次 2 us 的同步，净收益可能是 +2、0 甚至 −2 us；`triton_candidate` 用 1000 个元素、块大小 128 检查 8 个 Program、24 个被掩码的槽和 25% 填充上限。

## 为什么需要它：痛点是什么
初学者容易把"算子越少越快"当成口号，却说不清省在哪。比如 `y=(x+b)*s`，分开写是加法、乘法两个算子，中间结果要先写回显存再读出来；融合后中间值可以留在寄存器或片上，逻辑上只读一次输入、写一次输出。但如果只会喊"融合好"，遇到"48 个线程为什么浪费""共享内存为什么有时反而更慢""Triton 的 Program 和 CUDA 的 Block 是什么关系"就答不上来。

生活类比：一条装配流水线。分离算子像每道工序做完都把半成品搬回仓库，下一道再去仓库领；融合像半成品直接在工位之间传递。仓库往返就是全局内存读写。另一个类比是包车：一辆车固定 32 个座位，48 个人要两辆车，第二辆空 16 个座位——这就是 Warp 打包，和"车队的调度效率（occupancy）"不是一回事。

本节是 CPU-first 的机制计算，不启动 GPU，也不测量真实内核。所有字节数和微秒都是构造输入，用来练习"先判断哪些工作可以减少，再决定要控制哪些执行细节"。

## 核心问题
- 三个算子分开执行与完全融合，逻辑全局读写次数和字节量差多少？
- CUDA 的线程、线程块、网格、Warp、Lane 是什么关系？48 个线程为什么占 64 个槽？
- 线程槽利用比例 75% 和 SM 占用率（occupancy）有什么区别？
- 把 64 KB 数据搬进共享内存复用一次，省下的读取时间能否覆盖同步开销？
- Triton 的 Program、Tile、Mask 分别对应什么？1000 个元素、块 128 时为什么有 24 个槽被屏蔽？

## 解决思路：一步步看懂

### 第 1 步：Q1 `memory_traffic`——先把"读写次数"算清楚
函数模型很简单：每个算子完整读取一个等大张量，并写出一个等大张量；`fused=True` 表示整条链融合，只保留一次输入读取和一次最终输出写入。

```python
reads = 1 if fused else num_ops
writes = 1 if fused else num_ops
traffic_bytes = (reads + writes) * tensor_bytes
```

输入校验要求 `num_ops` 和 `tensor_bytes` 是正整数，`fused` 必须是布尔值。固定 `tensor_bytes=8_000_000`（8 MB）时：

| 情形 | 读 | 写 | 逻辑字节 |
|:---|:---:|:---:|:---:|
| 两个算子分离 | 2 | 2 | $4\times8=32$ MB |
| 三个算子分离 | 3 | 3 | $6\times8=48$ MB |
| 三个算子完全融合 | 1 | 1 | $2\times8=16$ MB |

三个分离算子的 48 MB 是这样来的：第一步读输入、写中间结果；第二步读中间结果、写第二个中间结果；第三步读第二个中间结果、写最终输出，共 3 读 3 写。融合后中间值不落全局内存，只剩输入读和输出写，16 MB，省掉 32 MB。

这里有两个限定。第一，这是"逻辑全局读写"，缓存命中会改变真实的设备内存流量；第二，notebook 明确说 PyTorch 表达的是张量运算，实际走分离算子、编译融合还是库调用，取决于执行路径。所以不能看到 48 MB 就断言"PyTorch 一定读了 48 MB"，它只是这条串行链的上界模型。

把两个算子的 32 MB 拆开看会更清楚：输入读 8 MB、中间结果写 8 MB、中间结果读 8 MB、最终输出写 8 MB，共 32 MB。融合后中间结果留在片上，只剩输入读 8 MB和输出写 8 MB，共 16 MB。每多一个未融合的算子，就多一次"写中间结果 + 读中间结果"，在等大张量模型下固定增加 $2\times8=16$ MB。所以三个算子比两个多 16 MB（48 对 32），融合后省掉 32 MB。这个"每个边界 16 MB"的算法，比背 32/48/16 三个数更好用。

当然，融合不是没有代价：一个内核要同时完成多步计算，可能增加寄存器压力、降低占用率，或者让编译器难以向量化。notebook 的模型只算逻辑字节，不预测这些执行成本；所以"融合一定更快"也不成立，最终仍要比较包含必要适配和同步的调用时间。

### 第 2 步：Q2 `block_launch_stats`——32 个线程一组的打包规则
CUDA 的执行单位是层次化的：线程（Thread）做局部计算，一组线程构成线程块（Block），一次启动的全部线程块构成网格（Grid）。NVIDIA 硬件把同一块内的线程按 32 个一组打成 Warp，线程在 Warp 里的位置叫 Lane。函数固定 `warp_size = 32`：

```python
warps = (num_threads + warp_size - 1) // warp_size   # 向上取整
thread_slots = warps * warp_size
return {
    "warps": warps,
    "unassigned_slots": thread_slots - num_threads,
    "thread_slot_utilization": num_threads / thread_slots,
}
```

48 个线程：$\lceil48/32\rceil=2$ 个 Warp，槽位 $2\times32=64$，未分配 $64-48=16$，利用比例 $48/64=0.75$。其它断言：1 个线程也要占 1 个 Warp，浪费 31 个槽；32 个线程刚好 1 个 Warp，利用比例 1.0；33 个线程要 2 个 Warp，浪费 $64-33=31$ 个槽。

关键区分：`thread_slot_utilization` 只描述"这个块内部的线程打包"，不是 SM 占用率（occupancy）。Occupancy 描述驻留的 Warp 数相对设备上限的比例，还要看每线程寄存器、共享内存、块大小等资源。notebook 也明确说，这一问没有给出整个输入的元素数，所以不计算 Grid 需要多少块，也不处理尾部越界线程——那些留到第 15、16 节。

把 48 个线程按 Lane 摆开：第一个 Warp 的 Lane 0–31 全部有线程，第二个 Warp 只有 Lane 0–15 有线程，Lane 16–31 空着。硬件调度以 Warp 为单位，这 16 个空 Lane 仍然占着这个 Warp 的发射位置，不能塞给另一个块使用。33 个线程更极端：第二个 Warp 只有 Lane 0 有线程，其余 31 个空着；虽然 `unassigned_slots` 和 1 个线程时一样都是 31，但 1 个线程只开 1 个 Warp，33 个线程要开 2 个，Warp 数不同。

这也解释了为什么块大小通常取 32 的倍数：32 的倍数不会在块内留下半个 Warp。48 不是 32 的倍数，所以有 16 个槽浪费；如果业务只需要 48 个线程，这是打包的代价，不是"GPU 只发挥了 75% 的性能"。真正的性能还要看这些线程有没有活干、访存是否合并、Warp 内是否出现分支发散。

Q2 只算"一个块内部"的打包，还没有算"整个输入要多少个块"。如果总元素是 1000、每块 128 个线程，那么网格需要 $\lceil1000/128\rceil=8$ 个块，最后一个块只有 104 个线程有效，另外 24 个要越界保护。这个结构和 Q4 的 Triton 几何很像：都是向上取整、都有尾部空槽。区别是 CUDA 的尾部保护通常写成线程索引判断，Triton 写成 Mask；一个在块/线程层，一个在 Tile 层。notebook 把 Grid 的计算留到第 15 节，是因为这一问只关心"块内打包"，混进网格会多一个变量。

### 第 3 步：Q3 `shared_tradeoff`——共享内存的收益与同步成本
块内多个线程重复读同一块数据时，可以先把它搬进共享内存（线程块协作使用的片上存储），再让消费者读取。但写入后要同步，消费者才能安全读到。函数把收益和成本都换成微秒：

```python
saved_read_bytes = (reuse_times - 1) * tile_bytes
estimated_read_saved_us = saved_read_bytes / bandwidth_bytes_per_us
sync_us = sync_points * sync_cost_us
estimated_net_saved_us = estimated_read_saved_us - sync_us
```

示例：`reuse_times=2`、`tile_bytes=64_000`、带宽 `16_000` B/us、单次同步 2 us。复用两次意味着原本要读两遍，现在只读一遍全局，省下 $(2-1)\times64{,}000=64{,}000$ B；按 16,000 B/us 换算，读取时间省 $64{,}000/16{,}000=4$ us。

| 同步次数 | 节省读取 | 同步成本 | 净节省 |
|---:|---:|---:|---:|
| 1 | 4 us | 2 us | +2 us |
| 2 | 4 us | 4 us | 0 us |
| 3 | 4 us | 6 us | −2 us |

所以"用了共享内存"不等于"一定更快"。只复用一次（`reuse_times=1`）时，省下的全局读取为 0，`estimated_net_saved_us == -2`，纯亏一次同步。这个模型还很粗：缓存可能已经把重复读取挡住，共享内存访问本身也有开销，bank 冲突、指令数和 occupancy 都没算；notebook 把这些留给实际实现去核对。

可以算一个简单的盈亏平衡：省下的 4 us 除以单次同步 2 us，等于 2。也就是说，同步不超过 2 次时净收益非负，超过 2 次就开始亏。如果实际实现需要更多同步（比如写回、块间协作、流水线阶段），就要重新算；如果单次同步更贵，盈亏点还会前移。这个"节省 ÷ 单次成本"的思路，可以直接套到别的融合/缓存优化上。

共享内存和硬件缓存不是一回事：缓存由硬件自动管理，命中率不受你控制；共享内存由程序显式分配和同步，适合"同一块数据在同一块内被多个线程确定性地复用"。也正因为它需要显式同步，才会出现"省了读取却亏了同步"的情况。如果复用模式很规则、缓存本来就能命中，显式搬进共享内存可能是多此一举。

还有一个容量约束：共享内存是每块有限的片上资源。64,000 B 的数据块能不能整体放进一个块，要看设备每块可用共享内存和同时驻留的块数；放不下就得切分，切分又会增加同步次数和边界处理。notebook 用 `tile_bytes=64_000` 只是构造输入，不代表任何具体设备都能一次放下。

### 第 4 步：Q4 `triton_candidate`——Program、Tile 与 Mask
Triton 的抽象层次和 CUDA 不同：一个程序实例（Program）处理一个逻辑数据块（Tile），启动网格负责安排这些实例，掩码（Mask）屏蔽超出输入的位置。开发者仍要选块大小、组织地址和复用关系；块内怎样映射到线程、指令和资源，主要由编译器完成。CUDA 则更直接地用线程索引和同步原语表达。

函数先算几何覆盖：

```python
programs = (num_elements + block_size - 1) // block_size
padding_ratio = (programs * block_size - num_elements) / (programs * block_size)
```

1000 个元素、块大小 128：Program 数 $\lceil1000/128\rceil=8$，总槽位 $8\times128=1024$，填充槽 $1024-1000=24$，填充比例 $24/1024\approx2.34\%$。这 24 个槽在访问时被掩码挡住，不会越界读写。

函数还会收集未满足的条件：布局不是连续、数据类型不支持、填充比例超过上限。默认 `max_padding_ratio=0.25`，判断是严格大于：

```python
if padding_ratio > max_padding_ratio:
    reasons.append("padding_ratio")
```

于是 96 个元素、块 128 时，Program 数 1，填充 $32/128=0.25$，恰好等于上限，`stated_conditions_met` 为真；95 个元素时填充 $33/128\approx25.78\%$，超过上限，`reasons == ["padding_ratio"]`。单独的 `layout_contiguous=False` 得到 `["non_contiguous_layout"]`，`dtype_supported=False` 得到 `["unsupported_dtype"]`。

notebook 特意提醒：这个函数检查的是"给定的连续布局示例"。非连续输入也可以有对应实现，应该先改写地址计算，而不是认定 Triton 只能处理连续张量。`max_padding_ratio` 还必须在 $[0,1)$ 内，等于 1 也不接受。

把 1000 个元素按 128 一块摆开，8 个 Program 的分工是：Program 0 处理 0–127，Program 1 处理 128–255，……，Program 7 处理 896–1023。最后一块里只有 896–999 是有效元素，1000–1023 这 24 个槽在访问时被 Mask 挡住。Mask 不是"少算几个元素"，而是防止越界读写；被屏蔽的槽仍然占着块内位置和指令槽，所以填充比例会影响效率。

Mask 的工作方式是"谓词执行"：这些 Lane 仍然在 Warp 里，只是对应的加载/存储被关掉，计算也可能被跳过。如果填充比例很高，很多 Lane 一直在空转，有效吞吐就低；这就是 `max_padding_ratio` 存在的意义。它不是正确性约束（越界本身会被 Mask 挡住），而是效率约束：填充太多，说明块大小和输入规模不匹配，应该换块大小或换分块方式。

块大小一换，几何就变。若 `block_size=64`，Program 数变成 16，总槽位仍是 1024，填充仍是 24；若 `block_size=256`，Program 数 4，总槽位还是 1024；若块大小取 100，Program 数 10、总槽位恰好 1000，填充为 0。对 1000 这个规模，块大小取 64、128、256、512、1024 时都会补到 1024，填充比例相同；更小的 2 的幂（如 16）会补到 1008 或 1000，填充比例不同。Triton 的块大小通常取 2 的幂，因为编译器对这类形状的向量化和掩码更友好，但最终仍要按实际规模算 Program 数和填充。

CUDA 和 Triton 的分工也可以借这个例子对照：CUDA 里你会显式写线程索引、`blockIdx`/`threadIdx`、边界判断和 `__syncthreads()`；Triton 里你写的是"一个 Program 处理一块 Tile、用偏移和 Mask 覆盖输入"，块内怎样映射到线程、指令和资源交给编译器。两者都要检查实际布局和执行结果，只是一个把控制写在代码里，一个把更多映射交给编译器。

把这四问连起来，就是一个选择顺序：先看 Q1 的中间读写，如果反复写出中间结果，优先找现有编译融合能否消除这些边界；再看 Q3，如果确实存在块内重复读取，才考虑共享内存和同步；需要自己控制线程协作、布局或同步时，选 CUDA；只需要按数据块表达、愿意把块内映射交给编译器时，选 Triton。任何一步都要以 Q2/Q4 的打包和覆盖检查为前提，最后用包含必要适配与同步的完整调用时间判断"多出来的控制是否值得"。

## 关键概念速查表
| 术语 | 大白话解释 |
|:---|:---|
| 计算内核（kernel） | 在设备上批量执行的函数，一次启动处理很多数据 |
| 算子融合 | 把多步计算合成一个内核，中间结果不落全局内存 |
| 逻辑全局读写 | 按算法数出来的读/写字节，不考虑缓存，是上界模型 |
| 线程 / 线程块 / 网格 | 单个执行者 / 一组协作线程 / 一次启动的全部线程块 |
| Warp | 硬件把同一块内 32 个线程打成的一组 |
| Lane | 线程在 Warp 中的位置，0 到 31 |
| 线程槽利用比例 | 实际线程数 ÷ Warp 槽位数，只描述块内打包 |
| 占用率（occupancy） | 驻留 Warp 数相对设备上限的比例，还要看资源 |
| 共享内存 | 线程块内共享的片上存储，写入后需同步才能安全读 |
| Program / Tile | Triton 的一个程序实例 / 它处理的一块逻辑数据 |
| Mask（掩码） | 屏蔽超出输入范围的槽，防止越界访问 |
| 填充比例 | 被屏蔽的槽数 ÷ 总槽数 |

## 小白常见疑问

**Q1：三个算子融合后为什么只有 1 读 1 写，中间结果去哪了？**
模型假设完全融合，中间值在寄存器或片上流转，不写回全局内存。所以逻辑上只读一次输入、写一次最终输出，共 16 MB。真实实现是否真的完全融合，要看编译器有没有消除边界；notebook 说的是"完全融合假设下"。融合还受算子语义、形状、精度和编译器能力限制，不是所有算子都能合成一个内核；即使合成了，也要检查寄存器压力和数值结果。

**Q2：48 个线程占 64 个槽，能说 GPU 占用率是 75% 吗？**
不能。`thread_slot_utilization=0.75` 只是"这个块里 64 个线程槽有 48 个坐了线程"。Occupancy 是另一回事：它看一个 SM 上同时驻留多少 Warp、相对设备上限多少，还受寄存器、共享内存和块大小限制。

**Q3：33 个线程为什么也浪费 31 个槽？**
因为 Warp 固定 32 个线程，33 个线程要开 2 个 Warp，共 64 个槽，$64-33=31$。和 1 个线程的未分配槽数一样，但 Warp 数不同：1 个线程是 1 个 Warp，33 个线程是 2 个 Warp。

**Q4：共享内存明明省了 4 us 读取，为什么还可能更慢？**
因为同步有成本。示例里每次同步 2 us，同步 3 次就是 6 us，净节省 $4-6=-2$ us。若数据只复用一次，省下的读取是 0，还要付同步，更不划算。真实系统还要看缓存是否已经命中、共享内存访问开销和 bank 冲突。共享内存被划分成多个 bank，如果同一 Warp 的多个 Lane 同时访问落到同一个 bank，就会被串行化；这类冲突不在本节的字节/带宽模型里，必须实测或看编译器报告。

**Q5：1000 个元素、块 128，填充比例 2.34%，为什么 96 个元素时 25% 也算通过？**
判断条件是 `padding_ratio > max_padding_ratio`，严格大于才拒绝。96 个元素时 $32/128=0.25$，等于上限，所以通过；95 个元素时 $33/128\approx0.2578$，大于 0.25，才被拒绝。这是典型的边界 inclusion 问题，写 `>=` 就会错。边界条件要拿实际数字验证，不能凭"到上限应该拒绝"的直觉；notebook 特意构造 96 和 95 两个相邻值，就是为了把这个边界钉死。

**Q6：Triton 是不是只能处理连续布局？**
不是。notebook 的 `triton_candidate` 只是检查一个"给定连续布局示例"，`layout_contiguous=False` 会把它标成未满足条件，但解析明确说非连续输入也可以实现，只是要先改写地址计算。不要把示例条件当成 Triton 的能力边界。非连续布局的地址计算更复杂，可能破坏合并访问、增加掩码分支，所以即使能实现，也要比较实际带宽和指令开销。
