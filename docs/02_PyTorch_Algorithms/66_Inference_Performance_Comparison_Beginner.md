> 配套 notebook：[66. 单卡推理测量基线](./66_Inference_Performance_Comparison.md) ｜ 难度：Hard ｜ 环境：CPU 主线，GPU 可选

## 一句话说清

测大模型的推理速度，一组请求跑完有输出，还不算一份能拿来比较的基线。这本 notebook 教你逐条核对请求记录和汇总，判断一份测量结果能不能引用。

## 为什么需要它

你想知道模型的推理速度，于是发一组提示词，记下每条用了多久。但 notebook 开头就提醒：提示词能返回文本，不等于你得到了可比较的基线。有三个常见的漏洞：

- 模型没固定。同名模型下，一次用短提示词，一次用长提示词。后一次吞吐更高，你也说不清是服务变快了，还是输入变了。
- 流式返回被当成一个词元一块。流式接口是一块一块传内容的，一块里可能有几个词元。数块数会低估词元数，算出来的间隔也不对。
- 汇总和原始记录对不上。原始记录只有 29 条，汇总却写着完成 30 条。

这本 notebook 解决的是“怎样核对”：固定输入之后，逐条检查请求记录的时间、词元数和停止原因，再核对每轮的汇总，最后给出 `reject`（不可引用）、`tune`（先补证据）或 `ready`（可以作为参照）。

## 先认识几个词

| 词 | 人话解释 |
|:---|:---|
| 流式请求（streaming） | 回答不是等全部生成完再返回，而是一块一块地传回来 |
| 内容块（chunk） | 流式返回中的一小段内容，一块可能带好几个词元 |
| 词元（token） | 模型生成文本的最小单位 |
| 首内容延迟 | 从发出请求到收到第一块非空内容的时间 |
| 流结束 | 客户端收到的“这条请求到此为止”的信号，可能晚于最后一块内容 |
| 基线（baseline） | 拿来当参照的一份测量结果；身份和记录都核对过，才能被引用 |
| `reject` / `tune` / `ready` | 基线的三种状态：不可引用、先补证据、可以作为参照 |

## 核心思路

输入是三样：期望的身份和实际的身份，每条请求的记录，每轮的汇总。身份有 7 个字段，比如模型版本、分词器版本、负载哈希、精度。请求记录里有四个时刻、词元数、停止原因。汇总里有成功数、失败数、词元总数、吞吐和时长。

你补四个判断：

```text
身份完整且匹配 → 每条请求有效 → 每轮统计算得对 → reject / tune / ready
```

Step 2 的时间关系，用 notebook 自己的例子写成纯文本，单位是毫秒：

```text
发送 0 → 首个内容块 20 → 最后内容块 70 → 流结束 80，输出 4 个词元

首内容延迟          = 20 - 0
内容间隔代理        = (最后内容 - 首个内容) / (输出词元数 - 1)
含结束尾部的平均时长 = (流结束 - 首个内容) / (输出词元数 - 1)
输出吞吐            = 本轮成功输出的词元总数 / 从开始发送到全部结束的时长
```

除以“词元数减 1”，是因为间隔只夹在相邻两个词元之间，4 个词元只有 3 段间隔。算一遍：

```python
submit, first, last, done = 0, 20, 70, 80   # 发送、首个内容块、最后内容块、流结束，单位毫秒
tokens = 4

print(first - submit)                       # 首内容延迟
print(round((last - first) / (tokens - 1), 1))   # 内容间隔代理
print((done - first) / (tokens - 1))        # 含结束尾部的平均时长
print(done - last)                          # 结束尾部

print(120 / 3)                              # 一轮成功输出 120 个词元，用时 3 秒

# 状态：有失败就拒绝，失败和缺失都为空才可引用
def status(failures, missing):
    return "reject" if failures else ("ready" if not missing else "tune")

print(status([], []), status([], ["exact_output_tokens"]),
      status(["time_order"], ["exact_output_tokens"]))
```

```text
20
16.7
20.0
10
40.0
ready tune reject
```

两种间隔要分别命名、分别保存。按可见内容算出来是 16.7，把最后 10 毫秒的结束尾部也算进去就是 20。notebook 说明两者都不是 GPU 上单个词元的计算时间；只有一个输出词元时，不计算间隔。

吞吐是每秒 40 个词元。分子只数成功输出的词元，分母是整轮的时间，失败请求也留在本轮的计数里。

最后一行是 TODO 4 的优先级：失败和缺失都没有，是 `ready`；只有缺失，是 `tune`；有失败就是 `reject`，哪怕同时有缺失。

## 容易踩的坑

- **把内容块数当词元数**：一个内容块可能带多个词元。间隔类指标要用后端准确报告的词元数；词元数只是估算时，它是一项缺失证据。
- **吞吐的分母算错**：分子是本轮成功输出的词元总数，分母是从开始发送到全部请求结束的整段时间。对每条请求的生成速率取平均，或者删掉请求之间的等待，都会改掉这个分母。
- **把已知失败和证据缺失混在一起**：只有 29 条记录却声称完成 30 条，是已知不一致，必须 `reject`。30 条都在、但词元数只是估算的，是缺证据，先补采，状态是 `tune`。
- **换了输入还比快慢**：模型和分词器的实际版本、请求内容与顺序、生成规则、精度、服务配置都要固定。本次是单并发，一条结束后再发下一条。
- **把记录完整当成质量通过**：`ready` 只说明基线可以被同条件比较引用，不等于优化收益或回答质量已经通过。因达到上限而停止的请求要单列，不自动当作回答完整。
