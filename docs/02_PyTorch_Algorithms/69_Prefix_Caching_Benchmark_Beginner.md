## 一句话说清

前缀缓存把已经算过的开头部分存起来，后面的请求开头相同时直接复用。这本 notebook 教你比较开关缓存的效果，并判断该不该采用。

## 为什么需要它

很多请求的开头是一样的，比如同一段系统提示。模型处理每个请求，都要先把整段输入算一遍，这一步叫预填充（prefill）。开头相同，这部分计算其实是重复的。前缀缓存复用的是已经计算出的 K/V，开头相同的请求可以跳过重复的预填充，首词元延迟（TTFT）因此可能缩短。

但开启缓存不等于一定有收益：

- 实际命中不足。开头相同的请求没几个，或者缓存条目被挤掉了，省不下多少计算。
- 缓存占了容量。保留更多缓存会占用物理容量，影响新请求。
- 只看命中率。命中率高，不等于请求更快，也不等于输出没变。

notebook 登记的一次真实对照就是例子：命中与延迟收益成立，但输出等价性和缓存开启后的重复稳定性没通过，结论是 `tune`，不是采用。

所以要把同一请求集合在关闭和开启缓存时的表现放在一起看。这本 notebook 的主线在 CPU 上把这套判断练熟：核对缓存身份、统计连续命中、收集配对证据、给出采用状态。真实服务上的对照放在可选的 Step 5。

## 先认识几个词

| 词 | 人话解释 |
|:---|:---|
| 前缀缓存（prefix caching） | 把请求开头已经算出的 K/V 存下来，后面开头相同的请求直接复用 |
| K/V | 注意力计算里由输入词元算出的中间结果。同一段文本换个模型或位置，算出的 K/V 就不同 |
| 缓存命名空间（namespace） | 允许共享缓存的范围。模型权重、分词结果、聊天模板、适配器、位置和注意力配置、缓存精度、访问权限都一致，才算同一范围 |
| 完整块（block） | 请求按固定词元数切成的块。只有完整的块进缓存，尾部不足一块的部分照常计算 |
| 最近最少使用（LRU） | 缓存满了，先淘汰最久没被访问的条目 |
| 首词元延迟（TTFT） | 从请求发出到第一个内容词元到达的时间 |
| 输出等价性 | 关闭和开启缓存时，同一请求的输出是否相同 |

## 核心思路

输入是基线和候选两份运行记录：基线关闭缓存（G0），候选开启缓存（G1），记录里带着身份字段、命中记录、各项指标和输出核对结果；另外还有三个门槛。你要补的是三个判断：身份和开关能不能比、证据够不够、收益达没达标。输出是 `reject`、`tune`、`accept` 之一，加上下一步动作。

notebook 已经写好了分块、查缓存和淘汰的代码，其中最关键的一点是：块的键必须包含之前的前缀。

```python
def key(blocks, i):      # 块位置 + 从第 0 块到当前块的全部内容
    return (i, tuple(blocks[:i + 1]))

cache = {key([(1, 2), (3, 4)], 0), key([(1, 2), (3, 4)], 1),   # 处理过 [1, 2, 3, 4]
         key([(9, 9), (5, 6)], 0), key([(9, 9), (5, 6)], 1)}   # 处理过 [9, 9, 5, 6]

blocks = [(1, 2), (5, 6)]        # 新请求 [1, 2, 5, 6]，每 2 个词元一块
hits = 0
for i in range(len(blocks)):
    if key(blocks, i) not in cache:
        break
    hits += 1
print(hits)

naive = {(0, (1, 2)), (1, (3, 4)), (0, (9, 9)), (1, (5, 6))}  # 只用“位置 + 当前块内容”
print([(i, b) in naive for i, b in enumerate(blocks)])
```

```text
1
[True, True]
```

新请求 `[1, 2, 5, 6]` 切成 `(1, 2)` 和 `(5, 6)` 两块。第一块的键能查到；第二块的键是“位置 1 加上 `(1, 2)`、`(5, 6)` 这段历史”，缓存里没有，查找在下标 1 停下，只复用了开头的 2 个词元。如果只用“位置加当前块内容”做键，`(1, (5, 6))` 能在缓存里找到，因为它来自 `[9, 9, 5, 6]`；但那份 K/V 是在另一个上下文里算出来的，这次不能用。

三个判断按下面的顺序做，和参考代码一致：

```text
身份字段有缺失或两边不一致、任一运行失败  → reject
缺指标，或候选没有直接命中记录            → tune
请求没有成功返回非空输出                  → reject
输出不等价，或重复运行不稳定              → tune
命中率、TTFT 改善、吞吐改善都达到下限      → accept，否则 tune
```

直接命中记录（字段 `backend_cache_hit_observed` 为 `True`）只能来自后端的命中记录，不能由更低的延迟反推。

采用门槛里的命中率是请求级的。notebook 提醒它和词元复用比例的分母不同，不能混用：

```python
hit_requests, request_count = 1, 4      # 4 个请求里 1 个有命中
reused_tokens, total_tokens = 4, 32     # 32 个输入词元里复用了 4 个
print(hit_requests / request_count, reused_tokens / total_tokens)
```

```text
0.25 0.125
```

前一个数是请求级命中率，模拟函数 `simulate_prefix_cache` 里叫 `hit_rate`，TODO 3 用的字段就是它；后一个数是词元复用比例，代码里叫 `token_reuse_rate`。

## 容易踩的坑

- **两边都缺身份当成一致**：`model_revision` 这类身份字段，任一边为空或两边不同，`namespace_ok` 都应为假。“都未知”和“已确认一致”不是一回事。
- **开关没有形成对照**：基线的 `prefix_cache_enabled` 必须是 `False`，候选必须是 `True`。关闭／开启是本次唯一的策略变化，其他条件要保持一致。
- **块的键只用了位置和内容**：同一位置的块内容相同，但前面的历史不同，仍然不能复用。命中数只数从第 0 块开始连续命中的部分。
- **把缺失的指标补成 0**：缺的观测字段要原样记进 `missing_evidence`，候选没有直接命中记录也算缺证。缺证的决策是 `tune`，不是拒绝。
- **只凭一个好数字采用**：命中率、TTFT 改善、吞吐改善三项要同时达到下限。请求成功返回也不等于输出等价，输出核对没过同样不能 `accept`。
