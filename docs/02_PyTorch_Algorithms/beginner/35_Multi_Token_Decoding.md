## 一句话说清

大模型生成时通常一次只出一个词。这本 notebook 讲一种把“猜词模块”直接做进大模型里的办法：内部先给出几个候选词，再逐个核对，对得上几个就用几个。

## 为什么需要它

普通的生成是一轮一个词元。想一轮多推进几个，常见的投机解码要另外请一个独立的小模型当草稿模型，先猜、再让大模型检查。

原生多 Token 预测（MTP）换了个思路：猜词的模块不是外挂的小模型，而是目标模型自己内部的一部分。它复用大模型已经算好的状态，对后面几个位置各给出一份词表分数，每份取一个最高分的词元，就组成了一串候选。检查用的是贪心规则：把候选和目标模型在同一位置的答案逐个对比，一样就留下，遇到第一个不一样就停下。

- 停下时：前面已经对上的候选照常提交，再补上目标模型在这个位置的答案，本轮结束。
- 全部对上：整串候选都提交，再从目标模型多看的一个位置补一个词元。

候选有几个，只说明这轮最多试几个位置；真正算数的是“从开头起连续对上了几个”。候选块越长，潜在推进量越大，但候选计算和验证的成本也越高。这本 notebook 在 CPU 上把这三步写出来：取候选、数连续匹配的长度、拼出本轮输出。

## 先认识几个词

| 词 | 人话解释 |
|:---|:---|
| 原生多 Token 预测（MTP） | 把未来位置的预测模块放在目标模型内部，一次形成多个候选词元，不再依赖独立草稿模型 |
| 预测深度（depth） | 内置模块的编号。不同深度面向不同的未来位置给出词表分数，顺序和待验证位置一一对应 |
| 候选块 | 每个深度各取一个词元，按位置排成的一串，比如 `[1, 0, 2]` |
| 预算 `max_candidates` | 本轮最多允许几个候选。候选数不能超过它，也不能超过深度数 |
| 目标首选 Token | 目标模型在同一个位置上分数最高的词元，用来和候选对比 |
| 连续接受长度 | 从第一个位置起，候选和目标首选连续相同的个数。第一次不同之后的候选都不算 |
| 修正 / 追加 Token | 第一次不同的位置上，补进输出的目标首选词元叫修正；全部相同时从额外位置补的词元叫追加 |

## 核心思路

输入是一张词表分数表 `depth_logits`，形状 `[depth, vocab]`，每个预测深度一行；另有一个预算 `max_candidates`。分三步：

```text
① 取候选：每一行取分数最高的词元，只保留前面最多 max_candidates 个，组成候选块
② 数匹配：候选块和目标结果从第一个位置起逐个比，数出连续相同的个数 accepted_length
③ 拼输出：
     accepted_length 等于候选块长度 → 整个候选块 + 目标结果在额外位置的词元
     否则                           → 前 accepted_length 个候选 + 目标结果在第一个不同位置的词元
```

用测试里的数字走一遍。3 个预测深度，词表大小是 3：

```python
import torch

depth_logits = torch.tensor([[0.1, 0.9, 0.0],      # 深度 1：面向下一个位置
                             [0.8, 0.1, 0.1],      # 深度 2：面向再下一个位置
                             [0.2, 0.3, 0.5]])     # 深度 3：面向更远的一个位置
candidates = depth_logits.argmax(dim=-1).tolist()   # 每个深度各取最高分的词元
print(candidates)

def one_round(candidates, target_tokens):
    accepted = 0
    for c, t in zip(candidates, target_tokens):
        if c != t:
            break                                   # 首次不匹配，停止
        accepted += 1
    emitted = candidates[:accepted] + [target_tokens[accepted]]   # 接受前缀 + 目标模型在下一个位置的词元
    return accepted, emitted, accepted == len(candidates)

print(one_round(candidates, [1, 0, 2, 0]))          # 全部匹配
print(one_round(candidates, [1, 2, 2, 0]))          # 第二个位置不同
```

```text
[1, 0, 2]
(3, [1, 0, 2, 0], True)
(1, [1, 2], False)
```

第一行是候选块 `[1, 0, 2]`。第二行是全部匹配：目标结果前三个位置都是同样的词元，3 个候选全部提交，再补上额外位置的目标词元 0，一轮输出了 4 个词元。第三行是第二个位置不同：候选是 0，目标是 2，到这里就停。第三个候选其实和目标相同，但它在不同的位置之后，照样丢弃。本轮输出是接受的前缀 `[1]`，加上目标在第二个位置的词元 2。

每轮只在接受前缀之后加入一个目标词元。另外要分清三个量：候选长度只是本轮最大尝试范围，不等于实际推进量；连续接受长度是可以直接提交的候选数，但不等于端到端加速比；每轮输出长度还要结合候选和验证成本一起看。

## 容易踩的坑

- **候选顺序被重排**：每个深度对应一个固定的未来位置，候选块只能按深度顺序排，不能按分数高低重排。
- **候选数超过了预算或深度数**：每行取最高分之后，要截到 `max_candidates` 个以内。预算必须是正整数，`depth_logits` 必须是非空二维张量。
- **把后面的匹配也算进接受长度**：接受结果只能是候选块从头开始的连续前缀。第一次不同之后就停止，后面即使相同也不能越过它进入输出。
- **一轮里追加了不止一个目标词元**：部分匹配时只加入第一个不同位置的修正词元，全部匹配时只加入额外位置的词元。未验证的候选后缀不得进入输出。
- **把接受长度当成加速比**：连续接受长度只是可直接提交的候选数，端到端快不快，还要结合候选计算和验证成本。
