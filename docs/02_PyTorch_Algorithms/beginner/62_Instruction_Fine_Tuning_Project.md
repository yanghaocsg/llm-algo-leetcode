> 配套 notebook：[62. SFT 训练交付项目](../62_Instruction_Fine_Tuning_Project.md) ｜ 难度：Hard ｜ 环境：CPU + 单卡 GPU

## 一句话说清

模型微调训练完，不能只凭“损失降了”就把结果交出去。这本 notebook 带你写三道检查：能不能开始训练、中断后能不能接着练、训练产物能不能交付。

## 为什么需要它

设想一次监督微调（SFT）训练到一半，进程被打断。你从保存下来的状态接着练，练完拿到一份训练产物。这时候有三件事容易出问题：

- 上游的选型结果里混进了别的配置的测量记录。你照着一份不可靠的清单开始训练。
- 恢复时接错了位置。比如目标 20 步，第 10 步保存，重启后第一步却是第 12 步。第 11 步的更新丢了，记录看上去却仍然“完成了 20 步”。
- 训练时损失一路下降，就直接交付。但没人确认过：把训练结果保存下来，再加载进一个新模型，评测结果还和保存前一样吗？

这本 notebook 解决的是其中的判断部分：把这三件事写成三道检查。每道检查都是一组必须同时成立的条件，任何一项不通过就停下，并报出是哪一项。

## 先认识几个词

| 词 | 人话解释 |
|:---|:---|
| 检查点（checkpoint） | 训练到某一步时存下来的一整套状态，训练中断后靠它接着练 |
| 适配器（adapter） | LoRA 训练出来的那部分参数，是本项目的训练产物 |
| 选型清单（manifest） | 上一环节留下的记录：选了哪个配置、复测结果、产物放在哪 |
| 复测 | 用不同的随机种子，把同一个候选配置再跑几次，确认结果不是碰运气（候选就是一份待选的配置，比如 `rank8`） |
| 哈希（hash） | 把文件或配置算成一串指纹，指纹相同才算同一样东西（如 `data_hash`） |
| 重载（reload） | 训练结束后，在一个新模型实例里重新加载适配器，再评测一次 |
| 合取关系 | 几个条件必须同时成立，任何一项失败，整体就算失败 |

## 核心思路

输入是三份记录：上游的选型清单、中断时留下的检查点、训练结束后的评测结果。你依次做三次判断。每次的输出都是一个决定，`accept`（接受）或 `reject`（拒绝），外加失败项的名字列表。

```text
关卡 1  选型清单   能不能作为训练输入
关卡 2  检查点     能不能从保存步接着练
关卡 3  评测结果   产物能不能交付
```

导读里的“上游”和“血缘”说的是输入从哪来：本项目唯一直接读的是 63 节的选型清单，它记录着自己用了 64 节通过检查的哪一版数据（notebook 里叫“数据准入快照”）。

三道关卡里最容易被忽略的条件，写成纯文本是：

```text
恢复首步 == 保存步 + 1
质量通过  <=>  最终评测损失 <= 初始评测损失 + 允许退化上限
重载通过  <=>  重载损失的绝对差 <= 允许容差
决定 = accept   当且仅当   全部门槛都通过
```

`<=>` 读作“当且仅当”。另外两个词这样理解：

- 训练身份：模型版本、数据哈希、更新配置哈希三项。三项都要和当前训练一致，否则启动新运行，不复用旧的优化器状态。
- 可训练状态：适配器、优化器、学习率调度器和随机数状态四类。四类都要存在且能读取，缺了就先修复检查点。

把三道关卡缩小成几行代码：

```python
# 关卡 1：复测是否属于同一候选，随机种子是否重复
selected = "rank8"
repeats = [{"name": "rank8", "seed": 42}, {"name": "rank8", "seed": 43}]
seeds = [item["seed"] for item in repeats]
print([item["name"] == selected for item in repeats], seeds, len(seeds) == len(set(seeds)))

# 关卡 2：恢复后的第一步是否紧接保存步
saved_step, first_resumed_step, total_steps = 10, 11, 20
print(0 < saved_step < total_steps, first_resumed_step == saved_step + 1)

# 关卡 3：所有门槛都通过才接受
checks = {"quality": 1.8 <= 1.9 + 0.0, "reload": 1e-6 <= 1e-4}
failed = [name for name, ok in checks.items() if not ok]
print("accept" if not failed else "reject", failed)

checks["reload"] = 0.01 <= 1e-4
failed = [name for name, ok in checks.items() if not ok]
print("accept" if not failed else "reject", failed)
```

```text
[True, True] [42, 43] True
True True
accept []
reject ['reload']
```

第一行的三个结果分别是：每次复测的名字都等于选中的名字、种子列表是 `[42, 43]`、种子没有重复。重载差值是 `1e-6`，没有超过允许的 `1e-4`，所以接受。把它改成 `0.01` 之后，质量那一项仍然通过，整体却被拒绝，失败项里只剩 `reload`。

还有两点边界。损失下降只说明参数发生了更新，不能代替独立评测。重载是在同一个进程里新建模型实例，notebook 注明当前不退出进程。

## 容易踩的坑

- **只看 `accept` 就开始训练**：上游清单写着接受还不够。复测至少 2 次，状态都是 `ok`，名字都等于选中的配置名；随机种子必须是不小于 0 的整数，而且不能重复。
- **同名就当成同一候选**：复测记录如果带 `config` 字段，它必须和选中的配置完全相等。同名但配置漂移，也要判失败。
- **身份变了还复用旧状态**：模型版本、数据哈希、配置哈希里任何一项对不上，旧优化器状态就不再属于当前训练，应当启动新运行。
- **恢复首步没有紧接保存步**：第一步必须等于保存步加 1，错位就停止恢复，去检查进度记录。保存步还必须落在起点和目标步之间。
- **把损失下降当成可以交付**：交付门槛是合取关系，任一失败都是 `reject`。解析里明确提醒：保留每项硬门槛和失败字段，不使用综合分数。
